# Designs

Technical design of Calm Terminal. What the features do is in [FEATURES.md](FEATURES.md); this document covers how. Items marked **Decided** record a choice and why; what is still open is marked as an open question. Source files and type names are given so the code can be read; the code is the reference for their exact shape.

## Tech stack

| Layer | Choice |
|---|---|
| Language | Swift 6, strict concurrency checking on |
| UI | SwiftUI for chrome (sidebar, panels, settings, search); AppKit for windows and the terminal view |
| Terminal engine | libghostty, used through the GhosttyKit framework |
| Storage | JSON for app state (`state.json`); SQLite FTS5 for the search index |
| Build | XcodeGen (`project.yml`) + `mise` tasks |
| Quality | swiftformat, swiftlint, Swift Testing |
| Minimum OS | macOS 26, Apple silicon (decided in M0.1; keeps the codebase free of old-version branches) |

**GhosttyKit source:** built from upstream Ghostty (`ghostty-org/ghostty`) at the commit pinned in `scripts/ghostty.env`, with the patches in `scripts/ghostty-patches` applied, and the Zig version Ghostty requires (pinned in `mise.toml`), locally and in CI. No prebuilt binaries, and no fork as the source: the patches are reviewable files in this repository.

- `scripts/ghosttykit.sh` checks out the commit, applies the patches in name order (a patch that doesn't apply stops the build rather than building half of it), builds `GhosttyKit.xcframework` (native arm64, ReleaseFast, no i18n or Sentry) plus Ghostty's resources (themes, shell integration, terminfo), caches them per commit and patch set in `~/Library/Caches/calm/ghostty/<commit>-<patches hash>`, and copies them into `Frameworks/` (not tracked).
- **Patches (decided 2026-09-29):** smooth scrolling, taken unchanged from `thdxg/ghostty` (a Ghostty fork, MIT) rather than written here: upstream has only the first piece (RenderState overscan, ghostty-org/ghostty#14400), and the fork's patch carries fixes found by measuring rendered frames that a rewrite would have to find again. The Ghostty pin follows the fork: `GHOSTTY_COMMIT` is the upstream parent of the fork commit the patches come from (`GHOSTTY_PATCHES_FROM`), so they always apply. `scripts/ghostty-patches/README.md` says what each patch does and how to move to a newer Ghostty. Drop a patch once upstream covers it. Calm's own patches (0007 and up) sit beside the fork's, each a separate small file: 0007 makes `read_text` report a row where smooth scrolling draws it, as the fork's patch already does for the IME position, so link marks and cell hit-testing stay on their rows; 0008 keeps an overlay a program redraws inside its scrolling region (Claude Code's "Jump to bottom" hint) out of the region scroll animation, which otherwise drew it two or three times per scroll; 0009 extends the padding beside a row only when the row's first (or last) three cells share a background or the row above or below has the same color at the edge, so a program's own cursor at column 0 (pi draws one as a reverse-video cell) stays a cell instead of growing out into the padding, while a pane painted in one color with its content inset (OpenCode) still extends; 0010 animates a program that moves its content by repainting rows rather than scrolling them (pi's full-screen view), by finding the rows that moved; 0011 lets a link under ⌘ work while a program has the mouse captured (Claude Code's full-screen view, vim, htop); 0012 pins only the cells of such an overlay rather than its whole row, so the text on that row still slides with the rest.
- `scripts/ghostty-deps.py` prefetches Ghostty's Zig packages with curl into the project-local `zig-pkg/`, because Zig's HTTP client fails behind some local HTTP proxies.
- A Ghostty `main` commit is pinned rather than the v1.3.1 release: v1.3.1 needs Zig 0.15.2, which cannot link against the macOS 26.5 SDK. Move to the next Ghostty release once it supports Zig 0.16.
- Building needs Xcode's Metal Toolchain (`xcodebuild -downloadComponent MetalToolchain`) for Ghostty's shaders.

Packages/CalmKit/        UI-free Swift package (see the module map)

Ghostty's resources are copied into `Calm.app/Contents/Resources/{ghostty,terminfo}` at build time, and `GHOSTTY_RESOURCES_DIR` points at them unless already set.

Rules:

- **CalmKit** has no dependency on SwiftUI, AppKit or GhosttyKit, so it is fully unit-testable (`swift test`).
- **Terminal** is the only code that touches GhosttyKit (two app-hosted tests aside).
- Each **CalmAgents** adapter is self-contained; adding an agent never changes the core.

## Data model

In CalmModel (`Workspace.swift`, `AgentRun.swift`, `SessionState.swift`):

- A `Project` is a sidebar group: a folder, a name, and a kind (`.project`, made by the user; `.directory`, made by grouping; `.scratch`).
- A `Session` is one shell. It has its folder and group, whether it stays pinned there, its `SessionState` (idle, working, needs you, done, failed) with the `StatusReport` behind it, the user's name for it, and a scratch session's hidden folder. Its id is exported to the shell as `CALM_SESSION_ID`.
- While an agent runs in the foreground, the session holds an `AgentRun`: which agent, its process, its own session id and transcript, and the latest `TranscriptTail` (title, recap, step, progress, interruption, the agent's folder). When the agent exits, its `AgentConversation` stays as `lastConversation`, so it can be resumed.

Panes and tabs are **views of sessions**: a layout tree references session IDs. Closing a pane closes its session and ends its shell (`SessionManager.closeSession`); quitting Calm detaches shells instead.

As built (M2): `Workspace` holds `projects`, `sessions` and `layouts`. A `PaneLayout` is one tab: a `SplitTree<Session.ID>` plus the focused session. Every session is one pane, so a split creates a session and `⌘T` creates a session with its own layout. Calm has **one main window**; "new window" requests from libghostty become new sessions, since the sidebar replaces windows and tabs as the way to hold many shells.

## Auto-grouping

1. The shell reports its working directory (OSC 7 through libghostty's pwd action). For panes that never send OSC 7, `SessionProbe` reads the shell's folder with `proc_pidinfo(PROC_PIDVNODEPATHINFO)` every 2 seconds: the shell's pid comes from `zmx list` for persistent sessions (looked up only when unknown) and from `ghostty_surface_foreground_pid` otherwise.
2. On change, a session that isn't pinned is refiled: the most specific project the user made that contains the folder, else the directory group keyed by the git repository's root, or by the folder itself outside a repository (made if needed). A directory group matches its key exactly; it never contains other folders, which is what let an automatic home-folder project swallow every session under `~` before (found in real use).
3. Pinned sessions stay: those started in a project (`Placement.project`, and ⌘T or splits inheriting it) and scratch sessions (`Placement.scratch`, only from ⌘⇧N). ⌘T or a split from a scratch session opens a directory session at home, so a scratch folder is never shared by accident.
4. Moves are animated in the sidebar (`matchedGeometryEffect`, so a row glides from one group to the other). Empty directory groups and an empty scratch group are removed.
5. With `auto-grouping = false`, the folder is still recorded but the session stays where it is.
6. At launch, `refileAll` files every unpinned session again, so a workspace saved under older rules finds its groups. State files before kinds (`isAutomatic`) load as `.directory`/`.project`; both keys are written, for older builds.
7. Scratch folders live under `~/.local/share/calm/scratch/`, named by time and never shown. Not a temporary directory, which macOS clears, and not Application Support: a working folder's path shows in the prompt and reaches every tool, and the space in "Application Support" trips tools that don't quote paths. The path is fixed, next to `~/.config/calm`, rather than read from `$XDG_DATA_HOME`, which an app opened from the Dock doesn't see. Folders made before this stay where they were: a session keeps its folder's full path, and the files column knows a scratch session by its session, not its path. The root is excluded from Time Machine; the exclusion is set on the root only, because it travels with a moved item and a folder kept as a project must be backed up. Self-tests and unit tests keep theirs under their own support folder. Closing the last session in one removes it when empty, or moves it to the Trash after asking. Keep as Project… moves the folder where the user picks; the shell stays inside it (only its path string is stale until it `cd`s).
8. No session is opened at launch: the first launch (no state file yet) shows the welcome page, and a later launch restores what was open, the welcome page if nothing was. Self-tests start with a home session unless `--welcome`. What the page holds is in Search → Welcome page.

**Project marks.** `Identicon` (CalmModel) makes a project's mark from its name: a 5×5 grid mirrored left to right, in one of eight hues spread around the wheel (a hue taken straight from the hash bunched up). The hash is FNV-1a, not Swift's `Hasher`, which is seeded per process: a mark must stay the same across launches. Clicking the mark stores a random `Project.markSeed`, mixed into the hash, so the new mark is kept. `GroupMark` and `IdenticonTile` draw it in the sidebar, the title strip and the welcome page.

## Agents

**Adapters (CalmAgents).** `AgentAdapter` says what an agent is: the names, binary prefixes and package paths its process runs under, its config folder (present means installed), how it connects to Calm (`AgentSetup`), its mark, and its resume and fork commands. An agent can also adopt `HookReporting` (its hooks call `calm hook <name>`), `TranscriptReading` (find and read its transcript for cards) and `TranscriptIndexing` (search). `Agents.adapters` lists them.

**Detection (as built, M3.1).** `SessionProbe` looks at every session every 2 seconds. A persistent session's shell pid comes from `zmx list`; `proc_pidinfo(PROC_PIDTBSDINFO)` gives the terminal's foreground process group (`e_tpgid`), and when it differs from the shell's own group a job is running. Only when that job changes does Calm read its path and arguments (`sysctl KERN_PROCARGS2`) and ask the adapters. Without zmx, the pane's foreground process (`ghostty_surface_foreground_pid`) is used. Adapters in `CalmAgents` match on executable or script names, per-platform binary prefixes, and package paths for scripts run by node or bun. Agent runs saved by an earlier launch are kept and checked before the window opens (Launch, below); they used to be cleared and found again by the first probe tick.

**Launch (as built, 2026-09-29).** A Restart used to show every session as idle and light them up one by one: `restore` cleared each saved agent run (and turned *working* into idle), the first probe tick came two seconds later, and rediscovering an agent never set *working*, only its next hook did. On the 22:29 restart, of five sessions saved *working*, two came back in 0.8 s and 1.5 s and two 22 s and 64 s later (a long tool call, a long reply: no hooks meanwhile). Now the sidebar comes back as it was left:

- `restore` keeps the saved runs. `SessionProbe.settleSavedRuns`, before the control server and the window, asks `LaunchPass` (off the main thread: `zmx list`, each saved session's shell foreground job with the probe's own syscalls, `Agents.detect` for the saved kind, and the adapter's `LiveStatusReading`) and waits for it up to `LaunchPass.budget` (250 ms; the pass took 3 ms for one session in the end-to-end check, most of it the `zmx list`; each further session adds a few syscalls and one small file read, so the budget is generous, and a dozen sessions haven't been timed yet). Claude Code's adapter reads `~/.claude/sessions/<pid>.json`: `status` (`busy` and `idle` seen on disk, `waiting` in the 2.1.283 binary), `statusUpdatedAt` (ms) and `waitingFor`; the file must name the pid it is read for. Nothing else keeps such a file yet, so other agents settle by the last rule below; Codex and OpenCode then correct themselves at the first regular tick, from their transcripts (`TranscriptTail.stateChange`: a turn that started and hasn't ended is working).
- `Workspace.settleSavedRun` (CalmModel, tested) decides per session from what the pass found: the run is kept only if the same agent still has the shell's foreground as the same process (or the run's process was not yet known); otherwise it ends, as an exit does. Where the agent's status speaks after the last report (within a second), it corrects the state: *working* while it says idle; idle, done or failed while it says busy (its `statusUpdatedAt` becomes the state's start, so "Working · 4m" keeps counting). *Needs you* and `waiting` are left to hooks until each agent's wording has been seen. With no status to ask, a saved *working* stands only if `state.json` was written under 30 s ago (a Restart); older, it is idle, as any launch made it. The pass also seeds the probe's shell list and foreground jobs, so its first tick neither asks zmx again nor takes a confirmed agent for a new one.
- If the pass isn't done within the budget, `SessionManager.confirming` names the rows and they show as loading (UIUX.md → Session states → Restoring). The answer is applied, with the state, when it comes, held for at least 450 ms after the loading began so a quick answer never flashes it; a pass that has not answered within 2 s (`LaunchPass.deadline`) is given up on, and every saved run ends as it used to. Quitting while rows load loses nothing: the saved state is only changed when the answer is applied.
- The transcript tail is saved with the run, so the first frame has its title, recap and todos; the first regular tick reads the transcripts again, off the main thread, and a tail that hasn't changed changes nothing.
- Checked end to end with a stand-in `claude` process and a status file of its own (`scripts/selftest.sh --persist --state`, launched over and over on one state file): kept, corrected either way, gone, and a slow pass (`CALM_LAUNCH_PASS_DELAY_MS`, debug builds).

**Supported agents, and removing one.** Claude Code, Codex, OpenCode and pi. omp was supported until 2026-09-29 and removed (little use, and not installed to check against): its adapter, mark, resume commands and search parser are gone. Removing an agent must not cost anyone their sessions, so an agent Calm doesn't know reads as no agent wherever it was saved: `Session.init(from:)` decodes `agent` and `lastConversation` leniently (`WorkspaceStore` starts over with an empty workspace when anything fails to decode, and a test covers a saved omp run), and the search index skips rows whose agent it doesn't know. Follow the same rule for the next removal.

**Claude Code hooks (as built, M3.4).** At each launch Calm writes a plugin (`.claude-plugin/plugin.json`, `hooks/hooks.json`) to `~/Library/Application Support/Calm/agents/claude-code` and adds that folder to `CLAUDE_CODE_PLUGIN_DIRS` (keeping the user's own entries) in the shells it starts. Claude loads it as `calm@inline` in those sessions only; nothing is written to `~/.claude`. Every hook runs `[ -n "$CALM_CLI" ] && "$CALM_CLI" hook claude-code || true`, synchronously so reports keep their order (`calm hook` gives up on the socket after 1 s). `calm hook` reads the payload on stdin; `ClaudeCodeAdapter.hookReport` maps it (UserPromptSubmit/PreToolUse/PostToolUse → working, PermissionRequest → needs you with "Allow Bash: …", Notification permission/elicitation → needs you, Stop → done with a one-line recap of `last_assistant_message`, or working while its `background_tasks` lists a `subagent` in flight (it wakes Claude when it ends, and that turn's Stop reports again). Every other task in flight counts as a shell (a Monitor arrives as `shell`, and a dev server or watcher never ends, so nothing would wake Claude): the Stop is done, and the count travels to the app as `shells` on the control request and as `StatusReport.backgroundShells`, for the card's "· 2 shells running" (not saved: it is one Stop's snapshot). Only `running` and `pending` tasks count, and a task with no status counts too, since the list is for work still in flight. Only `shell` and `subagent` are seen in captured payloads; the count also isn't cleared when a shell dies without waking Claude, which is why it only lives while the card says done. StopFailure → failed) and passes on the agent's session id and transcript path for transcript tails. Opt out with `claude-code-hooks = false` under `[agents]`. An Esc interrupt fires no `Stop`; the transcript tail catches it instead (below). Fixtures are built from the documented payload fields and should be replaced with captured payloads while dogfooding.

**Transcript tails (as built, M3.7 and M3.7b).** Claude Code, Codex, OpenCode and pi each have a `TranscriptReading` adapter: `transcript(forProcess:)` finds its transcript, `readTail` reads it (title, the latest agent text as a plain-text recap through `MessageText.recap`, whether the newest turn was interrupted, and step and progress where the agent keeps todos), and `changeMarkers` names the files whose size or modification time show it changed (OpenCode's `-wal` too). `SessionProbe` re-reads only on a change, one background read per session at a time: a transcript can hold megabytes of tool output, so the reading never runs on the main thread. An interruption settles *working* to idle, but only if the transcript was written after the latest report, since a new prompt's hook can arrive before its transcript line.

*Where the transcript is.* What a hook or extension reported (`calm hook`, or `calm status --transcript`) wins. Otherwise the adapter finds it from the process, tried every 4 s until it works and every 20 s after (an agent's `/new` starts another transcript); a different answer is adopted, but a failed search never drops a known transcript. The adapters share `ProcessFacts` (the process's folder, start time, terminal and arguments, and the files open in it and its children, all from plain syscalls) and `TranscriptDiscovery`: the transcript the process has open, else the agent's own rule, else *the only* transcript that starts in the process's folder and was written since it started. Two candidates mean unknown and no transcript is chosen: a card that shows another conversation's recap is worse than one that shows none.

*Reading a JSONL file.* `JSONLTail` reads from the end, newest record first, a block at a time. It stops after 512 KB of records and passes over any line longer than 512 KB unparsed (up to 32 MB in all): Codex's and pi's tool results reach megabytes (13 of 140 lines in one real rollout, 110 lines in the author's pi history), and a reader that gave up at the first one would show nothing.

*Turn phase, and state from a transcript.* An agent with no hook or extension has no way to tell Calm it is working: Codex sends a desktop notification only for a finished turn or an ask, and only while its terminal is unfocused, and OpenCode's are off by default. Their transcripts say it, so a reader may set `TranscriptTail.turn` (`inProgress`, `finished`, `failed`; nil when unknown or interrupted), and `SessionManager.transcriptChanged` turns it into a report through `TranscriptTail.stateChange` (tested as a table): a turn in progress moves an idle, done or failed session to *working*, and a turn that ended moves *working* or *needs you* to *done* (or *failed*). Three limits keep it a guess and not a claim: it has terminal rank, so an agent's own hook report outranks it (Claude Code and pi never reach it); it never overrides a pending *needs you*, since an ask is made mid-turn; and a reading written before the latest report is stale and ignored, as for an interruption (the finished turn's own desktop notification may arrive first). A run that ends mid-turn still settles *working* to idle when the agent exits.

- **Claude Code.** The process's `~/.claude/sessions/<pid>.json` → `sessionId` finds the file. Title: `custom-title` over `ai-title`. Recap: the latest assistant text. Interruption: the newest conversation record is a `[Request interrupted…` user record. Folder (`TranscriptTail.directory`): the newest record's `cwd` (every `user`, `assistant`, `attachment` and `system` record has one); it changes when Claude enters or leaves a git worktree, which `~/.claude/sessions/<pid>.json` doesn't show. Todos: `~/.claude/tasks/<sessionId>/*.json` (done of total, and the in-progress task's `activeForm` as the step).
- **Codex.** Recap: `task_complete.last_agent_message`, else the newest assistant message. Turn phase (`TranscriptTail.turn`): the newest turn marker is `task_started` (in progress), `task_complete` (finished) or `turn_aborted` with `reason: "interrupted"` (an interruption, no phase). No title (Codex keeps it in a versioned SQLite file) and no step or progress (recent rollouts hold no plan records). Finding it: the rollout the process has open (only in embedded mode: with the shared daemon, the daemon holds it, not `codex`); the id in `codex resume <id>` (a resumed conversation appends to its rollout from weeks ago; `fork` starts a new one, so it isn't used); else the folder rule, counting only rollouts a person started from a terminal (`originator` `codex-tui`, and not a subagent's thread): the desktop app's sessions and subagents' threads (90 of the author's 185 rollouts) sit in the same folders and would only make a folder look ambiguous. **`source` can't tell them apart** (found 2026-09-29 when a live Codex wasn't found): under the shared daemon a terminal's own rollouts say `vscode`, as the desktop app's do, and before it they said `cli`. Of the 185: 17 terminal rollouts say `cli`, 11 say `vscode`, the app has 67, subagents 90.
- **pi.** `message` records: the newest assistant message with `stopReason: "aborted"` is an interruption (tool results after it don't hide it); the title is `session_info.name`; no todos. Finding it: the extension names it on every report; else the folder rule over `~/.pi/agent/sessions`.
- **OpenCode.** `session_v2` and `session_message` of `opencode.db`, opened read-only through `CalmSQLite` (never created or written, and a schema that isn't OpenCode 2's reads as nothing). The title is `session_v2.title` unless it is the placeholder `New session - <time>`; the recap is the newest assistant `text` block; the newest record decides the turn phase: `idle` ends a turn (`succeeded` finished, `failed` failed, `interrupted` an interruption), and a `user` or `assistant` record with no `idle` after it means the turn is still going. No todo records appear in recent use. Finding it: the only top-level, unarchived session in the process's folder updated since the process started. A `/new` inside one OpenCode makes two, so the first one is kept (a known gap).

Checked against the author's real history with opt-in tests that print counts only (`CALM_REAL_CLAUDE_TRANSCRIPT`, `CALM_REAL_CODEX_SESSIONS`, `CALM_REAL_PI_SESSIONS`, `CALM_REAL_OPENCODE_DB`): all 184 Codex rollouts, 192 pi sessions and 60 OpenCode sessions read, none unreadable, the slowest pi session in 117 ms (off the main thread). Verified end to end in headless self-tests with stand-in processes (`argv[0]` set to the agent's name) and a scratch home: detection, discovery, tail and card for Codex, pi (through `calm status --agent pi --transcript`) and OpenCode, with no model called.

**Settings → Agents (as built, M3.11–M3.12).** Each adapter declares its `configFolder` (presence means installed) and its `AgentSetup`: `automatic` (Claude Code), `notifications` (Codex), `files` (pi: `~/.pi/agent/extensions/calm.ts`, API checked against pi 0.87.1's type declarations: `agent_start` → working, `agent_settled` → done/failed/idle by the outcome `agent_before_settle` saw, `ui_prompt_start`/`end` → needs you and back; every report also names the conversation with `--agent pi --transcript <session file> --agent-session <id>` from `ctx.sessionManager`, read each time because `/new` and `/resume` change it, and a missing or throwing accessor just sends no flags; reports are spawned detached because pi awaits handlers) or `hint` (OpenCode, until `attention.notifications` is true in its `cli.json`, which OpenCode 2 migrated from `tui.json`). The row holds the setup as it stands (`AgentAdapter.currentSetup(home:)`, re-read each time Settings shows), so an agent whose own config already did the work reads as `notifications`, Connected, and the hint goes away. Files Calm writes carry a marker line; Calm refuses to overwrite, and never removes, a file without it. At each launch (`AgentIntegrations.prepare`) Calm rewrites a file it wrote earlier if this version's contents differ (`AgentSetupFiles.refresh`: only a file that carries the marker and is already there; it never adds one), so a pi extension connected before an update keeps up. Settings are written into config.toml by editing only the one line (`CalmSettings.setting`), keeping every other line and comment.

**Codex hooks (researched 2026-09-29; decided not to build them).** From the docs, the source at `rust-v0.158.0`, this machine's install, and a probe of `hooks/list` in an isolated `CODEX_HOME` (no model call). No hook was run on a real turn: that needs the author's account.

- *The shared daemon.* Since 0.157 the terminal's `codex` attaches to one machine-wide `codex app-server --managed-daemon`, and that daemon runs the hooks with its own environment, the first launcher's, kept for every later session. On this machine it carries another app's environment and no `CALM_*` variables, and a hook's `$PPID` is the daemon's. A payload has `session_id`, `transcript_path` (the rollout), `cwd` and the event, but nothing that names the terminal, so a persistent hook can only be attributed to a Calm session by folder and time, which two Codexes in one folder make ambiguous. Embedded mode (hooks in the terminal's own `codex`, with the shell's environment) is forced by `--no-daemon`, `--profile`, `-c` beyond a small allowlist and a few other flags.
- *Events (0.158).* `SessionStart` (at the first turn, not when the TUI opens), `UserPromptSubmit`, `PreToolUse`, `PermissionRequest` (only when an approval prompt is about to show: never with `approval_policy = "never"`, which is the author's), `PostToolUse`, `Stop` (`last_assistant_message`), `Interrupt`, and compaction and subagent events. There is no event for a failed turn.
- *Trust.* Every hook must be approved (in `/hooks`). Trust is a `trusted_hash` (sha256 of the hook's canonical JSON) under `[hooks.state."<file>:<event>:<group>:<index>"]` in `config.toml`; editing a hook untrusts it and inserting a group before it breaks its key; a wrong hash fails safe (the hook is skipped, with a warning). The probe reproduced all six of this machine's hashes, so Calm could pre-approve by writing the file, but the format is internal. Hooks and their trust can also be passed for one launch with `-c 'hooks={…,state={…}}'`, which touches no user file but forces embedded mode (a cold in-process server on every launch) and needs a wrapper around `codex`.
- *Where hooks live.* `~/.codex/hooks.json` (the author's already holds two other tools' hooks), `[hooks]` in `config.toml`, a project's `.codex/`, or a plugin; sources add up, and hooks.json rejects unknown top-level keys.
- *Decided 2026-09-29: option 1, nothing more.* *Correction, the same day:* the premise below was wrong about *working*. Codex's notifications never say it (a desktop notification tells a finished turn or an ask, and only while its terminal is unfocused), and Calm's log showed no state signal at all while a live Codex worked, so its card never moved. Hooks would have given *working*; Calm now reads it from the rollout instead (Transcript tails → *Turn phase*), which keeps this decision. The options were: (1) Nothing more: Codex's own notifications and Calm's transcript tails already give state, recap and interruption; hooks would add immediate *needs you* and *done*. (2) A persistent hook that calls `calm hook codex`, attributed by folder only when exactly one Calm session runs Codex there: an edit to the user's hooks file and its trust, and no answer when two share a folder. (3) A `codex` wrapper in Calm's shells passing the hooks by `-c`: exact, but slower to start and invasive. Revisit if the daemon changes.

**Agent marks (as built).** Each adapter carries its mark as data (`AgentMarkArt` in `<Agent>+Mark.swift`): SVG path data in a view box, fill colors for dark and light (or a gradient), a scale, and a motion kind (`frames`, `turnAndRest`, `pulseGrid`, `build`, `gradientTurn`). A `frames` mark also carries its agent's own animation as transparent PNGs in the CalmAgents package's `Marks` resources, with the order they show in at a frame rate; Claude Code's spinner is played this way because posing its changing shapes from the spark didn't look like it. The app draws any mark the same way: `SVGPath` reads the path data (moves, lines, curves, closes; anything else falls back to the agent's letter), `MarkMotion` poses a mark as a pure function of time (looping while working, once for finishing up), and `AgentLogo` renders it in a `TimelineView` capped at 30 frames a second that runs only while the mark moves. Idle marks are drawn in the grays of their own colors rather than through a grayscale filter. `Session.stateSince` records when a report changed the state, for "Working · 4m".

**What this means for Calm.** Terminal signals alone already cover Claude Code and Codex (M3.5), with no setup. Hooks add precision (immediate *needs you*, exact messages): Claude Code's plugin is enabled inside Calm without writing anyone's config; pi's extension is a file Calm adds to pi's config folder only when the user clicks Connect; OpenCode's own notifications are a switch the user turns on in its `cli.json`; Codex keeps its own notifications, since its hooks can't tell Calm's sessions apart while its shared daemon runs (see Codex hooks). Transcript tails give every agent a recap and an interruption without any of that.

Open questions: whether `AskUserQuestion`/`ExitPlanMode` fire `PermissionRequest` in Claude Code's interactive mode; which hook, if any, follows a rejected permission; how OpenCode v2's TUI attaches to its shared service.

Transcript formats are undocumented and change between versions. Each adapter ships fixture files from real sessions and tests against them; a parse failure degrades to "no transcript", never a crash.

## Attention

**State reporting.** Every shell Calm starts gets `CALM_SESSION_ID`, `CALM_SOCKET` and `CALM_CLI` (the bundled `calm`) in its environment. A hook reports with `"$CALM_CLI" status <state> [message]` (pi's extension), or hands its payload to `"$CALM_CLI" hook <agent>` for the adapter to read (Claude Code's plugin); either sends a `status` request over the socket. States are `working`, `needs-you`, `done`, `failed` and `idle`, with a few synonyms (`waiting`, `error`, `stop`…) so hook scripts can use their agent's words. Hooks run on every turn and in every terminal, so `status`, `notify` and `hook` are silent no-ops that exit 0 outside a Calm session or when Calm isn't running (they never launch it), and give up on the socket after 1 second (`scripts/cli-hook-check.sh` checks this). What each agent needs is under Settings → Agents above.

**Fallback signals** when no hook is installed come from libghostty's actions, translated in `Terminal` into `TerminalSignal` and read by one pure function (`TerminalSignal.outcome`), with source `terminal` so hooks still win:

| Signal | In an agent session | In a plain shell |
|---|---|---|
| OSC 9;4 progress set / indeterminate | working | working |
| progress removed | done (if it was working) | idle (if it was working) |
| progress error | failed | failed |
| OSC 9 / 777 notification | read by its words: permission, approval, allow, confirm, question → *needs you*; error, failed → failed; "waiting for (your) input" and anything else → done. Only an explicit ask can notify | passed on as a notification (at the next pause, if you're elsewhere) |
| bell | *needs you*, only if the agent was working | ignored |
| command finished (OSC 133) | ignored (the agent run ends when it exits) | done or failed, if it ran 10 s or longer |

Window titles aren't used: agents' title formats vary and change. Calm never plays the system beep for a bell (Ghostty's default is silent too).

**State machine.** Per session: `idle → working → (needsYou | done | failed) → idle` (once the user leaves it). Reports are idempotent; the latest report wins, except that terminal guesses never override a hook report from the same agent run (the run ends when the agent exits). Each session keeps its last `StatusReport` (state, message, source, time) for cards and the arrival card. Applying a report returns an effect: *notify* only for a new *needs you* in a session the user isn't looking at, *withdraw* when a session leaves *needs you*. A finished session stays *done* or *failed* while the user reads it, even the one they are looking at; it settles to idle when they leave it: selecting another session, opening a new session or split, or Calm losing focus.

**Notification scheduling.**

- Only `needsYou` in an unfocused session produces a notification (configurable).
- A **breakpoint detector** watches keystrokes and focus changes. A notification is delivered when the user has not typed for a short interval, switches focus, or after a maximum wait. It is never dropped.
- Delivered notifications are removed when the session is visited.
- As built (M3.9): `AttentionQueue` (CalmModel, unit-tested) holds one notification per session; a pause is 3 s without typing (a local key monitor, so only typing in Calm counts), any focus change (session or app), or 60 s at most. `AttentionCenter` delivers through `UNUserNotificationCenter` with no sound, one identifier per session (a newer message replaces the older; visiting removes it), and skips a notification if the user is looking at the session by then. macOS asks for permission the first time one is delivered. Clicking focuses the session. Self-tests set `CALM_NO_NOTIFICATIONS=1` and only log.
- **What a notification says** is `NotificationText` (CalmModel, unit-tested): title = state mark + `session.displayTitle`, no subtitle; body = a pick from the message. `AttentionQueue.Item` carries the state along with the message (nil for `calm notify` and a plain shell's own notification, which get no mark). It reads the message as it is: it flattens lines, splits sentences at `. ? !` followed by a space or at `。？！`, and measures width in columns (East Asian wide characters and emoji count two, limit 100). *Needs you* takes the last question; other states take sentences from the start while they fit; a single long sentence is cut at a word with "…". Headless self-tests drive it with `report_away:<state>[:<message>]` after `calm.new_session` (a session other than the focused one reports, `\n` in the message is a line break) and read `calm-selftest: notification <title> | <body>` from the log.
- **Making an agent's words plain** is `MessageText.recap` (CalmModel, unit-tested), applied where prose enters Calm, so the card, the arrival card, the sidebar tooltip and the notification all get the same text: the Claude Code `Stop` message (`ClaudeCodeAdapter.hookReport`), its transcript tail (`ClaudeCodeTranscript`), and an agent's OSC 9/777 notification body (`TerminalSignal.outcome`, which passes `asking` for a *needs you*). It drops fenced code, rules, tables and headings (a heading is only used when nothing else is left), reads `#`, list and quote marks at the start of a line, and joins list items as "a; b". Markdown that arrives already flattened (OpenCode sends its answer on one line) is split at ` ##`–` ######` marks; a flat line doesn't say where a heading ends, so its label stays glued to the first sentence. Decoration (backticks, `**bold**`, `~~strike~~`, links) is removed by a scanner that protects code spans and reads a mark as decoration only where it clearly wraps words, so globs (`**/dist`), `2*3` and `__init__` stay; single `*` and `_` are never touched. Cut at 280 columns, at a word. It must be idempotent: a `needsYou` message is read again by the notification.
  **Left alone on purpose:** the `Allow <tool>: <command>` text of a permission request, a `Notification` hook's own text, `StopFailure`'s error, a plain shell's notification, `calm notify` and `calm status` messages. They are Calm's text or quote a command, and a command must reach the screen exactly (hiding the backticks of `` echo `date` `` would hide what runs). An ask classified from an OSC body keeps its inline marks for the same reason (`asking`). User prompts (search index, resume titles) keep `HookReport.recap`, which only flattens. Found 2026-09-29: the first cut of this (single `*`/`_` emphasis, applied to everything) turned `find -name '*.py'` into `find -name '.py'` in a permission banner.

## App icon

**The icon file.** `Calm/Resources/AppIcon.icon` is an Icon Composer document, written by `scripts/app-icon.py`. It has one flat layer per part (ring, center, cursor, and the light icon's glow), each with a light and a dark color, over a light or dark gradient tile, with Liquid Glass off. XcodeGen (2.45.1 and later) adds `.icon` folders as Icon Composer files. With `ASSETCATALOG_COMPILER_APPICON_NAME = AppIcon`, Xcode compiles it (actool) into `Assets.car`, with light, dark and tinted renditions, plus an `AppIcon.icns` for places that want a plain image. To check a change, render it with Icon Composer's `ictool`, which ships inside Xcode (`…/Icon Composer.app/Contents/Executables/ictool AppIcon.icon --export-image --output-file out.png --platform macOS --rendition Default|Dark --width 512 --height 512 --scale 1`).

**Dock states.**
- **Model:** `AppIconState.summarizing` reduces the sessions' states to one. `AppIconMotion` (CalmModel, unit-tested) turns state changes into frames; it is pure, so a frame is a function of time. `AppIconFrame.places` gives each of the ring's twelve places its cell and cursor strength.
- **Drawing:** `DockIcon` (App) follows the workspace through Observation. While the icon isn't idle, it sets `NSApp.dockTile.contentView` to a `DockIconView`, which draws the frame with Core Graphics on the 1024-point grid: the tile at 100…924, a superellipse for the continuous corners, in the .icon's geometry and colors. At rest it clears the content view, so the Dock shows the real icon.
- **Cost:** it ticks at 30 frames a second only while something moves, and calls `display()` only for frames that changed. The stepped chase holds on each place for most of its beat, so most ticks change nothing.
- **Testing:** headless self-tests have no Dock; `calm.dock_icon:<folder>` writes the states as PNGs.

Known limits:
- The drawn states don't follow the user's icon style (tinted or clear).
- The drawn idle frame differs slightly from the system's rendering of the icon (the system adds its own edge light), visible only at the moment the drawing hands back.

## Search

- **Engine:** SQLite FTS5 with `bm25()` ranking, in `~/Library/Application Support/Calm/index.sqlite`.
- **Tokenizer — Decided (M4.2): `trigram`, with a `LIKE` scan for queries under three characters.** Benchmark on the author's history (2026-09-27; 13,879 messages, 4.3M characters extracted from 1.4 GB of Claude Code, Codex and pi transcripts): trigram matched plain substring search on every test query (whole words, partial words such as `persist`/`notif`, Chinese such as `终端`/`审核记录`); unicode61 missed partial words (6 of 15, 1 of 13) and most Chinese (7 of 56, 0 of 6). Trigram index 35 MB vs 18 MB, built in 0.6 s; queries ≤ 1 ms, 2-character `LIKE` ≈ 10 ms.
- **Indexed content:** user and agent messages only; tool calls, tool output and file dumps are skipped.
- **Parsers (M4.1):** `TranscriptIndexing` adapters read complete JSONL records from a byte offset (`JSONLReader` stops at the last newline, so a file being written is read again later from there). Claude Code: `user` text (string or blocks; not `isMeta`, not tag-wrapped) and `assistant` text blocks, top-level files only (not `subagents/`). Codex: `response_item` messages with role user/assistant, skipping `developer` messages, tag-wrapped context and the injected `# AGENTS.md instructions` block. pi: `message` text blocks of user/assistant (no thinking, tool calls or results). Each also gathers the session id, folder, title and first prompt. Checked against the real history: the Swift counts match the benchmark's (Codex 5,747 and pi 3,103 messages exactly).
- **Incremental indexing:** each file's byte offset, size and modification time are stored, so only new lines are parsed; a file that shrank is read again from the start. A deleted transcript is kept, marked `gone` (M4, 2026-09-29): Claude Code deletes transcripts older than `cleanupPeriodDays` (30 by default), and on the author's machine that had already removed 281 of 424 Claude Code sessions (history back to April, transcripts only to September).
- **Prompt histories:** an adapter may name a prompt log that outlives its transcripts (`promptHistoryFile`, `historyPrompt(in:)`). Claude Code's `~/.claude/history.jsonl` has `{display, pastedContents, timestamp, project, sessionId}` per prompt. It is read incrementally (offset in `sources`); prompts of sessions with no transcript row become a `history` row (`path` = `<log>#<session id>`, user prompts only, not resumable). A transcript that turns up later for that session replaces it. On the author's history: 229 sessions and 2,643 prompts recovered, 0.1 s, idle update still 8 ms.
- **Keeping the index:** since it now holds sessions that exist nowhere else, a schema change migrates (`1` → `2` adds `origin` and `gone`) instead of rebuilding; only an unknown schema starts over.
- **Snippets:** built in Swift from the best matching message (by rowid) for the results shown, starting on a word up to 28 characters before the first term, so a one-line row always shows the match. FTS5's `snippet()` counted trigram tokens and often put the match past the visible line. As built (M4.3, M4.7): instead of FSEvents, the app refreshes the index when ⌘K opens and every few minutes, because an update with nothing new takes 8 ms on the author's 502 transcripts.
- **Tables** (`SearchIndex`): `files` has a row per transcript, or per session known only from a prompt history. It holds the agent, the read offset, size and modification time, the session's id, folder, title and first prompt, when it was last active, its `origin` and whether it is `gone`. `messages` is the FTS5 table of each message's text, with its file and role. `sources` keeps the read offsets of prompt histories, and `meta` the schema version.

- **Ranking (M4.4):** per term, the best `bm25()` message in each session, normalized to 0…1 against the query's best; every term must appear somewhere in the session (not necessarily one message). Then boosts: title match +0.35, recency ×0.3 (1 today, 0.5 after a week), current project +0.2 ("slightly higher": it beats a few days, not months). Terms under three characters use `LIKE` and count as fully relevant.
- **Welcome page:** with no session open, `WelcomePage` puts one `NSHostingView` over the whole window (sidebar included) and shows `WelcomeView`, so the search and the projects live on the page the sidebar would have. Each showing gets a `WelcomeModel`: it owns a `SearchPanelModel`, the very model ⌘K uses (an empty query lists the most recent sessions; opening refreshes the index; typing queries it, debounced), the projects the user made, and the selection, kept as *what a row stands for* (a transcript path or a project id) so it survives the lists changing under it. Projects are filtered by `ProjectSearch` (CalmModel): every word must be in the name or in the folder as shown, ignoring case and accents, and the same function gives the ranges the row marks. `WelcomeContent.choose` (CalmModel, pure) picks between the lists and the three-row welcome from three facts: first launch, whether the index knows any session (`SearchPanelModel.hasHistory`, nil until it answers, when sessions are assumed to be coming so the page doesn't rearrange), and whether a project exists. ⌘K on the page calls `WelcomePage.focusSearch()` instead of opening the panel over it; opening a result is `openSearchResult`, the panel's own. The rows are the panel's (54 pt, agent mark, snippet with marked words) and the sidebar's (`AgentLogo`, `IdenticonTile` at 30 pt, `KeyCaps`), not new drawings.
- **The mark on the page:** the welcome page draws Calm's icon with `DockIconView`, the Dock's own drawing view, so the two can't drift apart. `AppIconFrame` gained two numbers for it: `arrival` (seconds since the mark began to draw itself; infinity for every other frame, so the Dock is unchanged) and `cursorLevel` (how much of the cursor shows while it breathes). `WelcomeMarkMotion` (CalmModel, pure, like `AppIconMotion`) maps time to frames: the ring's ten cells fade in one `ringStagger` after another in typing order, the center follows, the cursor appears on place 11 (the ring's last cell) and takes the last step to place 0 over a second with the ease-out the Dock uses for its settle, then `cursorLevel` follows a cosine between 1 and 0.42 (3.6 s a breath), eight breaths, then `.still`. A click runs `AppIconMotion` for one lap. The view is a `TimelineView` on a schedule that ticks 30 times a second only until the mark comes to rest, so a page left alone stops redrawing; Reduce Motion asks for one frame. `WelcomeMarkClock` (owned by the model) keeps the start and the last click, so the animation carries on if the page swaps layouts.
- **Panel (M4.6):** ⌘K opens `SearchPanelView` over the window. Opening refreshes the index (in the background) and then each keystroke only queries it, debounced by 70 ms. A result counts as open when a Calm session's agent run has the same transcript path or agent session id. Enter selects that session, or opens a new session in the result's folder (home if the folder is gone) and types the adapter's resume command into it.
- **Module (as built):** `CalmSearch` in CalmKit: `SearchIndex` (all database access on one serial queue, so the control socket can search off the main thread) and `SearchRanking`, over `CalmSQLite`, a small package-internal wrapper over the system SQLite (`import SQLite3`, no dependency) that `CalmAgents` also uses to read OpenCode's own database, read-only. The index keeps sessions whose transcripts are gone, so schema changes migrate (see Keeping the index). `CALM_INDEX_FILE` overrides its path.
- **Performance (M4.7, author's history, Debug build):** first full index 12.6 s for 502 files and 13,889 messages (mostly JSON parsing of 1.4 GB); update with nothing new 8 ms; index 30 MB; queries 0.7–14 ms. Targets: queries under 50 ms while typing, and a no-change update under 50 ms so ⌘K can refresh before every search.

## Persistence

- **Decided (M2.7): zmx** ([zmx.sh](https://zmx.sh), MIT, actively maintained), pinned in `scripts/zmx.sh` (version and SHA-256) and bundled at `Contents/Resources/bin/zmx`.
- Each session's terminal command is `/usr/bin/env -u ZMX_SESSION <zmx> attach calm-<12 hex>`: attaching creates the zmx session on first use and reattaches, with scrollback, after a relaunch. zmx starts the account's login shell.
  - `env -u ZMX_SESSION`: inside a zmx session that variable makes `attach` switch the *calling* terminal instead of starting a client, which would hijack the terminal Calm was launched from.
  - `ZMX_DIR=$TMPDIR/calm-zmx` (mode 700) keeps Calm's sessions apart from any other zmx use; names stay short because each session is a Unix socket there. `ZMX_NO_DETACH_KEY=1` leaves Ctrl-\\ to programs.
- Quitting detaches; closing a session runs `zmx kill <name> --force`. Inside zmx, libghostty's "process running?" check can't see the agent, so a close asks whenever the session has an agent run.
- **Restart** (`Restart`) is an ordinary quit plus a relaunch. Once the quit can't be cancelled (`applicationWillTerminate`, after state is saved), Calm starts a `/bin/sh` helper that waits for Calm's PID to be gone (an unreaped zombie counts as gone; it gives up after 30 s rather than start a second Calm), then runs `open <bundle path>`, retrying for 5 s in case `install.sh` is mid-swap. Two Calms never attach to the same zmx sessions or write the same state. `open` hands its own environment to the app it launches, so the helper gets Calm's environment minus the self-test drivers (`CALM_SELFTEST_*`, `CALM_SNAPSHOT*`): shells keep the same `PATH`, and a Debug or test instance keeps its `CALM_*` isolation instead of coming back on the real Calm's state. Opening by path (checked: Launch Services starts the copy at that path even while another copy with the same bundle ID runs) means a Debug build never wakes the installed Calm. Without `-n`, so a Calm the user opened in between is brought forward, not joined.
- Quit asks only when shells won't survive: zmx unavailable, or persistence turned off mid-run after zmx failed, and libghostty sees a running process.
- **Closing the session on screen selects none.** `Workspace.selectedLayout` is nil when `selectedLayoutID` is (it no longer falls back to the first layout), and `removeSession` clears it when the shown layout goes, so Calm never picks a session for the user (it used to take the newest, wherever that sat in the sidebar). The state is saved and restored like any other: a relaunch after it shows the same empty main area. `MainWindowController.showNoSession` hides every workspace view and follows no folder, and with no pane focused ⌘W and the other pane shortcuts do nothing (⌘W never falls through to closing the window). ⌃Tab from here goes to the first session (⌃⇧Tab: the last). Closing one pane of a split keeps its layout on screen, focus on the sibling; ⌘⇧T reopens the session and selects it.
- **Closing never reaches the next pane.** libghostty queues surface messages by address, and a new surface can be allocated where a freed one was. Killing zmx makes the closed pane's client exit, so its "child exited" could close the pane that replaced it, and then persistence was turned off as "failing" (found in real use: one ⌘W closed two sessions). So: close requests from libghostty run after its call returns; `teardown` drains the mailbox right after `ghostty_surface_free`; a child exit whose runtime is longer than the pane's age is ignored; and only a live pane's exit can turn persistence off. At launch, `calm-*` sessions in Calm's directory that no saved session refers to are killed.
- **Shell integration inside zmx.** libghostty injects Ghostty's shell integration only when the command it runs is a shell, and here it runs zmx. `ShellIntegration` sets the same variables Ghostty would (zsh: `ZDOTDIR` pointing at the bundled integration, keeping the user's in `GHOSTTY_ZSH_ZDOTDIR`; fish and elvish: the integration prepended to `XDG_DATA_DIRS`), and zmx hands them to the shell it starts. `shell-integration = none` in the Ghostty config turns this off. Bash and nushell need their command lines rewritten, so they rely on the process-based folder lookup.
- If zmx is missing or fails, sessions fall back to plain shells for the rest of the run (`CALM_NO_PERSISTENCE=1` forces this).
- App state (projects, sessions, layouts) lives in `~/Library/Application Support/Calm/state.json`: a versioned envelope, written atomically and debounced. A file Calm can't read, or one from a newer Calm, is moved aside as `state.unreadable-<time>.json` instead of being overwritten. The window's windowed frame is kept by AppKit's autosave, which doesn't record a window left filling the screen; `Workspace.windowFilled` does (see Window).
- The shared text size (`Workspace.fontSize`, nil at the config's `font-size`) is saved there too. libghostty sizes each surface on its own, so Calm watches `CELL_SIZE` (it fires on every font change, whatever caused it), reads the pane's size back through `ghostty_surface_inherited_config`, and moves the other panes with `set_font_size`/`reset_font_size`; they report the saved size back, which ends the loop. New panes get `set_font_size` rather than the surface config's `font_size`, because only the binding action marks the size as the user's, so a config reload keeps it. With `window-inherit-font-size = false` libghostty won't report the size, and Calm quietly stops syncing.

## Smart links and Copy Cell

- **Links:** libghostty detects URLs and paths. Calm resolves relative paths against the session's working directory, parses `:line[:column]`, and routes to the viewer or the editor (`code -g`, `cursor -g`, `zed`, `xed -l` and so on).
  - As built (M5.1): libghostty's own link regex already matches URLs, absolute, `./`, `../` and `~/` paths with their `:line:column`; its `OPEN_URL` action goes to the pane's host, which knows the session. `Link.parse` (CalmModel) keeps only known schemes as URLs (so `Package.swift:12` is a path), peels up to two trailing numbers, expands `~` and resolves relative paths against the session's folder; a missing file is tried against the project's folder too. `EditorLocator` takes `editor` from config.toml (a name or a path) or finds the first installed of VS Code, Cursor, Trae, Windsurf, Zed, Sublime Text, IntelliJ IDEA, then Xcode (last: `xed` exists wherever Xcode does), checking known install paths since a GUI app's PATH is minimal. An `.app` path (Settings → General → Choose Application…) is matched by bundle name to a known editor's tool inside it (so a copy in ~/Applications gets the line too); any other app is opened with the file through NSWorkspace, without the line. Headless self-tests log what they would open instead of opening it.
  - As built (link marks and tag): libghostty highlights links only while ⌘ is held, and its `link` setting can't be set yet (`Config.zig`: "TODO: This can't currently be set!"), so Calm finds links itself. `LinkMatcher` (CalmModel) is libghostty's own pattern (`src/config/url.zig`, adapted for ICU: bounded lookbehind, escaped `[\:`) and is tested against Ghostty's own cases. Each pane (`TerminalSurfaceView+Links`) rescans when its layer gets a new frame, at most every 0.1 s: changed rows drop their marks, and once the rows read the same 0.3 s later it matches every line and keeps the links that resolve (`LinkOpener.resolveExactly` for each of `Link.candidates`, longest first: the pattern lets a path run on across single spaces, and counts a sentence's closing `.` as part of a path, so each try is also tried without trailing `.,;:!?`; the whole text goes first, since a name may end in a dot). Rows the terminal soft-wrapped are joined first (a two-row read without a line break), since libghostty's ⌘-click matches across them. `LinkMarksView`, one per workspace above its panes, draws a small view per mark so each can fade on its own. No resting marks while `ghostty_surface_mouse_captured` (such a screen is redrawn too often); ⌘ hover and click still work there through patch 0011, and the pane drops the hovered link when its rows change (libghostty looks again only on the next pointer move or key). The tag follows `MOUSE_OVER_LINK`, which arrives while libghostty holds its renderer lock, so the pane handles it on the next turn of the main loop (reading the screen takes the same lock). The action says where the link is, not what cells it covers, so the pane matches the row under the pointer again. `LinkTag` (Window) places it from the link's cells and fetches image thumbnails with `QLThumbnailGenerator`. Resting marks can't show OSC 8 links whose label isn't a path or URL, and a link a program hard-wrapped (its own line breaks, as `bat` or an agent's TUI draw them) can't be joined.
- **Copy Cell:** read the grid text around the click with libghostty's text API, scan left and right for the nearest vertical border characters and up and down for horizontal border rows, then join the cell's lines and trim padding. Pure function over a text grid, so it is unit-tested with fixtures of real agent tables.
  - As built (M5.2): `CopyCell` and `TextGrid` in CalmModel. The grid is built with display widths (`CellWidth`: CJK, fullwidth and emoji take two cells), so columns match the terminal's. Borders include box-drawing lines and junctions, `|` and `+`; a rule is a row of rule characters with at least one dash. Tables with a rule after every row are delimited by the rules; tables with only a header rule treat each line as a row, except that a line whose first column is empty continues the row above. Wrapped lines join with a space, or without one between two wide characters.
  - The view reads the grid one row at a time (a whole-viewport read joins soft-wrapped lines and shifts the rows) and maps the click to a cell from cell (0,0)'s origin and the cell size. `ghostty_text_s.tl_px_x` is the left padding, but `tl_px_y` is row 0's text baseline, not its top (`Surface.zig`: padding + cell height − the font's baseline, which the API doesn't expose). `ghostty_surface_ime_point` gives the bottom of the cursor's cell (padding + whole cells), so the top padding is the one value a whole number of cells from it and less than a cell above the baseline (`gridOrigin`). Before this, reading `tl_px_y` as the top put a click above a row's baseline (most of the row) on the row above. ⌥-double-click copies; the right-click menu (when the program isn't capturing the mouse) offers Copy Cell, Copy and Paste; a small "Cell copied" note fades by the pointer.

## Paste

- A terminal can't carry image data, but agents attach an image from its path. So `TerminalClipboard.plainText` pastes files as their shell-escaped paths, text as text, and an image with neither (a screenshot) as the path of a PNG it saves in `$TMPDIR/calm-pasted-images`, a temporary folder so macOS clears old pastes. A drop onto a pane goes through the same function.

## Window

- **Size across launches:** `setFrameAutosaveName` saves the windowed frame, but only for frames the user sets: a window left zoomed, filled or maximized keeps the older windowed frame in the defaults (found by zooming a window headless: the saved frame stayed put), so it used to come back small. `MainWindowController.noteFill` (from `windowDidResize` and `windowDidMove`) records whether `CalmWindow.isFilled` (the frame covers `screen.visibleFrame`, within a point) in `Workspace.windowFilled`, saved with the rest of the state; it ignores full screen and miniaturized windows, whose frames say nothing about the user's choice, and it stays off until `restoreFrame` has run, so restoring isn't taken for leaving the filled state. `restoreFrame` (called from `openMainWindow`) applies AppKit's frame, then `CalmWindow.fillAsLeft`: `zoom` from that frame, which makes AppKit remember it for Zoom, and `frameBeforeFill` for Fill. Without that, a window that opened already filled had no size to go back to, and a double-click on the title strip did nothing. Full screen is kept the same way, apart from the filled state: `windowDidEnterFullScreen` and `windowDidExitFullScreen` set `Workspace.windowFullScreen` (they cover the menu, the green button and Ghostty's `toggle_fullscreen` alike), and `windowFilled` stays as it was under it, so leaving full screen goes back to the filled window. `noteFill` has to skip full screen: on a notched display its frame is a point taller than `visibleFrame`, which passes `isFilled`. After `showAndFocus`, `restoreFullScreen` calls `toggleFullScreen` on the next turn of the run loop; it worked with the app inactive too (a launch with `open -g`), so it doesn't wait for activation. Headless runs never enter full screen, so a test can't take a Space over on the user's screen; the self-test action `calm.window_state` logs the frame and whether the window is in full screen, and full screen itself was checked on screen with a copy of the app (below). Known gap: in one of six test launches that should have restored full screen, the window came back filled but not in full screen, and the next five didn't repeat it; the cause isn't known. The fallback is the filled or windowed window. The defaults key is shared by every build with the bundle id `com.jinhuang.calm`, Debug and self-test runs included; in headless runs neither a programmatic resize (`--resize`) nor a zoom wrote it, so self-tests don't overwrite the installed Calm's frame, and `windowFilled` lives in the state file, which self-tests keep apart (`CALM_STATE_FILE`). To exercise the saved frame without touching the installed Calm's defaults, run a copy of the Debug app with another `CFBundleIdentifier` (re-signed ad hoc): its `UserDefaults` are then its own.
- **Title bar double-click:** Calm's content fills the window under a transparent title bar (`fullSizeContentView`), so a double-click at the top reaches Calm's views, not the title bar, and AppKit never zooms. `CalmWindow.sendEvent` catches the second click of a double-click in the top strip (48 points, or the title bar's height if taller), skipping controls such as the traffic lights, and does what `AppleActionOnDoubleClick` says: Zoom (`performZoom`, also when unset), Minimize, nothing, or Fill. Fill has no public API, so the window takes the screen's visible frame and the next double-click restores it.
- **Session title:** `SessionTitleView` (SwiftUI, in a `SessionTitleHost` whose `hitTest` returns nil, so dragging and double-clicks still reach `CalmWindow`) is pinned over the main area at `titleStripHeight`. The host sets `safeAreaRegions = []`: under the transparent title bar its safe area would push the text onto the terminal's first row. `SidebarView` reserves the same `titleStripHeight` above its search field, so a double-click in the strip never lands on the field. It reads `Session.titleStrip(agentTitle:)` (CalmModel, unit-tested: the folder via `WorkspacePath.abbreviated`, and the card's title unless it only repeats the folder). Its leading edge follows the main area at high priority and never goes left of the zoom button's end, so with the sidebar hidden it clears the traffic lights. It hands the title (else the folder) to `window.title`, which `titleVisibility = .hidden` keeps off screen but the system still uses. `SessionTitleView` shows the session's group with the sidebar's own `GroupMark` (the host takes no clicks there, so the mark's shuffle easter egg stays in the sidebar), and after the text a `GitPill` (shared with the files column's branch) with `Session.worktreeName`: `Session.activeDirectory` (CalmModel: the running agent's `TranscriptTail.directory`, else `workingDirectory`) run through `GitRoot.worktreeName`, which counts a folder as a linked worktree only when its `.git` file points into `…/worktrees/` (a submodule's points into `modules/`). The sidebar's card asks the same property, so the two agree. Inside a `ViewThatFits` the pill variant comes first and the plain one second, so the pill drops out before the title is cut; a session with no worktree skips `ViewThatFits` and draws the text alone, so it never holds an optional child. The view also holds the ⋯ `Menu`, showing `SessionMenu` (the card's context menu uses the same view, so the two can't drift). The host reports the button's frame and answers `hitTest` only over it; elsewhere it returns nil, so the strip still drags and double-clicks. `CalmWindow.isInTitleStrip` treats a hit inside `SessionTitleHost` as not the strip, so a double-click on the button doesn't zoom. What the copy items give comes from `SessionCopy` (CalmAgents, unit-tested); the actions are `MainWindowController.sessionActions`, shared with the sidebar. Rename sets `SidebarEditing.renamingSessionID`, and the card's field loads its draft when it appears, so both entry points work; a hidden sidebar is brought back first. Headless self-tests copy to a pasteboard of their own and log Reveal instead of opening Finder.

## Arrival card

- `ArrivalCard` remembers when the user left each session (not saved; after a relaunch every session counts as unseen). Arriving shows the card only if the sidebar is hidden and the session's last activity (`lastReport.date`, else the agent's start) is newer than that (`ArrivalCard.shouldShow`, tested). Found in real use: with the sidebar showing, the card repeated the sidebar card beside it and covered the top of the agent's screen.

## Session actions

- **As built (M7):** `Session.customName` (the user's name; `displayTitle` and `title(agentTitle:)` put it first) and `Session.lastConversation`, an `AgentConversation` (agent, session id, transcript, title) kept by `endAgentRun` when the run's id or transcript was known. Both are optional in the state file, so older files load.
- Each adapter's `resumeCommand` and `forkCommand` build the agent's own command, shell-quoted (research of 2026-09-28: Claude Code `--fork-session`, Codex `codex fork`, pi `--fork`). The card menu shows an action only when its command exists.
- Resume types the command into the session's own shell; fork splits beside the session (`MainWindowController.split`) or opens a new tab in its folder and types it there. Headless self-tests log the command instead of typing it, so no test ever starts a real agent on the user's account; ⌘K's resume goes through the same guard.
- **Reopen (⌘⇧T):** `SessionManager.closeSession` pushes a `ClosedSession` (folder, name, project if the session was staying in one, `createdAt`, and the running agent's conversation) onto `ClosedSessions`, a stack of the last ten kept in memory. Scratch sessions are skipped, and so is an agent that had already exited: only what was open comes back. `Workspace.reopen` makes a new session through the same `newSession` path, then restores the name and `createdAt`; the sidebar sorts a group by `createdAt`, so the session lands where it was. `SessionManager.reopenClosedSession` picks the folder (its own, else the project's, else home); the window shows the layout and types `MainWindowController.resumeCommand(for:)` for the conversation. The menu item is validated through `TerminalMenuTarget` and greyed out while the stack is empty. Ghostty's default binding for ⌘⇧T is `undo`, which takes the key before the menu does, so `CalmDefaults` unbinds it (a user's own `keybind` still wins). Self-tests: `calm.cmd_shift_t`, and `calm.agent_run:<agent>:<id>` with `calm.confirm_sheet` to close a session with an agent in it; the fake run needs a few seconds after the session opens, since the probe's first pass over a session ends any agent it can't find.

## Files and viewer

- **As built (M5.3):** `FilesListing` reads the focused session's project folder off the main thread: `git ls-files -co --exclude-standard -z` (tracked plus untracked, ignored left out), `git status --porcelain=v1 -z -uall` for changes (repository-relative paths re-based with `git rev-parse --show-prefix`, so a project that is a repository's subfolder works), and `git branch --show-current`. Outside a repository it walks the folder breadth first (so a big first folder can't use up the 5,000-file limit before its siblings show), building paths relative to the folder as it goes, which survives symlinked folders (`/tmp` → `/private/tmp`). `GitChange.parse` and `FileNode.tree` (CalmModel, unit-tested) turn the output into the tree. `FilesColumn` owns the SwiftUI view, a width constraint between the sidebar and the terminal area (272 pt at the interface size, updated with the sidebar's in `applyAppearance`), and a 5 s refresh timer that runs only while the column is shown. Rows are tapped, not selected: a list's selection is the system accent, louder than the sidebar's highlight.
- **Changes first (2026-09-29):** line counts come from `git diff --numstat -z --relative HEAD` (staged and unstaged together, as `status` shows them; paths relative to the folder; `LineCounts.parse` keys a rename by its new path and leaves binaries out). `git diff` skips untracked files, so Calm counts their lines itself as git would (`LineCounts.lines`: a last line without a newline counts; a NUL byte in the first 8 KB means binary), bounded because it runs every 5 s: files up to 512 KB, 4 MB per read. A repository without commits has no HEAD, so git counts nothing and only untracked files are counted. `ChangedFile.list` orders the changes by path; `FileNode.rows` flattens the tree through the open folders (`FilesModel.expanded`, emptied for another folder). The tree is a `LazyVStack` of buttons, not an outline `List`, so its chevrons, gutter and row heights match the sidebar's. `ViewThatFits` drops the branch pill and a change's folder when they don't fit whole. Self-tests drive it with `files_open:<file>`, `files_expand:<folder>` and `files_state`.
- **Guarded folders are read when opened (2026-09-29).** Outside a repository the walk reads every folder it meets; in the home folder that would include Desktop, Documents and Downloads, which macOS guards, so the first look at the home folder asked for three permissions, and the read waited for the answers while the column stayed empty. `GuardedFolders` (CalmModel) names them; `FilesListing.walk` doesn't enter one below the root unless it's in `opened`, and lists it in `Result.unread` instead. `FileNode.tree(…, unread:)` shows an unread folder as an empty folder; opening it (`FilesModel.toggle`) adds it to `opened` and reads again, so the prompt comes when the user asks for that folder, and every later 5 s listing reads it. A root that is or lies inside a guarded folder is read whole: the user chose it. No probe for Full Disk Access is needed, since the folders stay visible either way. Not covered: a folder the user opened and macOS refused shows empty, with no word why (a quiet note with a link to System Settings → Privacy & Security is the place for it, if it proves confusing). iCloud Drive, removable and network volumes are guarded too but a walk doesn't reach them by itself (iCloud Drive sits in the hidden `Library`). A repository is listed through git, not walked, so none of this applies to it.
- **Layout motion:** the sidebar and the files column change width through `Motion.animateLayout`, which sets the constraints to their final values at once and then glides only the layers (position and bounds, presentation-only). The terminal is resized once, not on every frame: each resize reaches the program in the terminal (SIGWINCH), and agents redraw on each. AppKit's `animator()` constraint animation was dropped for this, and because its timer stalls outside event handling, leaving the layout half-changed. Both columns lay out their content at full width and clip it, so they never squeeze while sliding.
- **Decided (M5.4): a web view for Markdown, HTML, code and text; PDFKit for PDFs; an image view for images.** Agents write GitHub-flavored Markdown (tables, fenced code), which a native path would need a hand-written block renderer for (`AttributedString(markdown:)` doesn't render tables), plus a separate highlighter; HTML needs a web view anyway. The page (`Calm/Resources/Viewer/viewer.html`) uses markdown-it 15.0.2 (MIT) and highlight.js 11.12.0 (BSD-3-Clause), pinned with checksums in `scripts/viewer-assets.sh` and committed so builds stay offline. Raw HTML in Markdown is off. Colors come from Calm's palette (`SidebarStyle.viewerColors`), with low-saturation code tones.
- **As built (M5.5–M5.6):** `ViewableKind` picks the kind by extension (a small UTF-8 file without a known one shows as text; over 5 MB opens outside Calm). The viewer covers the terminal area, not the sidebar, and is pinned to `mainArea`'s sides by constraints (a fixed frame was left behind when the files column closed); it remembers the session it was opened over and `closeViewer(unlessOver:)` closes it when another is shown (`select` and `showSelectedLayout`). Its header has the file name and path, Open in Editor, and "esc · Back to <session>". Code gets line numbers and, for `path:line`, the line highlighted and centered. Links in a viewed file open in the browser or, for local files, through the same link opener. ⌘-clicked files open in the viewer when it can show them (`open-paths = "editor"` in config.toml prefers the editor); `calm open <file>[:line]` too.

## Themes

A theme is a small TOML file with a light and a dark variant (either may be left out; the other then serves both):

```toml
name = "Forest"

[dark]
background = "#1f2e28"
foreground = "#c8c3af"
cursor = "#…"           # optional
selection = "#…"        # optional
palette = "#…, #…, …"   # optional: the 16 ANSI colors, comma-separated
sidebar = "#…"          # optional: the sidebar's background (else derived)
accent = "#…"           # optional: the chrome accent (else Calm's amber); never a state color

[light]
…
```

- **As built (M6.1):** `CalmTheme` and `ThemeLibrary` (CalmModel, unit-tested) read the files with the same flat TOML reader as config.toml. A bad color is dropped and a variant without a background or foreground is left out, each with a logged problem; the rest of the theme still works. Built-in themes are bundled from `Calm/Resources/Themes`; user themes live in `~/.config/calm/themes/`, and one with a built-in's name replaces it. `theme = "Name"` in config.toml picks one.
- **The built-in set:** five themes (Calm, Ink, Dusk, Forest, Plum) in light and dark, written by `scripts/themes.py` from OKLCH values per theme and role, which also checks their contrast. Each is a direction of its own (a hue, a depth or both), not a tint of another: an earlier six came from one generator that changed only the background's tint, and read as one theme six times in the picker. Calm is Ink's neutral gray, hues and accent with a lifted background and softer text. Original palettes, not copied from other themes. Text is 6.4–8.3:1 against the background; the six ANSI hues stay below the text's contrast in dark and at least 4.3:1 in light; bright white stays within 1.2× the text's contrast, since agents draw emphasis in it (and Claude Code's ANSI themes their body text). A unit test holds the shipped files to these.
- **Not the theme's to change:** colors an app sends as truecolor. Claude Code's `dark` theme draws its text in pure white, about 14:1 on Calm, whatever the theme; its ANSI themes, or a custom Claude Code theme with `"text": "ansi:whiteBright"` in `~/.claude/themes/`, follow the terminal's colors.
- **How a theme reaches the terminal** (`TerminalTheme`). Ghostty ranks a theme file's colors below any color set directly in the config, wherever it's set, while `theme =` goes to the last file that sets it. So:
  - The **default** theme (Calm) is written as two Ghostty theme files and `theme = light:…,dark:…` in Calm's defaults. A theme or colors in the user's Ghostty config win, so an existing setup carries over, and Ghostty switches light and dark itself.
  - A theme **picked** in Calm is written as plain colors for the current appearance to `choices.ghostty` (with the other terminal-side choices from Calm's settings), loaded after the user's config, so it wins. When the system appearance changes, Calm rewrites it and reloads.
- **Chrome (M6.2):** the sidebar, cards, panels, files column and viewer derive their colors from the terminal's background (`SidebarStyle.derived`). When that background is a Calm theme's, the theme's sidebar color, foreground (for text), accent and red are used instead. The accent colors chrome only (`SidebarStyle.accent`); *needs you* stays Calm's amber (`SidebarStyle.attention`), since a blue or green accent read as *working* or *done*. When the user's own Ghostty colors are in effect, everything stays derived. Glass or solid and card or edge-to-edge are window options (M6.4), not part of a theme.
- **Picker (M6.3):** `ThemePickerModel` gives each theme's colors for the current appearance (background, text, sidebar, hues, cursor, accent); `AppearanceSection` draws them as chips and as `WindowPreview`, a miniature of the window with the picked layout and background. A pick saves `theme` with `CalmSettings.save` and reloads the Ghostty config. Picking Calm, the default, still writes `theme = "Calm"`, so it wins over colors in the user's Ghostty config; only the Ghostty choice removes the key. The **Ghostty** choice appears when `TerminalConfig.userColors` finds colors in the user's own config. A config only resolves `theme = light:…,dark:…` inside a surface, so the pair is read from the files (`CalmTheme.ghosttyThemePair`) and the probe loads one extra `theme =` line per appearance; colors set directly still win, as in the terminal.
- **Window options (M6.4):** `WindowStyle` owns the terminal area's insets and an `NSVisualEffectView` under everything. Glass makes the window non-opaque, shows the effect view, and sets Ghostty's `background-opacity` (0.84) in `choices.ghostty`, so it wins over the user's Ghostty config. The sidebar and files column keep 55% of their color; the viewer and panels stay solid so nothing reads through them. This avoids Ghostty's private-API window blur. Card insets the terminal area by 8 points (sliding through `Motion.animateLayout`) and rounds it (10 points, continuous corners, a faint border) on a window painted in the sidebar's color; the viewer takes the same corners. Settings → Appearance saves each option (a default removes its key) and reloads the Ghostty config only when the terminal side changes (glass, or motion, which turns the cursor shader on and off).
- **Adaptive background:** when an app paints the terminal's background (OSC 11, `COLOR_CHANGE`), the pane's override feeds `applyAppearance`. The chrome derives from the new color (the theme's tints drop, since its background is no longer on screen), and the sidebar eases into it over 0.35 s.
- **Settings screen (M6.5):** `SettingsPage` puts one `NSHostingView` over the whole window, as `WelcomePage` does, drawn in the chrome's `SidebarStyle` (restyled when the theme changes); its list is `SidebarView.width` wide and drawn like the sidebar's footer rows, a size up (`SettingsMetrics`), and a local key monitor takes esc while the page is on top. An extension of `MainWindowController` opens and closes it, hands focus back to the session, and pauses the sidebar peek meanwhile; `select` and the new-session paths close it, and a config reload refreshes its models. Each section has a small `@Observable` model (`ThemePickerModel`, `WindowOptionsModel`, `AgentsSettingsModel`, `GeneralSettingsModel`) that saves through `CalmSettings.save` (a default removes the key; comments and unknown keys stay). The controls in `SettingsComponents` (segmented, switch, buttons, menus) are drawn in SwiftUI because AppKit's only know the system accent. Ghostty's C API can't return `font-family` (a repeatable key has no C value), so `GhosttyConfigText.fontFamily` reads it from the config text; the size is the shared one (⌘+/⌘−) or the config's `font-size`. `SettingsMetrics` holds the page's sizes. Blocked notifications come from `UNUserNotificationCenter.getNotificationSettings` (never asked in self-tests; `CALM_NOTIFICATIONS_BLOCKED=1` shows the notice). The page's scroll view hides its indicators: with them, headless snapshots drew the page blank. Headless self-tests drive it with `settings`, `settings:<section>`, `set:<key>=<value>`, `pick_theme:<id>` and `report:<state>`, and log the files and System Settings pane it would open.
- **Accessibility (M6.6):** `AccessibilitySettings` reads Reduce Motion and Increase Contrast (self-tests force the latter with `--increase-contrast`) and reloads the config when either changes. With Increase Contrast, `SidebarStyle.contrasted()` strengthens the chrome, and `CalmTheme.Colors.contrasted()` (CalmModel, tested on every built-in theme) lifts each text color toward white or black until it reaches 4.5:1. Ghostty's `minimum-contrast` was tried first and dropped: it swaps short colors to white or black, which made dim text brighter than normal text.
- **Interface size:** `InterfaceScale.shared.factor` (an `@Observable`, set from `CalmSettings.interfaceSize` whenever the settings change) multiplies the chrome's sizes: `.calmFont(size:)` for type and `.scaled` for lengths (frames, paddings, spacing, corners; 0 and 1 stay, so hairlines stay hairlines). Views read it in their bodies, so a change redraws them; `applyAppearance` resizes the sidebar's width constraint and its peek. SwiftUI's Dynamic Type doesn't reach fixed-size fonts on macOS, so the chrome scales itself. The window miniatures in Settings keep their own proportions, and the session switcher's live previews keep their size.
- Self-tests leave the user's Ghostty config out unless asked (`--ghostty-config`), write Calm's generated files to their own folder (`CALM_SUPPORT_DIR`), and can force the appearance (`--appearance light|dark`, `calm.appearance:<mode>`).

## Motion in the window

- The window's content view is layer-backed, so fades and slides run on Core Animation. Without layers AppKit falls back to timer-driven animation, which never ran when started outside event handling (for example from `calm open`), leaving a new session's workspace at alpha 0. The layout fade is a presentation-only `CABasicAnimation`: the view's own alpha stays 1, so a skipped animation can't leave a session invisible. Overlays (the switcher, the peeking sidebar) are removed on a timer rather than in an animation completion handler, so one can never linger invisibly over the terminal and take clicks.
- `Motion` is the one switch: no animation when the system's Reduce Motion is on or `motion` is `reduced`/`off` in `config.toml`.
- **Session switcher:** a local event monitor sees ⌃Tab before the terminal does and consumes it (and Esc, Return and the arrows while the switcher is open), so Ghostty's own ⌃Tab binding never fires. The switcher shows only after ~160 ms of holding ⌃, like ⌘Tab. Previews are `cacheDisplay` snapshots of each session's pane, refreshed every 250 ms; panes in hidden layouts are un-occluded while the switcher is open so their previews stay live, and occluded again when it closes. It cycles in sidebar order (`SessionManager.orderedSessions`, which ⌘1…9 use too).
- **Sidebar peek:** a 6 pt sensor at the left edge (tracking area only, it never takes clicks) slides a second sidebar view in over the terminal; it slides away 350 ms after the pointer leaves it.

## Motion in the terminal

- **Padding and title strip:** Calm's defaults set `window-padding-color = extend`, so the padding takes the nearest cell's color. libghostty doesn't expose that color, so each pane watches its layer's `contents` (the IOSurface libghostty renders into), samples the middle of the top row at most every 0.1 s (`SurfaceEdgeColor`) in the frame's color space (Display P3), and compares it with the pane's body (the most common shade across 32 points on each of three rows, at 30%, 50% and 70% of the height, so a full-width band on one row can't outvote the rest): when they agree the app painted the whole pane, and when they differ the top row is only a band (Claude Code's sticky prompt) and the body is used, so the strip isn't tinted by it. The window paints the title strip with the focused pane's sample, edge to edge on a solid background. The sidebar still derives from the theme's background. Side-by-side splits share one strip, so it follows the focused pane. Left and right, the padding beside a row takes the edge cell's color only when the row's first (or last) three cells share it, or the row above or below has it at the edge (engine patch 0009): a background painted out to the edge still extends, but a lone cell doesn't. pi draws its cursor as a reverse-video space, and at column 0 of an empty prompt the padding took its color, a block twice a cell's size running to the pane's edge; the same happened over a wide character (two cells) and at the last column. Three is the widest cursor plus one; the neighbors are looked up through smooth scrolling's shift and region animations like the edge cell. The rows above and below are the second test because OpenCode paints every cell of its pane and keeps a two-cell margin: its message panels, scrollbar and prompt box begin the third cell in, so the first three cells of those rows differ, yet the column beside them is one color down the whole pane. With the run rule alone the padding fell back to the theme's color on exactly those rows, strips beside every panel, the scrollbar and the prompt (found 2026-09-29). Check with `scripts/selftest.sh padding --type "bash $PWD/scripts/fixtures/edge-cursor.sh"` (its header says which rows extend; 2026-09-29: the padding of rows 4, 6, 8 and 10 took the cursor's color before 0009 and stays plain after).
- **Cursor glide:** `Calm/Resources/Shaders/cursor_glide.glsl`, a Ghostty custom shader using the `iCurrentCursor`/`iPreviousCursor`/`iTimeCursorChange` uniforms. `CalmDefaults` writes `~/Library/Application Support/Calm/defaults.ghostty` on each launch with `custom-shader` and `custom-shader-animation = true`, and loads it **before** the user's Ghostty config, so the user's settings win. It is skipped when Reduce Motion is on. Cost: while a custom shader is active, the focused pane runs an animation loop (Ghostty's docs estimate under 10% CPU).
- **Smooth scrolling (as built, 2026-09-29):** upstream Ghostty draws only whole rows, so this comes from the engine patch `0005-smooth-scroll.patch` (see GhosttyKit source above) behind its `smooth-scroll` key, which `CalmDefaults` writes with full motion only (the same gate as the cursor glide) and only when the engine knows the key (`GhosttyRuntime.hasSmoothScroll`; an unpatched build would report it as unknown). What it does:
  - A trackpad scroll keeps its sub-row remainder and draws the viewport between rows, momentum included.
  - On the alternate screen, a scroll of a region by whole rows (DECSTBM/DECSLRM with SU/SD, or IND/RI at the margin) is drawn as motion: the region's new content starts where the old content was and eases home (τ = 45 ms, drawn every 8 ms while it moves); the rows that scrolled out slide away as ghost rows. A scroll of the same region mid-ease adds to it. This is what makes Claude Code's full-screen view smooth: as an answer streams it scrolls its transcript region by about a dozen rows every ~100 ms, which stock Ghostty draws as a jump each time.
  - A resize's leftover height (under a row) is drawn as a pixel offset, so a divider drag slides the content. At rest this leaves part of the scrollback row above the viewport showing at a pane's top.
  - Clicks, selection, mouse reports and the IME position all use the rows as drawn.
  - 0006 makes a custom shader's `iCursorVisible` 0 while the cursor is scrolled out of view or blinked off, so the glide never smears from a stale spot.
  - 0008 leaves overlays still. Claude Code, scrolled back, redraws its "Jump to bottom" hint on its region's last row after every scroll; animated with the region, the old copy slid out as a ghost row while the new one slid in, two or three hints at once. The renderer now compares the region's top and bottom rows before and after each scroll: a row with an unchanged run of cells that have a background color and text (the hint's grey box) was repainted in place, is drawn where it is, and only the rows between move. Plain text never counts, so streaming is unchanged.
  - 0010 finds scrolls a program draws without scrolling. pi's full-screen view rewrites every changed row in place, one synchronized update per streamed line or wheel step, and never scrolls, so the terminal had nothing to animate and pi moved a row at a time. On the alternate screen, when the terminal recorded no scroll, the renderer hashes each row and compares it with the previous frame: when at least half of the rows that changed, and at least three, are the old ones moved by the same number of rows, the span they cover, widened by the rows that came in and bounded by rows that stayed the same (a header, the prompt), is animated as a region scroll of it, with the same ghost rows and hit testing. A redraw that only changes rows in place (a progress display) finds no shift and doesn't move.
  - 0011 gives a link under ⌘ back to a program that has the mouse captured. Ghostty hands links to the program once it turns on mouse reporting (Claude Code's full-screen view does; so do vim and htop) and offers only shift to take them back, which is the select gesture, not the link gesture. Super can't be reported (no mouse protocol has a bit for it), so the program loses nothing: `SurfaceMouse.linksOverrideCapture` says links refresh while super or an unkept shift is held, at the two places that refresh them (pointer moves, modifier changes), and a press or release over a link isn't reported, so the click that opens the link doesn't also reach the program as a plain click. Claude Code's docs say it detects Ghostty and opens a link on a plain click, so a reported press would have opened the link a second time. Away from a link, ⌘-click reaches the program as before. Zig test: `-Dtest-filter=linksOverrideCapture`; end to end with `printf '\033[?1000h\033[?1006h'` before a URL in a self-test.
  - 0012 pins the overlay's cells, not its row. The row holds the transcript's last line too, and drawing it whole in place made that line stand still while the rows around it slid: its final text showed at once, the same line again squeezed in above it, and the last row looked stuck (2026-09-29, from a real scroll). The region now animates whole, edge rows included, and the run 0008 finds (`repaintedInPlace` returns its columns) is a hole in it, one per edge row (`Overlays`, `region_hole`). In the shaders a cell in a hole belongs to no region, so it is drawn in place with the hint drawn once; content sliding through the hole is cut off there (the text fragment stage discards it) and the hole's own cells are never drawn as content, so neither the old hint (a ghost row) nor the new one (the row sliding in) shows. The hit test skips the cells too (`RegionHole`, `RegionShifts.addHoledScroll`): a click on the hint lands on it even while the text beside it slides. A ghost of the old bottom row is made without the overlay's columns (`ghostCells`). The hole alone was not enough, and this was found only by replaying Claude Code's real bytes (2026-09-29, the day 0012 landed): the renderer often takes several scrolls in one frame (Claude Code's come about 5 ms apart under a trackpad flick), each making its ghosts from the frame before, so the second scroll's copy of the old bottom row started a row above the hole and slid down the region as a second, third or fourth hint. Zig tests: `EdgeRows`, `repaintedInPlace`, `Overlays`, `RegionShifts`.
- **Checking it:** `scripts/selftest.sh <name> --type "bash $PWD/scripts/fixtures/region-scroll.sh" --motion 5` runs a fixture that scrolls a region the way Claude Code does (its bytes, captured from 2.1.284) and logs, from the frames libghostty presents (`MotionProbe`, Debug only), how far the content moved in each. With full motion each 3-row step (102 px) shows as a dozen frames of a few pixels each, a frame every ~9 ms; with `--config 'motion = "off"'` it is one 102 px jump per step. `--motion-cells col,row,col,row` watches part of the pane. `region-scroll.sh -2 20 hint` scrolls back with a hint in a magenta box redrawn after every step, and `--motion-color ff00ff` counts the pixel rows showing it in each frame: one row's height means one hint (2026-09-29: at most 34 px in every frame, scrolling back by 2 or by 1 rows and forward by 3, with 0012 as well; before 0008, 68 px in a quarter of them). To see what the frames look like rather than count them, `CALM_SELFTEST_MOTION_FRAMES=<dir>` saves each of the first 240 as `frame-NNN.png` (it slows the sampling, so read timing from a run without it): with 0008 alone the hint's row showed its final line at once while the rows around it slid, and with 0012 it slides with them. `region-scroll.sh -2 20 hint burst` sends steps in pairs 4 ms apart, which the renderer takes in one frame, as Claude Code does; the tidy fixture without `burst` passed while the real thing showed up to four hints, so try a change against both. Against the real thing: run `claude --resume <a copied old session>` in a pty of the pane's size with `--settings '{"disableAllHooks": true}' --strict-mcp-config` (no hook reaches a running Calm, no prompt is sent), send SGR wheel events, record the output with timestamps, and replay it into a self-test (the capture holds a conversation, so it stays out of the repo). Counting grey hint boxes in the dumped frames went from up to 4 in 50 of 175 frames to at most 1 in none. `region-scroll.sh 3 20 repaint` moves the region by rewriting every row, as pi does: with 0010 every move is under a row, a frame every ~9 ms; without it, 102 px jumps. Measured cost while streaming (headless Debug app, 2026-09-29): about 7% of a core with full motion, the same as idle with the cursor glide's animation loop, which the scrolling rides on; 3% with motion off.

## Configuration

- One file: `~/.config/calm/config.toml` (`CALM_CONFIG_FILE` overrides it), read and written by the settings screen. `CalmSettings` reads the flat subset of TOML Calm needs (`key = value`, comments, `[sections]` flattened to `section.key`) and reports malformed lines instead of failing. Keys: `auto-grouping`, `motion`, `theme`, `ui-size`, `editor`, `open-paths`; `background` and `layout` under `[window]`; `notify`, `sound` and `claude-code-hooks` under `[agents]`.
- Settings are written one line at a time (`CalmSettings.save`), so comments and unknown keys stay. Choosing a default removes the key, except the theme (see Themes → Picker).
- Ghostty options load in this order, each winning over the one before: Calm's `defaults.ghostty` (keybindings, padding color, motion, the default theme), the user's Ghostty config, Calm's `choices.ghostty` (a picked theme, glass), then `~/.config/calm/terminal.ghostty` for Calm-only overrides.

## Control protocol

- Unix socket at `~/Library/Application Support/Calm/calm.sock` (mode 600; `CALM_SOCKET` overrides it). One request per connection: a line of JSON with `v` and `cmd`, answered by `{"ok":true,…}` or `{"ok":false,"error":…}`. A request from a newer `calm` (a higher `v`) is refused with a note to update Calm. The types are in `CalmControl` (`ControlProtocol.swift`).
- **One Calm per socket, and a socket that heals (as built, 2026-09-30).** A Calm that starts while another answers on the same socket quits at once, in `main.swift` before the engine, the saved state or any shell is touched (`SingleInstance`, a plain connect without a request). A second copy used to unlink the running Calm's socket and bind its own, so every hook reached the newcomer; when it quit it left a dead socket file, every hook was refused, and the sessions of the Calm still running stopped following their agents: a session that started working stayed gray, one that finished stayed *Working*. This happened when a script ran the app's binary with `--version`. The Restart helper starts the new Calm only after the old one has exited, and self-tests and Debug runs set `CALM_SOCKET` to their own path, so neither is affected. A running Calm also checks every 5 s that the path still leads to its listener (`listenAgainIfLost`): when the file is gone or is what a dead Calm left, it listens again (trace: `control socket lost; listening again`); when a live Calm owns the path, it leaves it alone. Accepted connections set `SO_NOSIGPIPE`, so a caller that hangs up before the reply (a hook that timed out) can't end Calm.
- Commands: `open` (a folder becomes a project with a new session; a file, or `file:line`, opens in the viewer or the editor), `list` (sessions with id, title, project, folder, state and agent), `status` (a state report, with the agent, its session id, its transcript and the shells still running when the hook knows them), `notify`, and `search`, which is answered off the main thread since the index has its own queue.
- `calm hook <agent>` exists only in the CLI: the adapter (`HookReporting`) turns the payload into a `status` request.
- `open` and `list` start Calm when the socket is missing (`open -g -b`) and wait up to 5 s; `status`, `notify` and `hook` never do. `calm search` reads the index itself when Calm isn't running.
- The CLI is a small separate target (module `CalmCLI`) installed into the app bundle at `Contents/Resources/bin/calm` and linkable onto `PATH`.

## Testing

- **Unit:** CalmKit's packages (`swift test`), with fixtures from real transcripts; app-hosted tests in `CalmTests` for code that needs AppKit or the engine.
- **Integration:** control socket round trips, indexer on fixture folders.
- **Self-tests** (Debug builds): `scripts/selftest.sh` launches the app, drives it through variables read in `Calm/App/SelfTest.swift` (typing, key events, `calm.<action>` hooks in `MainWindowController.performForTesting`, motion probes), saves a snapshot, the screen text and a log, and quits. `CALM_HEADLESS=1` keeps the window invisible, click-through and never key, so a run never takes the user's focus (`Headless`). Checks read the log and the snapshot; there are no reference images.
- **Isolation:** each self-test gets its own `CALM_STATE_FILE`, `CALM_SUPPORT_DIR`, `CALM_CONFIG_FILE`, `CALM_SOCKET`, `CALM_ZMX_DIR`, `CALM_INDEX_FILE` and `CALM_SEARCH_HOME`, plus `CALM_GHOSTTY_CONFIG=none`, `CALM_NO_PERSISTENCE=1` (unless `--persist`) and `CALM_NO_NOTIFICATIONS=1`, so it never touches the installed Calm's state, shells or index. `UserDefaults` are the exception: they follow the bundle id (see Window).
- Swift Testing throughout; `mise run test` runs everything.
- **Trace (as built, 2026-09-29):** `Trace` writes a timeline of what decides a session's row to the unified log (category `trace`, notice level, so it is kept): `/usr/bin/log show --last 5m --predicate 'subsystem == "com.jinhuang.calm" AND category == "trace"'` (plain `log` is a zsh builtin). Each line is `+seconds since launch`, the event, and the session's first eight hex digits (the ids in `state.json` and the zmx names). It was added to find out why a Restart is slow to show *working*: launch milestones (engine, state restored, control socket listening, probe scheduled, window open), `restore` per session (the saved state and agent), `launch pass` (how many saved runs, how long, and whether it finished before the window or the rows showed as loading) and `settle` per session (what the pass found, and what the row showed before and after), `pane` attach, `probe` (an agent started or ended in the foreground), `agent named` (a hook, or the probe finding a transcript, told which agent and transcript), `report` (source, state, and what the row showed before and after), `transcript` (which fields the tail held, and any state change it made), and `control … waited` when a request waited 100 ms or more for the main thread (a hook waits that long too; `calm hook` gives up after a second). Every report and hook is written for the first minute after launch; later only those that changed something. Only states, sources, counts and agent names, never text a user or agent wrote. `SessionProbe`'s own polls aren't traced, so a slow transcript read shows as the gap before its `transcript` line.

## Distribution

- Now: built from source. `install.sh` builds a Release Calm into `/Applications` and links `calm` into `~/.local/bin`. It swaps the app in with two renames, so a failed copy never leaves no Calm, and leaves a running Calm alone: macOS keeps the running binary's pages, and the new one starts at the next launch or Restart Calm. CI (`.github/workflows/ci.yml`, a macOS 26 runner) builds GhosttyKit (cached by the pin and the patches), then lints, builds and tests every push to `main` and every pull request.
- **Local builds are signed ad-hoc; a stable local certificate was tried and dropped (2026-09-29).** macOS keeps a privacy grant (Desktop, Documents, Downloads, Full Disk Access, …) against the app's *designated requirement*, and an ad-hoc signature's is `cdhash H"…"`, a hash of that one build, so each rebuild or `./install.sh` is a new app and gets asked again. (That is how macOS is documented to work; it wasn't observed here, since reading the TCC database needs Full Disk Access.) A self-signed certificate gives a requirement that survives rebuilds (`identifier "com.jinhuang.calm" and certificate leaf = H"…"`), but the setup cost too much trust: `codesign` refuses an untrusted identity, so trusting it takes a system password dialog; then every `codesign` run asks for the login keychain password (a build signs many binaries, and a run nobody answers fails with `errSecInternalComponent`) unless the key's partition list is set, which means typing the login password into a script. An app or its tooling that asks for a password over and over looks like malware, so Calm asks for none: the certificate, its script, and the `Config/Signing.xcconfig` hook were removed. (An xcconfig include also can't name a path under `$(HOME)`, so a per-checkout file would have needed copying into every worktree.) What keeps prompts few instead: guarded folders are read only when opened (Files and viewer, above), so macOS asks in context, about a folder the user chose.
- Later: Developer ID signing, notarization, Sparkle updates, a Homebrew cask. A Developer ID identity has a requirement that stays the same across updates, so a user's grants survive them, and it asks the user for nothing beyond macOS's own folder prompts. It is the real answer to repeated prompts for users.
