# Designs

Technical design of Calm Terminal. What the features do is in [FEATURES.md](FEATURES.md); this document covers how. Items marked **Decided** record a choice and why; what is still open is marked as an open question. Source files and type names are given so the code can be read; the code is the reference for their exact shape.

## Tech stack

| Layer | Choice |
|---|---|
| Language | Swift 6, strict concurrency checking on |
| UI | SwiftUI for chrome (sidebar, panels, settings, search); AppKit for windows and the terminal view |
| Terminal engine | libghostty, used through the GhosttyKit framework |
| Storage | JSON for app state (`state.json`); SQLite FTS5 for the search index |
| Build | XcodeGen (`project.yml`) + `mise` tasks |
| Quality | swiftformat, swiftlint, Swift Testing |
| Minimum OS | macOS 26, Apple silicon (decided in M0.1; keeps the codebase free of old-version branches) |

**GhosttyKit source:** built from upstream Ghostty (`ghostty-org/ghostty`) at the commit pinned in `scripts/ghostty.env`, with the patches in `scripts/ghostty-patches` applied, and the Zig version Ghostty requires (pinned in `mise.toml`), locally and in CI. No prebuilt binaries, and no fork as the source: the patches are reviewable files in this repository.

- `scripts/ghosttykit.sh` checks out the commit, applies the patches in name order (a patch that doesn't apply stops the build rather than building half of it), builds `GhosttyKit.xcframework` (native arm64, ReleaseFast, no i18n or Sentry) plus Ghostty's resources (themes, shell integration, terminfo), caches them per commit and patch set in `~/Library/Caches/calm/ghostty/<commit>-<patches hash>`, and copies them into `Frameworks/` (not tracked).
- **Patches (decided 2026-09-29):** smooth scrolling, taken unchanged from `thdxg/ghostty` (a Ghostty fork, MIT) rather than written here: upstream has only the first piece (RenderState overscan, ghostty-org/ghostty#14400), and the fork's patch carries fixes found by measuring rendered frames that a rewrite would have to find again. The Ghostty pin follows the fork: `GHOSTTY_COMMIT` is the upstream parent of the fork commit the patches come from (`GHOSTTY_PATCHES_FROM`), so they always apply. `scripts/ghostty-patches/README.md` says what each patch does and how to move to a newer Ghostty. Drop a patch once upstream covers it. Calm's own patches (0007 and up) sit beside the fork's, each a separate small file: 0007 makes `read_text` report a row where smooth scrolling draws it, as the fork's patch already does for the IME position, so link marks and cell hit-testing stay on their rows; 0008 keeps an overlay a program redraws inside its scrolling region (Claude Code's "Jump to bottom" hint) out of the region scroll animation, which otherwise drew it two or three times per scroll; 0009 extends the padding beside a row only when the row's first (or last) three cells share a background or the row above or below has the same color at the edge, so a program's own cursor at column 0 (pi draws one as a reverse-video cell) stays a cell instead of growing out into the padding, while a pane painted in one color with its content inset (OpenCode) still extends; 0010 animates a program that moves its content by repainting rows rather than scrolling them (pi's full-screen view), by finding the rows that moved; 0011 lets a link under ⌘ work while a program has the mouse captured (Claude Code's full-screen view, vim, htop); 0012 pins only the cells of such an overlay rather than its whole row, so the text on that row still slides with the rest; 0013 starts a surface's command at the size and text size Calm passes in, rather than at an 800×600 placeholder that a resize replaces (Persistence); 0014 adds `custom-shader-animation = cursor`, which runs a custom shader's animation loop only for a second after the cursor or the focus changes, so the cursor glide no longer redraws a still pane every 8 ms; 0015 makes 0010 move a pane painted in one color (OpenCode) whole, rather than the part between rows that only look unchanged, and leaves a scrollbar or sidebar beside it in place; 0016 draws a region scroll's frames only as its content moves another pixel, so the slow half of each ease no longer draws a frame at every refresh; 0017 keeps the renderer thread's animation timer off while the display link draws every refresh, where it only woke the thread.
- `scripts/ghostty-deps.py` prefetches Ghostty's Zig packages with curl into the project-local `zig-pkg/`, because Zig's HTTP client fails behind some local HTTP proxies.
- A Ghostty `main` commit is pinned rather than the v1.3.1 release: v1.3.1 needs Zig 0.15.2, which cannot link against the macOS 26.5 SDK. Move to the next Ghostty release once it supports Zig 0.16.
- Building needs Xcode's Metal Toolchain (`xcodebuild -downloadComponent MetalToolchain`) for Ghostty's shaders.

Rules:

- **CalmKit** has no dependency on SwiftUI, AppKit or GhosttyKit, so it is fully unit-testable (`swift test`).
- **Terminal** is the only code that touches GhosttyKit (two app-hosted tests aside).
- Each **CalmAgents** adapter is self-contained; adding an agent never changes the core.

## Data model

In CalmModel (`Workspace.swift`, `AgentRun.swift`, `SessionState.swift`):

- A `Project` is a sidebar group: a folder, a name, and a kind (`.project`, made by the user; `.directory`, made by grouping; `.scratch`).
- A `Session` is one shell. It has its folder and group, whether it stays pinned there, its `SessionState` (idle, working, needs you, done, failed) with the `StatusReport` behind it, the user's name for it, and a scratch session's hidden folder. Its id is exported to the shell as `CALM_SESSION_ID`.
- While an agent runs in the foreground, the session holds an `AgentRun`: which agent, its process, its own session id and transcript, and the latest `TranscriptTail` (title, recap, step, progress, interruption, the agent's folder). When the agent exits, its `AgentConversation` stays as `lastConversation`, so it can be resumed.

Panes and tabs are **views of sessions**: a layout tree references session IDs. Closing a pane closes its session and ends its shell (`SessionManager.closeSession`); quitting Calm detaches shells instead.

As built (M2): `Workspace` holds `projects`, `sessions` and `layouts`. A `PaneLayout` is one tab: a `SplitTree<Session.ID>` plus the focused session. Every session is one pane, so a split creates a session and `⌘T` creates a session with its own layout. Calm has **one main window**; "new window" requests from libghostty become new sessions, since the sidebar replaces windows and tabs as the way to hold many shells. Which sessions share a layout isn't fixed at creation: `Workspace.join` puts an existing session beside another in that one's layout, `takeOut` gives a pane a layout of its own, and `unsplit` does that for every pane but the focused one; none of them touches a session or its shell.

## Auto-grouping

1. The shell reports its working directory (OSC 7 through libghostty's pwd action). For panes that never send OSC 7, `SessionProbe` reads the shell's folder with `proc_pidinfo(PROC_PIDVNODEPATHINFO)` every 2 seconds: the shell's pid comes from `zmx list` for persistent sessions (looked up only when unknown) and from `ghostty_surface_foreground_pid` otherwise.
2. On change, a session that isn't pinned is refiled: the most specific project the user made that contains the folder, else the directory group keyed by the git repository's root, or by the folder itself outside a repository (made if needed). A directory group matches its key exactly; it never contains other folders, which is what let an automatic home-folder project swallow every session under `~` before (found in real use).
3. Pinned sessions stay: those started in a project (`Placement.project`, and ⌘T or splits inheriting it) and scratch sessions (`Placement.scratch`, only from ⌘⇧N). ⌘T or a split from a scratch session opens a directory session at home, so a scratch folder is never shared by accident.
4. Moves are animated in the sidebar (`matchedGeometryEffect`, so a row glides from one group to the other). Empty directory groups and an empty scratch group are removed.
5. With `auto-grouping = false` (under `[sidebar]`), the folder is still recorded but the session stays where it is.
6. At launch, `refileAll` files every unpinned session again, so a workspace saved under older rules finds its groups. State files before kinds (`isAutomatic`) load as `.directory`/`.project`; both keys are written, for older builds.
7. Scratch folders live under `~/.local/share/calm/scratch/`, named by time and never shown. Not a temporary directory, which macOS clears, and not Application Support: a working folder's path shows in the prompt and reaches every tool, and the space in "Application Support" trips tools that don't quote paths. The path is fixed, next to `~/.config/calm`, rather than read from `$XDG_DATA_HOME`, which an app opened from the Dock doesn't see. Folders made before this stay where they were: a session keeps its folder's full path, and the files column knows a scratch session by its session, not its path. The root is excluded from Time Machine; the exclusion is set on the root only, because it travels with a moved item and a folder kept as a project must be backed up. Self-tests and unit tests keep theirs under their own support folder. Closing the last session in one removes it when empty, or moves it to the Trash after asking. Keep as Project… moves the folder where the user picks; the shell stays inside it (only its path string is stale until it `cd`s).
8. No session is opened at launch: the first launch (no state file yet) shows the welcome page, and a later launch restores what was open, the welcome page if nothing was. Self-tests start with a home session unless `--welcome`. What the page holds is in Search → Welcome page.

**Project marks.** `Identicon` (CalmModel) makes a project's mark from its name: a 5×5 grid mirrored left to right, in one of eight hues spread around the wheel (a hue taken straight from the hash bunched up). The hash is FNV-1a, not Swift's `Hasher`, which is seeded per process: a mark must stay the same across launches. Clicking the mark stores a random `Project.markSeed`, mixed into the hash, so the new mark is kept. `GroupMark` and `IdenticonTile` draw it in the sidebar, the title strip and the welcome page.

**Folded groups.** `GroupSummary` (CalmModel, unit-tested) turns a group's session states into what its folded line draws: runs, most urgent first, each a mark per session up to `markLimit` (3) or one mark and the count; idle only when nothing else is going on; and a `tally` of every state for the words (VoiceOver, the header's tooltip). `GroupSummaryView` draws the runs with the cards' own `StateMark` (`compact` shrinks done's check to sit with the dots). It is `.fixedSize()` with a layout priority, so the group's name truncates before a mark is cut. The header's amber fill is keyed on `GroupSummary.needsYou`. Self-tests fold the focused session's group with `fold_group`.

## Agents

**Adapters (CalmAgents).** `AgentAdapter` says what an agent is: the names, binary prefixes and package paths its process runs under, its config folder (present means installed), how it connects to Calm (`AgentSetup`), its mark, its resume and fork commands, any variables it wants in the shells Calm starts (`shellEnvironment`: OpenCode's theme, see Themes), and a theme file Calm keeps in step with its own while the agent is connected (`themeFilePath`, `themeFile(for:mode:)`: OpenCode's and pi's `calm` theme). An agent can also adopt `HookReporting` (its hooks call `calm hook <name>`), `TranscriptReading` (find and read its transcript for cards) and `TranscriptIndexing` (search). `Agents.adapters` lists them.

**Detection (as built, M3.1).** `SessionProbe` looks at every session every 2 seconds. A persistent session's shell pid comes from `zmx list`; `proc_pidinfo(PROC_PIDTBSDINFO)` gives the terminal's foreground process group (`e_tpgid`), and when it differs from the shell's own group a job is running. Only when that job changes does Calm read its path and arguments (`sysctl KERN_PROCARGS2`) and ask the adapters. Without zmx, the pane's foreground process (`ghostty_surface_foreground_pid`) is used. Adapters in `CalmAgents` match on executable or script names, per-platform binary prefixes, and package paths for scripts run by node or bun. Agent runs saved by an earlier launch are kept and checked before the window opens (Launch, below); they used to be cleared and found again by the first probe tick.

**Launch (as built, 2026-09-29).** A Restart used to show every session as idle and light them up one by one: `restore` cleared each saved agent run (and turned *working* into idle), the first probe tick came two seconds later, and rediscovering an agent never set *working*, only its next hook did. On the 22:29 restart, of five sessions saved *working*, two came back in 0.8 s and 1.5 s and two 22 s and 64 s later (a long tool call, a long reply: no hooks meanwhile). Now the sidebar comes back as it was left:

- `restore` keeps the saved runs. `SessionProbe.settleSavedRuns`, before the control server and the window, asks `LaunchPass` (off the main thread: `zmx list`, each saved session's shell foreground job with the probe's own syscalls, `Agents.detect` for the saved kind, and the adapter's `LiveStatusReading`) and waits for it up to `LaunchPass.budget` (250 ms; the pass took 3 ms for one session in the end-to-end check, most of it the `zmx list`; each further session adds a few syscalls and one small file read, so the budget is generous, and a dozen sessions haven't been timed yet). Claude Code's adapter reads `~/.claude/sessions/<pid>.json`: `status` (`busy` and `idle` seen on disk, `waiting` in the 2.1.283 binary), `statusUpdatedAt` (ms) and `waitingFor`; the file must name the pid it is read for. Nothing else keeps such a file yet, so other agents settle by the last rule below; Codex and OpenCode then correct themselves at the first regular tick, from their transcripts (`TranscriptTail.stateChange`: a turn that started and hasn't ended is working).
- `Workspace.settleSavedRun` (CalmModel, tested) decides per session from what the pass found: the run is kept only if the same agent still has the shell's foreground as the same process (or the run's process was not yet known); otherwise it ends, as an exit does. Where the agent's status speaks after the last report (within a second), it corrects the state: *working* while it says idle; idle, done or failed while it says busy (its `statusUpdatedAt` becomes the state's start). *Needs you* and `waiting` are left to hooks until each agent's wording has been seen. With no status to ask, a saved *working* stands only if `state.json` was written under 30 s ago (a Restart); older, it is idle, as any launch made it. The pass also seeds the probe's shell list and foreground jobs, so its first tick neither asks zmx again nor takes a confirmed agent for a new one.
- **A shell that went with its agent (2026-10-07).** After a reboot every saved run settled as gone, so the rows came back as plain shells and the user started their six agents again by hand and closed the seven dead sessions. The pass now also says whether zmx listed the shells (`Answer.shellsListed`: `zmx list` exited 0; a dead session lists with `err=ConnectionRefused` and no pid, so it is never taken for a live one), and a run whose agent is gone *because its shell is* gets `Session.resumesWhenOpened` (saved, nil otherwise), provided the run's own conversation was known. `SessionManager.pane(for:)` takes the mark as it makes the session's first pane and types the adapter's resume command (`type(_:into:)`, logged instead in headless self-tests); the menu's Resume takes it first, so the command is never typed twice. A failed or late listing marks nothing: typing `claude --resume` into a shell where Claude Code still runs would land in its prompt.
- If the pass isn't done within the budget, `SessionManager.confirming` names the rows and they show as loading (UIUX.md → Session states → Restoring). The answer is applied, with the state, when it comes, held for at least 450 ms after the loading began so a quick answer never flashes it; a pass that has not answered within 2 s (`LaunchPass.deadline`) is given up on, and every saved run ends as it used to. Quitting while rows load loses nothing: the saved state is only changed when the answer is applied.
- The transcript tail is saved with the run, so the first frame has its title, recap and todos; the first regular tick reads the transcripts again, off the main thread, and a tail that hasn't changed changes nothing.
- Checked end to end with a stand-in `claude` process and a status file of its own (`scripts/selftest.sh --persist --state`, launched over and over on one state file): kept, corrected either way, gone, and a slow pass (`CALM_LAUNCH_PASS_DELAY_MS`, debug builds).

**Supported agents, and removing one.** Claude Code, Codex, OpenCode and pi. omp was supported until 2026-09-29 and removed (little use, and not installed to check against): its adapter, mark, resume commands and search parser are gone. Removing an agent must not cost anyone their sessions, so an agent Calm doesn't know reads as no agent wherever it was saved: `Session.init(from:)` decodes `agent` and `lastConversation` leniently (`WorkspaceStore` starts over with an empty workspace when anything fails to decode, and a test covers a saved omp run), and the search index skips rows whose agent it doesn't know. Follow the same rule for the next removal.

**Compaction (as built, 2026-10-06).** Claude Code summarizes a conversation that has filled up, on its own mid-turn or when you type `/compact`, and it takes a while: in the author's 15 compactions (13 automatic), 99 s at the median and 141 s at the longest, 968k tokens down to 13–17k on 1M context. The card used to go on saying the turn's step all that time, and a `/compact` changed nothing at all. Captured from 2.1.291 against a stand-in API (a scratch home whose hooks log their payloads, a local mock of the Messages API answering the compaction slowly, Claude Code in a pty, no model call): `/compact` sends `PreCompact` (`trigger: "manual"`), then `SessionStart` (`source: "compact"`) and `PostCompact` (`trigger`, `compact_summary`), and no `UserPromptSubmit` before or `Stop` after; one Claude begins on its own comes between the prompt's `UserPromptSubmit` and the turn's `Stop` with `trigger: "auto"`; Esc during either sends nothing at all, and the `/compact` stays in the input. So `PreCompact` → working with `CompactionReport.started`, `PostCompact` → done ("Conversation compacted.") for `manual` and working for `auto`, with `.ended`; a trigger Calm doesn't know reads as `auto`, which never ends a turn. `calm hook` passes it as `compaction` on the control request ("start:manual", "end:auto"), and `StatusReport.compaction` carries it (not saved). `Workspace.report` keeps a `Compaction` on the session (trigger, start, end, the sizes; not saved, so a restart can't bring back a "Compacting" that ended while Calm was away), and a hook report that isn't *working* while one runs ends it. The sizes come from the transcript (`ClaudeCodeTranscript`): `contextTokens`, the newest `assistant` record's usage (input, cache creation, cache read and output), which matched the compaction's own `preTokens` within 1.4% in all 14 of the author's compactions that had a reply before them; and `lastCompaction`, the newest `compact_boundary` record (`compactMetadata.preTokens`, `postTokens`), written within 10 ms of `PostCompact`. A record whose date is before the compaction began (2 s of slack, for one first heard of when it ended) is an earlier one. Esc leaves only a `user` record (a "local command" caveat), so `newestMessageAt`, the newest `user` or `assistant` record that isn't the compaction's own summary, written more than 0.5 s after the start with no record of an end means it was cancelled: a `/compact` goes back to idle, and one begun mid-turn is left to the turn's interruption. The author's real compactions wrote only bookkeeping while they ran (`queue-operation` for a prompt queued meanwhile, `pr-link`, `frame-link`), never a message. `Session.compactionBar(now:)` (CalmModel, tested) says what the card draws: `.full` while it runs, `.drained` once over with both sizes, for `CompactionBar.lingers` (5 s) after one Claude began, and for as long as a `/compact`'s *done* card stays *done*; with the end heard and nothing recorded yet it holds `.full`, and with no record at all it goes when a drained one would. `compactionBarEnds` is when it goes by itself, and the card's `.task` moves its clock on then, so nothing redraws on a timer. **Transcript tails (as built, M3.7 and M3.7b).** Claude Code, Codex, OpenCode and pi each have a `TranscriptReading` adapter: `transcript(forProcess:)` finds its transcript, `readTail` reads it (title, the latest agent text as a plain-text recap through `MessageText.recap`, the agent's own summary where it writes one, whether the newest turn was interrupted, and step and progress where the agent keeps todos), and `changeMarkers` names the files whose size or modification time show it changed (OpenCode's `-wal` too). `SessionProbe` re-reads only on a change, one background read per session at a time: a transcript can hold megabytes of tool output, so the reading never runs on the main thread. An interruption settles *working* to idle, but only if the transcript was written after the latest report, since a new prompt's hook can arrive before its transcript line.

*Where the transcript is.* What a hook or extension reported (`calm hook`, or `calm status --transcript`) wins. Otherwise the adapter finds it from the process, tried every 4 s until it works and every 20 s after (an agent's `/new` starts another transcript); a different answer is adopted, but a failed search never drops a known transcript. The adapters share `ProcessFacts` (the process's folder, start time, terminal and arguments, and the files open in it and its children, all from plain syscalls) and `TranscriptDiscovery`: the transcript the process has open, else the agent's own rule, else *the only* transcript that starts in the process's folder and was written since it started. Two candidates mean unknown and no transcript is chosen: a card that shows another conversation's recap is worse than one that shows none.

*Reading a JSONL file.* `JSONLTail` reads from the end, newest record first, a block at a time. It stops after 512 KB of records and passes over any line longer than 512 KB unparsed (up to 32 MB in all): Codex's and pi's tool results reach megabytes (13 of 140 lines in one real rollout, 110 lines in the author's pi history), and a reader that gave up at the first one would show nothing. Only the block just read can hold newlines (the rest carried is one line), so only it is searched, with `memchr`, and a long line's pieces are joined once: re-joining each block to the carry and splitting it all again made long lines quadratic, and Claude Code transcripts carry pasted screenshots as such lines. A file shaped like a real one (five 0.55–0.7 MB lines among the last 320) read in 28 ms before and 1.2 ms after, and the author's largest transcripts 2–4× faster (2026-09-30); `JSONLTailEquivalenceTests` holds the scan to the old one's records on generated files.

*Turn phase, and state from a transcript.* An agent with no hook or extension has no way to tell Calm it is working: Codex sends a desktop notification only for a finished turn or an ask, and only while its terminal is unfocused, and OpenCode's are off by default. Their transcripts say it, so a reader may set `TranscriptTail.turn` (`inProgress`, `finished`, `failed`; nil when unknown or interrupted), and `SessionManager.transcriptChanged` turns it into a report through `TranscriptTail.stateChange` (tested as a table): a turn in progress moves an idle, done or failed session to *working*, and a turn that ended moves *working* or *needs you* to *done* (or *failed*). Three limits keep it a guess and not a claim: it has terminal rank, so an agent's own hook report outranks it (Claude Code and pi never reach it); it never overrides a pending *needs you*, since an ask is made mid-turn; and a reading written before the latest report is stale and ignored, as for an interruption (the finished turn's own desktop notification may arrive first). A run that ends mid-turn still settles *working* to idle when the agent exits.

- **Claude Code.** The process's `~/.claude/sessions/<pid>.json` → `sessionId` finds the file. Title: `custom-title` over `ai-title`. Recap: the latest assistant text. Summary (`TranscriptTail.summary`): Claude's own "※ recap" of the conversation, a `system` record with `subtype: "away_summary"` whose `content` it writes about three minutes after a turn ends (median 186 s over the author's 246, versions 2.1.260 to 2.1.284), mostly ending in the hint "(disable recaps in /config)", which is dropped. It counts only while no `user` or `assistant` record is newer, so a new turn outdates it. `Session.recap` shows it on an idle card and arrival card only: a done card's latest message is the news. Interruption: the newest conversation record is a `[Request interrupted…` user record. Folder (`TranscriptTail.directory`): the newest record's `cwd` (every `user`, `assistant`, `attachment` and `system` record has one); it changes when Claude enters or leaves a git worktree, which `~/.claude/sessions/<pid>.json` doesn't show. Todos: `~/.claude/tasks/<sessionId>/*.json` (done of total, and the in-progress task's `activeForm` as the step).
- **Codex.** Recap: `task_complete.last_agent_message`, else the newest assistant message. Turn phase (`TranscriptTail.turn`): the newest turn marker is `task_started` (in progress), `task_complete` (finished) or `turn_aborted` with `reason: "interrupted"` (an interruption, no phase). No title (Codex keeps it in a versioned SQLite file) and no step or progress (recent rollouts hold no plan records). Finding it: the rollout the process has open (only in embedded mode: with the shared daemon, the daemon holds it, not `codex`); the id in `codex resume <id>` (a resumed conversation appends to its rollout from weeks ago; `fork` starts a new one, so it isn't used); else the folder rule, counting only rollouts a person started from a terminal (`originator` `codex-tui`, and not a subagent's thread): the desktop app's sessions and subagents' threads (90 of the author's 185 rollouts) sit in the same folders and would only make a folder look ambiguous. **`source` can't tell them apart** (found 2026-09-29 when a live Codex wasn't found): under the shared daemon a terminal's own rollouts say `vscode`, as the desktop app's do, and before it they said `cli`. Of the 185: 17 terminal rollouts say `cli`, 11 say `vscode`, the app has 67, subagents 90.
- **pi.** `message` records: the newest assistant message with `stopReason: "aborted"` is an interruption (tool results after it don't hide it); the title is `session_info.name`; no todos. Finding it: the extension names it on every report; else the folder rule over `~/.pi/agent/sessions`.
- **OpenCode.** `session_v2` and `session_message` of `opencode.db`, opened read-only through `CalmSQLite` (never created or written, and a schema that isn't OpenCode 2's reads as nothing). The title is `session_v2.title` unless it is the placeholder `New session - <time>`; the recap is the newest assistant `text` block; the newest record decides the turn phase: `idle` ends a turn (`succeeded` finished, `failed` failed, `interrupted` an interruption), and a `user` or `assistant` record with no `idle` after it means the turn is still going. No todo records appear in recent use. Finding it: the only top-level, unarchived session in the process's folder updated since the process started. A `/new` inside one OpenCode makes two, so without the plugin the first one is kept; the plugin names the session on every report (see OpenCode plugin).

**Codex hooks (researched 2026-09-29; decided not to build them).** From the docs, the source at `rust-v0.158.0`, this machine's install, and a probe of `hooks/list` in an isolated `CODEX_HOME` (no model call). No hook was run on a real turn: that needs the author's account.

- *The shared daemon.* Since 0.157 the terminal's `codex` attaches to one machine-wide `codex app-server --managed-daemon`, and that daemon runs the hooks with its own environment, the first launcher's, kept for every later session. On this machine it carries another app's environment and no `CALM_*` variables, and a hook's `$PPID` is the daemon's. A payload has `session_id`, `transcript_path` (the rollout), `cwd` and the event, but nothing that names the terminal, so a persistent hook can only be attributed to a Calm session by folder and time, which two Codexes in one folder make ambiguous. Embedded mode (hooks in the terminal's own `codex`, with the shell's environment) is forced by `--no-daemon`, `--profile`, `-c` beyond a small allowlist and a few other flags.
- *Events (0.158).* `SessionStart` (at the first turn, not when the TUI opens), `UserPromptSubmit`, `PreToolUse`, `PermissionRequest` (only when an approval prompt is about to show: never with `approval_policy = "never"`, which is the author's), `PostToolUse`, `Stop` (`last_assistant_message`), `Interrupt`, and compaction and subagent events. There is no event for a failed turn.
- *Trust.* Every hook must be approved (in `/hooks`). Trust is a `trusted_hash` (sha256 of the hook's canonical JSON) under `[hooks.state."<file>:<event>:<group>:<index>"]` in `config.toml`; editing a hook untrusts it and inserting a group before it breaks its key; a wrong hash fails safe (the hook is skipped, with a warning). The probe reproduced all six of this machine's hashes, so Calm could pre-approve by writing the file, but the format is internal. Hooks and their trust can also be passed for one launch with `-c 'hooks={…,state={…}}'`, which touches no user file but forces embedded mode (a cold in-process server on every launch) and needs a wrapper around `codex`.
- *Where hooks live.* `~/.codex/hooks.json` (the author's already holds two other tools' hooks), `[hooks]` in `config.toml`, a project's `.codex/`, or a plugin; sources add up, and hooks.json rejects unknown top-level keys.
- *Decided 2026-09-29: option 1, nothing more.* *Correction, the same day:* the premise below was wrong about *working*. Codex's notifications never say it (a desktop notification tells a finished turn or an ask, and only while its terminal is unfocused), and Calm's log showed no state signal at all while a live Codex worked, so its card never moved. Hooks would have given *working*; Calm now reads it from the rollout instead (Transcript tails → *Turn phase*), which keeps this decision. The options were: (1) Nothing more: Codex's own notifications and Calm's transcript tails already give state, recap and interruption; hooks would add immediate *needs you* and *done*. (2) A persistent hook that calls `calm hook codex`, attributed by folder only when exactly one Calm session runs Codex there: an edit to the user's hooks file and its trust, and no answer when two share a folder. (3) A `codex` wrapper in Calm's shells passing the hooks by `-c`: exact, but slower to start and invasive. Revisit if the daemon changes.

**Agent marks (as built).** Each adapter carries its mark as data (`AgentMarkArt` in `<Agent>+Mark.swift`): SVG path data in a view box, fill colors for dark and light (or a gradient), a scale, and a motion kind (`frames`, `turnAndRest`, `pulseGrid`, `build`, `gradientTurn`). A `frames` mark also carries its agent's own animation as transparent PNGs in the CalmAgents package's `Marks` resources, with the order they show in at a frame rate; Claude Code's spinner is played this way because posing its changing shapes from the spark didn't look like it. The app draws any mark the same way: `SVGPath` reads the path data (moves, lines, curves, closes; anything else falls back to the agent's letter), `MarkMotion` poses a mark as a pure function of time (looping while working, once for finishing up), and `AgentLogo` renders it in a `TimelineView` capped at 30 frames a second that runs only while the mark moves, and only while `WindowPresence` says the window can be seen (its occlusion state): SwiftUI kept the timelines ticking at full cost in a headless run's transparent window, which counts as occluded (a real Space switch wasn't measured). A working `.frames` mark (Claude Code's spinner) and the working line's light don't use a timeline: every tick of one had SwiftUI lay out and render the whole sidebar again, about 2% of a core per working card, and moving the mark into a hosting view of its own made it 4× worse (a nested `NSHostingView`'s frames run a layout transaction on its parent's graph; `.drawingGroup()` changed nothing). They are Core Animation layers (`MotionLayers.swift`), which play in the render server with nothing for the app to do between frames: `MarkFramesLoop` is a discrete `contents` keyframe animation of the sequence, each image drawn once onto the whole tile where the SwiftUI path draws it (`MarkFrameImages`; shrunk to its own pixel size and stretched again by the layer, it came out soft), and `ShimmerBand` is a `CAGradientLayer` whose `transform.translation.x` keyframes follow `ShimmerText.phase`, masked to the letters by SwiftUI's `.mask(Text)` around it. Both take their `timeOffset` from the wall clock, as `MarkMotion.frameIndex` and `ShimmerText.phase` do, so cards side by side agree and the settling after the work (still a timeline) carries on from the frame the loop was on; a card that becomes visible again starts them afresh. The other motions (turn, build, grid, gradient) and every settling still pose in a timeline. Measured 2026-09-30 in headless runs with three working stand-in Claude Code cards, in retired instructions (steadier than CPU time on a busy Mac): the timelines cost 311–331 M/s with the window seen (11 unseen); the layers 9–12 M/s, as plain shells (9); wakeups 142–148 a second against 20–27. Checked: the light at three places of its crossing, dark and light, against the timeline's drawing (no pixel off by more than 8); the loop's frames against SwiftUI's drawing of the same image (`MotionLayersTests`); and `calm.layer_motion` sampling the layers' presentation for 2 s (every frame within one of the wall clock's, the light within 0.1 pt). Idle marks are drawn in the grays of their own colors rather than through a grayscale filter. `Session.stateSince` records when a report changed the state. The card showed it as "Working · 4m" until 2026-09-30, when the minutes went (the time in the card's corner counts them); it is still saved, for whatever needs a state's start next.

**What this means for Calm.** Terminal signals alone already cover Claude Code and Codex (M3.5), with no setup. Hooks add precision (immediate *needs you*, exact messages): Claude Code's plugin is enabled inside Calm without writing anyone's config; pi's extension is a file Calm adds to pi's config folder only when the user clicks Connect; OpenCode's plugin, like pi's extension, is added only on Connect; Codex keeps its own notifications, since its hooks can't tell Calm's sessions apart while its shared daemon runs (see Codex hooks). **OpenCode plugin (as built, 2026-09-30).** OpenCode 2 runs the agent in one shared background service (`opencode serve --service`), whose environment is the terminal that first started it: on the author's machine it carried one Calm session's `CALM_*`, so a plugin in the service would have sent every OpenCode's reports to that one session. 2.0.19 loads a plugin folder's `tui` entry in each terminal's own TUI process instead (read in its source at `v2.0.19`: `plugin/src/host.ts` resolves `server` or `index` for the service and `tui` for the TUI, with `Bun.resolveSync`, so `tui.ts` loads and a folder with only that is never loaded by the service). `OpenCodeAdapter.pluginSource` is that `tui.ts`: it uses `context.data.on` for the TUI's events, which it hears for every session, and reports only those of the session on its own screen (`ui.router.current()`, its root through `data.session.root`): `session.execution.started`/`succeeded`/`failed`/`interrupted` of that session itself (not a subagent's) → working, done, failed (with the error), idle; `permission.asked` and `form.created` anywhere under it → needs you ("Allow <action>", or the form's title), and back to working once every ask is answered. Checked by running the plugin under Bun against a fake context (the events above, a subagent's, another terminal's, `/new`, the home page, outside Calm); not yet in a real OpenCode turn, which needs a model call. `opencode run` and `mini` have no TUI and keep the files fallback. **Send with ⌘ Return (as built, 2026-10-07).** ⌘ Return sends an agent's prompt and Return starts a new line in it, with no key intercepted by Calm: each agent rebinds its own prompt, and Calm only lets ⌘↵ through.

- *The key.* Calm's Ghostty defaults (`CalmDefaults`) bind `super+enter` to `text:\r` while the setting is off and unbind it while it's on (it is never Ghostty's full screen). Headless self-tests (`calm.cmd_return`, a program running `stty raw -echo; cat -v`): off `^M`; on, plain `^[[27;9;13~`; on, after `ESC[>1u`, `^[[13;9u`.
- *The agents* (`SendKeys`, one per adapter, applied by `SendKeysFile`). Claude Code: two blocks first in `~/.claude/keybindings.json` (or under `CLAUDE_CONFIG_DIR`): `Chat` `enter → chat:newline`, `cmd+enter → chat:queueSubmit` (`chat:submit` did nothing while a `/` or `@` menu was open; while Claude works, both queue a message the same way, see *Checked*), and `Autocomplete` `enter → autocomplete:accept` (else Return closed the menu and added a line). Codex: none. Its keymap knows only ctrl, alt and shift (0.159.0 and 0.160.1), and a `cmd-` or `super-` key in `config.toml` stops it from starting.
- *Checked* in a pty that answered as Ghostty does, against the installed agents (Claude Code 2.1.291, OpenCode 2.0.20, pi 0.99.1, Codex 0.159.0), with scratch homes and local mock model servers (2026-10-06): Return adds a line and ⌘ Return sends in both encodings; Return is unchanged in Claude Code's AskUserQuestion (its "Type something" answer too), permission prompts, `/model` and Ctrl+R; in OpenCode's question tool (its own answer too), permission prompt, pickers, palette and `/`/`@` menus; in pi's select, confirm and input dialogs, `@` menu and lists. End to end in Calm (2026-10-07, headless, `CFFIXED_USER_HOME` on a scratch home, `--agent-files`, a mock Messages API): Calm wrote its two blocks into the scratch `~/.claude/keybindings.json`, and in a real Claude Code 2.1.291 in the pane `hello`, Return, `world`, ⌘↵ sent one message, `hello\nworld`. While Claude works (2026-10-07, the author's own session in the installed Calm, read from its transcript): a ⌘↵ message is queued at once and handed to Claude as soon as the running tool call finishes (`queue-operation` `remove`, reason `absorbed_mid_turn`), within the turn, as a Return message always was. That is what Claude Code's docs say of both `chat:submit` and `chat:queueSubmit`: queued messages reach Claude after the current tool calls, and only slash and `!` commands wait for the turn to end. `queueSubmit`'s "never interrupts the turn" sets it apart from `chat:sendNow` (⌃↵), which interrupts a turn that is only writing; its one other difference from `chat:submit` is that it sends while a `/` or `@` suggestion is highlighted. No key holds a message until the turn ends. Not checked: OpenCode and pi inside Calm (only in the pty).
- *Writing the files* (`SendKeysFile`). Plain JSON only: a file with comments (pi and OpenCode accept them) or that doesn't parse is left as it is, since rewriting it would lose them. On adds Calm's bindings and nothing else; off removes exactly those (a block or value that still matches Calm's), and a file left with nothing else goes. pi and OpenCode take an action's value as a whole, so a value the user set for any of the three (two) actions keeps that agent as it is. Files are rewritten in a hand-written layout (`JSONText`: two-space indents, sorted keys, `$schema` and a block's `context` first), so a user's own formatting of these files doesn't survive a change. Applied at launch (an agent installed since gets it) and when the switch changes; self-tests and unit tests never write (`CALM_AGENT_FILES=none`). The files are the agents' own, so the change holds in every terminal: where ⌘ never arrives, ⌃X ↵ sends in Claude Code and OpenCode (their defaults) and ⌃S in pi.
- *zsh.* A shell that gets ⌘↵ unbound beeped and typed `;9;13~` (checked on zsh 5.9). Calm's zsh startup (`ShellIntegration.zshStartup`, below) binds both sequences, at the first prompt and in the emacs, viins and vicmd keymaps, to whatever Return does there. Shells that started before the update keep running without it (zmx), as do bash and fish, and plain shells (persistence off), whose integration libghostty injects itself.

Transcript formats are undocumented and change between versions. Each adapter ships fixture files from real sessions and tests against them; a parse failure degrades to "no transcript", never a crash.

## Attention

**State reporting.** Every shell Calm starts gets `CALM_SESSION_ID`, `CALM_SOCKET` and `CALM_CLI` (the bundled `calm`) in its environment. A hook reports with `"$CALM_CLI" status <state> [message]` (pi's extension), or hands its payload to `"$CALM_CLI" hook <agent>` for the adapter to read (Claude Code's plugin); either sends a `status` request over the socket. States are `working`, `needs-you`, `done`, `failed` and `idle`, with a few synonyms (`waiting`, `error`, `stop`…) so hook scripts can use their agent's words. Hooks run on every turn and in every terminal, so `status`, `notify` and `hook` are silent no-ops that exit 0 outside a Calm session or when Calm isn't running (they never launch it), and give up on the socket after 1 second (`scripts/cli-hook-check.sh` checks this); `hook` gives up on its stdin after 1 second too (Control protocol below). What each agent needs is under Settings → Agents above. Whatever an agent starts inherits those variables, so a `status` request that names an agent (`agent`) is checked against the session's foreground: `SessionProbe.foregroundAgent` reads the process holding the terminal as it is now (`Agents.detect(processID:)`), and `AgentKind.speaksForSession` drops the whole request, state included, when a *different* agent is recognised there (Claude Code's Bash tool running `pi -p` turned the row into pi's, "done" included, on 2026-09-30). With nothing recognised in the foreground the request stands, and the trace notes each dropped one (`ignored`). One agent of the same kind starting another (`claude -p` inside Claude Code) is not told apart yet.

**Fallback signals** when no hook is installed come from libghostty's actions, translated in `Terminal` into `TerminalSignal` and read by one pure function (`TerminalSignal.outcome`), with source `terminal` so hooks still win:

| Signal | In an agent session | In a plain shell |
|---|---|---|
| OSC 9;4 progress set / indeterminate | working | working |
| progress removed | done (if it was working) | idle (if it was working) |
| progress error | failed | failed |
| OSC 9 / 777 notification | read by its words: permission, approval, allow, confirm, question → *needs you*; error, failed → failed; "waiting for (your) input" and anything else → done. Only an explicit ask can notify | passed on as a notification (at the next pause, if you're elsewhere) |
| bell | *needs you*, only if the agent was working | ignored |
| command finished (OSC 133) | ignored (the agent run ends when it exits) | done or failed, if it ran 10 s or longer |

Window titles aren't used: agents' title formats vary and change. Calm never plays the system beep for a bell (Ghostty's default is silent too).

**State machine.** Per session: `idle → working → (needsYou | done | failed) → idle` (once the user leaves it). Reports are idempotent; the latest report wins, except that terminal guesses never override a hook report from the same agent run (the run ends when the agent exits). Most reports repeat themselves (Claude Code's `PreToolUse` and `PostToolUse` say *working* on every tool call and name the session and transcript again), so the manager applies each to a copy of the workspace and writes it back only when it changed (`SessionManager.changeWorkspace`): a mutating call on the observed `workspace` notifies every view that reads it even when it changes nothing, and the sidebar rendering again cost 13 to 20 million instructions a report (one card and ten, measured 2026-10-07; busy agents send 0.2 to 0.8 such reports a second). A repeat now costs under a million (`SessionManagerReportTests`). Each session keeps its last `StatusReport` (state, message, source, time) for cards and the arrival card. Applying a report returns an effect: *notify* only for a new *needs you* in a session the user isn't looking at, *withdraw* when a session leaves *needs you*. A finished session stays *done* or *failed* while the user reads it, even the one they are looking at; it settles to idle when they leave it: selecting another session, opening a new session or split, or leaving Calm for another app. Calm merely losing the front isn't leaving: Snipaste took it for a second to take a screenshot, and the done card being read went idle under it (2026-09-30). So the app that comes to the front decides (`LeavingCalm`, CalmModel, unit-tested, fed by `NSWorkspace.didActivateApplicationNotification` in `AttentionCenter`): one with a Dock icon (activation policy `.regular`) settles the session on screen; a menu-bar tool (`.accessory`: Snipaste, Maccy, Spotlight, checked on the author's Mac) is remembered with what Calm showed, and coming back to Calm forgets it, while going on to a regular app settles that session if it is still the one on screen in the same state (one that finished while the tool was in front wasn't seen). Not tested end to end: a headless run never becomes the active app.

**Notification scheduling.**

- Only `needsYou` in an unfocused session produces a notification (configurable).
- A **breakpoint detector** watches keystrokes and focus changes. A notification is delivered when the user has not typed for a short interval, switches focus, or after a maximum wait. It is never dropped.
- Delivered notifications are removed when the session is visited.
- As built (M3.9): `AttentionQueue` (CalmModel, unit-tested) holds one notification per session; a pause is 3 s without typing (a local key monitor, so only typing in Calm counts), any focus change (session or app), or 60 s at most. `AttentionCenter` delivers through `UNUserNotificationCenter` with no sound, one identifier per session (a newer message replaces the older; visiting removes it), and skips a notification if the user is looking at the session by then. macOS asks for permission the first time one is delivered. Clicking focuses the session. Self-tests set `CALM_NO_NOTIFICATIONS=1` and only log.
- **What a notification says** is `NotificationText` (CalmModel, unit-tested): title = state mark + `session.displayTitle`, no subtitle; body = a pick from the message. `AttentionQueue.Item` carries the state along with the message (nil for `calm notify` and a plain shell's own notification, which get no mark). It reads the message as it is: it flattens lines, splits sentences at `. ? !` followed by a space or at `。？！`, and measures width in columns (East Asian wide characters and emoji count two, limit 100). *Needs you* takes the last question; other states take sentences from the start while they fit; a single long sentence is cut at a word with "…". Headless self-tests drive it with `report_away:<state>[:<message>]` after `calm.new_session` (a session other than the focused one reports, `\n` in the message is a line break) and read `calm-selftest: notification <title> | <body>` from the log.
- **Making an agent's words plain** is `MessageText.recap` (CalmModel, unit-tested), applied where prose enters Calm, so the card, the arrival card, the sidebar tooltip and the notification all get the same text: the Claude Code `Stop` message (`ClaudeCodeAdapter.hookReport`), its transcript tail (`ClaudeCodeTranscript`), and an agent's OSC 9/777 notification body (`TerminalSignal.outcome`, which passes `asking` for a *needs you*). It drops fenced code, rules, tables and headings (a heading is only used when nothing else is left), reads `#`, list and quote marks at the start of a line, and joins list items as "a; b". Markdown that arrives already flattened (OpenCode sends its answer on one line) is split at ` ##`–` ######` marks; a flat line doesn't say where a heading ends, so its label stays glued to the first sentence. Decoration (backticks, `**bold**`, `~~strike~~`, links) is removed by a scanner that protects code spans and reads a mark as decoration only where it clearly wraps words, so globs (`**/dist`), `2*3` and `__init__` stay; single `*` and `_` are never touched. Cut at 280 columns, at a word. It must be idempotent: a `needsYou` message is read again by the notification.
  **Left alone on purpose:** the `Allow <tool>: <command>` text of a permission request, a `Notification` hook's own text, `StopFailure`'s error, a plain shell's notification, `calm notify` and `calm status` messages. They are Calm's text or quote a command, and a command must reach the screen exactly (hiding the backticks of `` echo `date` `` would hide what runs). An ask classified from an OSC body keeps its inline marks for the same reason (`asking`). User prompts (search index, resume titles) keep `HookReport.recap`, which only flattens. Found 2026-09-29: the first cut of this (single `*`/`_` emphasis, applied to everything) turned `find -name '*.py'` into `find -name '.py'` in a permission banner.

## App icon

**The icon file.** `Calm/Resources/AppIcon.icon` is an Icon Composer document, written by `scripts/app-icon.py`. It has one flat layer per part (ring, center, cursor, and the light icon's glow), each with a light and a dark color, over a light or dark gradient tile, with Liquid Glass off. XcodeGen (2.45.1 and later) adds `.icon` folders as Icon Composer files. With `ASSETCATALOG_COMPILER_APPICON_NAME = AppIcon`, Xcode compiles it (actool) into `Assets.car`, with light, dark and tinted renditions, plus an `AppIcon.icns` for places that want a plain image. To check a change, render it with Icon Composer's `ictool`, which ships inside Xcode (`…/Icon Composer.app/Contents/Executables/ictool AppIcon.icon --export-image --output-file out.png --platform macOS --rendition Default|Dark --width 512 --height 512 --scale 1`).

**Dock states.**
- **The dev build's icon and name:** `BuildVariant` (`Calm/App/BuildVariant.swift`) is `#if DEBUG`, and Debug is what the self-tests and `mise run run` build; `install.sh` builds Release. `scripts/app-icon.py` writes a second document, `AppIconDev.icon` (violet on a cool tile), and `project.yml` gives the Debug configuration `ASSETCATALOG_COMPILER_APPICON_NAME = AppIconDev` and `APP_DISPLAY_NAME = Calm Dev`, which Info.plist reads for `CFBundleName` and `CFBundleDisplayName`. Only the named icon is compiled, so a Release bundle holds no dev icon. `DockIconView` picks its dev palette from `BuildVariant.isDev`; keep it and `AppIconDev` together. `PRODUCT_NAME` stays Calm: the scripts and tests find the app and its process by that name. Menus, alerts and the window's fallback title take `BuildVariant.appName`, and `BuildVariantTests` checks the bundle and the Swift agree. The Debug configuration also sets `PRODUCT_BUNDLE_IDENTIFIER = com.jinhuang.calm.dev`, so macOS tells the two apart (a pinned Dock tile, `UserDefaults`, notification and privacy grants); `BuildVariantTests` checks it. The state folder and control socket are still shared (see UIUX.md → The dev build).
- **Model:** `AppIconState.summarizing` reduces the sessions' states to one. `AppIconMotion` (CalmModel, unit-tested) turns state changes into frames; it is pure, so a frame is a function of time. `AppIconFrame.places` gives each of the ring's twelve places its cell and cursor strength.
- **Drawing:** `DockIcon` (App) follows the workspace through Observation. While the icon isn't idle, it sets `NSApp.dockTile.contentView` to a `DockIconView`, which draws the frame with Core Graphics on the 1024-point grid: the tile at 100…924, a superellipse for the continuous corners, in the .icon's geometry and colors. At rest it clears the content view, so the Dock shows the real icon.
- **Cost:** it ticks only while something moves, and calls `display()` only for frames that changed: during the steady chase at the next step (`AppIconMotion.nextWholeStep`, 8 times a second), while something eases 30 times a second. The Dock takes the chase in whole steps (`AppIconMotion.frame(at:wholeSteps:)`): the cursor jumps from place to place when the eased step would have arrived, 8 frames a second instead of 16, since every frame goes to the Dock as a new picture and at Dock size the 37 ms ease between places doesn't show; the settle keeps its ease, and the welcome page's mark, drawn larger, keeps easing too. Ticking at half the rate would still have drawn 12. Nothing is drawn while nobody can see the Dock (`DockSight`, CalmModel, unit-tested): from `screensDidSleep` to `screensDidWake`, and while another user's session is in front (`sessionDidResignActive`/`sessionDidBecomeActive`), the timer stops; the next tick after draws wherever the motion is by then, since frames are a function of time. Not tested end to end: headless runs and the test host start no Dock icon, and a test can't put the user's displays to sleep. What moves is only the cells and the glow, so the tile, its shadow and its edge are drawn once per appearance, size and resolution into a `CGLayer` and stamped under each frame (the Dock's view only: the welcome page's mark redraws seldom, through a layer-backed view the test doesn't cover): 0.11 ms a frame instead of 0.58 ms, the blurred shadow being most of it (measured 2026-09-30). `DockIconViewTests` renders every state with and without the layer and holds them to the same pixels; it caught the layer being sized in points (a blurred outline on Retina) and its shadow measured in pixels where the view's is in points. The steady chase is only twelve pictures, one per place the cursor holds (`AppIconFrame.chasePlace`): each is drawn whole into a layer the first time it comes round and stamped after that, and they're let go once the icon is at rest. The Dock draws into a half-float bitmap, where a 256-pixel frame took 0.20 ms with the tile stamped and the cells drawn, and takes 0.11 ms stamped whole (a timing test in a bitmap like it, 2026-10-06); the rest of `NSDockTile.display`, about as much again in a sample of the running app, is AppKit handing the picture to the Dock, which only fewer frames would cut. The settle and the changes between states are drawn as they come. `DockIconViewTests` holds each of the twelve pictures to the pixels of drawing it whole.
- **Testing:** headless self-tests have no Dock; `calm.dock_icon:<folder>` writes the states as PNGs.

Known limits:
- The drawn states don't follow the user's icon style (tinted or clear).
- The drawn idle frame differs slightly from the system's rendering of the icon (the system adds its own edge light), visible only at the moment the drawing hands back.

## Search

- **Engine:** SQLite FTS5 with `bm25()` ranking, in `~/Library/Application Support/Calm/index.sqlite`.
- **Short terms start words (2026-09-30).** A term of one or two ASCII letters or digits matches only where a word starts (`SearchMatch`, CalmSearch): the `LIKE` scan adds `calm_word_start(text, term)`, a SQL function `SQLiteDatabase.addPredicate` registers, which runs the same Swift rule the panel marks with, so every mark is a match. Other short terms (Chinese) still match anywhere. On the author's history "d" takes 125–150 ms.
- **Tokenizer — Decided (M4.2): `trigram`, with a `LIKE` scan for queries under three characters.** Benchmark on the author's history (2026-09-27; 13,879 messages, 4.3M characters extracted from 1.4 GB of Claude Code, Codex and pi transcripts): trigram matched plain substring search on every test query (whole words, partial words such as `persist`/`notif`, Chinese such as `终端`/`审核记录`); unicode61 missed partial words (6 of 15, 1 of 13) and most Chinese (7 of 56, 0 of 6). Trigram index 35 MB vs 18 MB, built in 0.6 s; queries ≤ 1 ms, 2-character `LIKE` ≈ 10 ms.
- **Indexed content:** user and agent messages only; tool calls, tool output and file dumps are skipped.
- **Parsers (M4.1):** `TranscriptIndexing` adapters read complete JSONL records from a byte offset (`JSONLReader` stops at the last newline, so a file being written is read again later from there). Claude Code: `user` text (string or blocks; not `isMeta`, not tag-wrapped) and `assistant` text blocks, top-level files only (not `subagents/`). Codex: `response_item` messages with role user/assistant, skipping `developer` messages, tag-wrapped context and the injected `# AGENTS.md instructions` block. pi: `message` text blocks of user/assistant (no thinking, tool calls or results). Each also gathers the session id, folder, title and first prompt. Checked against the real history: the Swift counts match the benchmark's (Codex 5,747 and pi 3,103 messages exactly).
- **Incremental indexing:** each file's byte offset, size and modification time are stored, so only new lines are parsed; a file that shrank is read again from the start. A deleted transcript is kept, marked `gone` (M4, 2026-09-29): Claude Code deletes transcripts older than `cleanupPeriodDays` (30 by default), and on the author's machine that had already removed 281 of 424 Claude Code sessions (history back to April, transcripts only to September).
- **Prompt histories:** an adapter may name a prompt log that outlives its transcripts (`promptHistoryFile`, `historyPrompt(in:)`). Claude Code's `~/.claude/history.jsonl` has `{display, pastedContents, timestamp, project, sessionId}` per prompt. It is read incrementally (offset in `sources`); prompts of sessions with no transcript row become a `history` row (`path` = `<log>#<session id>`, user prompts only, not resumable). A transcript that turns up later for that session replaces it. On the author's history: 229 sessions and 2,643 prompts recovered, 0.1 s, idle update still 8 ms.
- **Agents' own databases (2026-09-30):** OpenCode 2 keeps every session in one SQLite database, not a file per session, so it has its own adapter protocol, `SessionDatabaseIndexing` (`sessionDatabase`, `indexedSessions(in:)`, `messages(ofSession:in:)`; `OpenCodeIndexing.swift`), and `SearchIndex` a pass of its own (`indexDatabase`). Each top-level session is a `files` row with `origin` 'database' and `path` `<database>#<session id>`; its `size` and `mtime` hold the session's version, its messages' count and newest `time_updated`, because OpenCode rewrites messages in place for days and `session_v2.time_updated` doesn't follow them. A changed version reads the session again whole (its messages are deleted and inserted again). The pass is skipped while the database and its `-wal` are unchanged (their sizes and times, in `sources`), and a session gone from the database stays searchable, marked `gone`, so it isn't offered for resuming. Text is taken out in SQL (`json_extract`, `json_each` over `content`), so tool output, most of the bytes, never reaches Swift; subagent sessions (`parent_id`), sessions with no text, and a fork's copied messages (written before the fork's `time_created`) are left out. On the author's database (2.0.19, 276 MB, 182 top-level sessions): 181 sessions and 2,379 messages in 0.34 s the first time, 0.1 ms with nothing new.
- **Keeping the index:** since it now holds sessions that exist nowhere else, a schema change migrates (`1` → `2` adds `origin` and `gone`) instead of rebuilding; only an unknown schema starts over.
- **Snippets:** built in Swift from the best matching message (by rowid) for the results shown, starting on a word up to 28 characters before the first term, so a one-line row always shows the match. FTS5's `snippet()` counted trigram tokens and often put the match past the visible line. As built (M4.3, M4.7): instead of FSEvents, the app refreshes the index when ⌘K opens and every few minutes, because an update with nothing new takes 8 ms on the author's 502 transcripts.
- **Tables** (`SearchIndex`): `files` has a row per transcript, per session in an agent's own database, or per session known only from a prompt history. It holds the agent, the read offset, size and modification time, the session's id, folder, title and first prompt, when it was last active, its `origin` and whether it is `gone`. `messages` is the FTS5 table of each message's text, with its file and role. `sources` keeps the read offsets of prompt histories, and `meta` the schema version.

- **Ranking (M4.4):** per term, the best `bm25()` message in each session, normalized to 0…1 against the query's best; every term must appear somewhere in the session (not necessarily one message). Then boosts: title match +0.35, recency ×0.3 (1 today, 0.5 after a week), current project +0.2 ("slightly higher": it beats a few days, not months). Terms under three characters use `LIKE` and count as fully relevant.
- **Welcome page:** with no session open, `WelcomePage` puts one `NSHostingView` over the whole window (sidebar included) and shows `WelcomeView`, so the search and the projects live on the page the sidebar would have. Each showing gets a `WelcomeModel`: it owns a `SearchPanelModel` (a flat list of results: an empty query lists the most recent sessions; opening refreshes the index; typing queries it, debounced; ⌘K itself uses `SearchModel`), the projects the user made, and the selection, kept as *what a row stands for* (a transcript path or a project id) so it survives the lists changing under it. Projects are filtered by `ProjectSearch` (CalmModel): every word must be in the name or in the folder as shown, ignoring case and accents, and the same function gives the ranges the row marks. `WelcomeContent.choose` (CalmModel, pure) picks between the lists and the three-row welcome from three facts: first launch, whether the index knows any session (`SearchPanelModel.hasHistory`, nil until it answers, when sessions are assumed to be coming so the page doesn't rearrange), and whether a project exists. ⌘K on the page calls `WelcomePage.focusSearch()` instead of opening the panel over it; opening a result is `openSearchResult`, the panel's own. The projects end with a New project… row (`Target.newProject`, in the arrow keys' walk, ↵ calls `newProject`), outside the list's scroller so it stays in view. The rows are the old flat panel's (54 pt, agent mark, snippet with marked words) and the sidebar's (`AgentLogo`, `IdenticonTile` at 30 pt, `KeyCaps`), not new drawings.
- **The mark on the page:** the welcome page draws Calm's icon with `DockIconView`, the Dock's own drawing view, so the two can't drift apart. `AppIconFrame` gained two numbers for it: `arrival` (seconds since the mark began to draw itself; infinity for every other frame, so the Dock is unchanged) and `cursorLevel` (how much of the cursor shows while it breathes). `WelcomeMarkMotion` (CalmModel, pure, like `AppIconMotion`) maps time to frames: the ring's ten cells fade in one `ringStagger` after another in typing order, the center follows, the cursor appears on place 11 (the ring's last cell) and takes the last step to place 0 over a second with the ease-out the Dock uses for its settle, then `cursorLevel` follows a cosine between 1 and 0.42 (3.6 s a breath), eight breaths, then `.still`. A click runs `AppIconMotion` for one lap. The view is a `TimelineView` on a schedule that ticks 30 times a second only until the mark comes to rest, so a page left alone stops redrawing; Reduce Motion asks for one frame. `WelcomeMarkClock` (owned by the model) keeps the start and the last click, so the animation carries on if the page swaps layouts.
- **No session chosen:** with sessions open and none selected, `NoSessionPage` puts one `NSHostingView` over the main area only (the sidebar stays) and shows `NoSessionView`; `updateNoSessionPage` shows or hides it wherever the welcome page is updated (a layout shown, the appearance). What it shows is `NoSessionContent.choose` (CalmModel, pure): the sessions `SessionCardLayout.waitsForALook` marks (needs you, then done and failed, newest report first, at most three, the rest counted, plus how many still work), or with none the lists; once the user has typed in the lists' search the lists stay, so a turn ending doesn't swap the page under their keys. The view reads `manager.workspace.sessions` and recomputes on every change, so it follows the sidebar. The lists are `WelcomeView` with `placement: .mainArea` (its own `WelcomeModel`, `firstUse` false): no hint line while the sidebar's footer is on screen (`sidebarFooterShown`: the `sidebar.footer` setting and a sidebar that isn't hidden, read in `updateNoSessionPage`, which folding the footer reaches through `applyAppearance` and hiding the sidebar through `toggleSidebar`), a smaller mark, and the mark alone when there is nothing to list. With nothing typed, `WelcomeModel.sessions` leaves out conversations running in an open session (`Session.runs`, the rule ⌘K uses to go to a session instead of resuming it), read from the manager on each draw rather than from the items, so one closed meanwhile comes back. The waiting cards take the keyboard through a focusable SwiftUI view (↑ ↓ through `Waiting.step`, ↵); ⌘K focuses the lists' field (`focusSearch`) and otherwise opens the panel. Self-tests: `calm.nosession_state`, `calm.nosession_key:down|up|enter`, and the `calm.welcome_*` actions drive its lists.
- **Panel (M4.6, grouped 2026-09-30):** ⌘K opens `SearchPanelView` over the window (`MainWindowController+Search`). Opening refreshes the index (in the background) and then each keystroke only queries it, debounced by 70 ms. A result counts as open when a Calm session's agent run has the same transcript path or agent session id. Enter selects that session, or opens a new session in the result's folder (home if the folder is gone) and types the adapter's resume command into it.
  - *Model:* `SearchModel` asks `SearchService.searchPanel` for every match (limit 5000, so each group's count is true) with `lines: true`, and with nothing typed for the 300 most recent. `SearchGrouping`, a Sendable snapshot of the projects you made, gives each result its group by the sidebar's rule (scratch folders, then the most specific made project, then `GitRoot.find` or the folder), and names groups for the index's `groupName`: a term a group's name holds counts as found in all of it. The pure parts are in CalmSearch and unit-tested: `SearchGroups.grouped` (the current group first, the rest by best match; shares of three and two; "more" adds five; never "1 more"), `SearchGroups.switcher`, `SearchGroupCounts`, `SearchResult.linesToShow` (greedy: the fewest lines that cover the words the title and group name don't show, at most three) and `SearchLineFit.parts` (context before and after each word given up in steps until the line fits, measured by `NSString.size` in the view's font at the standard size, with 5% to spare for the heavier marks). `WrittenTime` (CalmModel) writes the time out.
  - *Index:* `SearchResult.lines` carries, per result, the message behind each term's best match (deduplicated), flattened to one line and cut to its stretch around the words, 240 characters either side (`SearchQuery.excerpt`), with its role and the terms it holds. On the author's history a ⌘K query takes 6–40 ms with its lines, one letter about 150 ms.
  - *View:* a `LazyVStack` with pinned section headers on a solid surface (`LinkTag`'s: the terminal's background lifted 7% toward white in dark, 55% in light), so rows scroll under them cleanly. Row frames in the list's own coordinate space give the height that ends on a whole row. "More" keeps its row still: the model counts `moreRequest`, the view notes where the row stood before the new rows are laid out and scrolls by as much as it moved (`ScrollPosition`). A title's word counts as shown only when it fits before the time and a ↵ key, measured the same way. Self-tests: `calm.search:<text>`, `calm.search_key:down|up|tab|shift_tab|right|left|enter`, `calm.search_state` (groups, counts, rows with their lines, the selection).
- **Module (as built):** `CalmSearch` in CalmKit: `SearchIndex` (all database access on one serial queue, so the control socket can search off the main thread) and `SearchRanking`, over `CalmSQLite`, a small package-internal wrapper over the system SQLite (`import SQLite3`, no dependency) that `CalmAgents` also uses to read OpenCode's own database, read-only. A connection that fails to open is closed in `SQLiteDatabase.init` and never kept: a class's deinit runs even when its init throws, and closing it there too freed it twice (found 2026-09-30 from SQLite's "API call with invalid database connection pointer" in the log, from the unit tests and from the running Calm; the package suite crashed inside the next open about once in 10 to 20 runs). The index keeps sessions whose transcripts are gone, so schema changes migrate (see Keeping the index). `CALM_INDEX_FILE` overrides its path.
- **Performance (M4.7, author's history, Debug build):** first full index 12.6 s for 502 files and 13,889 messages (mostly JSON parsing of 1.4 GB); update with nothing new 8 ms; index 30 MB; queries 0.7–14 ms. Targets: queries under 50 ms while typing, and a no-change update under 50 ms so ⌘K can refresh before every search.

## Find

⌘F in a session (FEATURES.md → F16, UIUX.md → Find). Designed, not built; the plan is ROADMAP.md → M8.

- **Ghostty's engine does the searching** (pinned source, checked 2026-10-06): the actions `START_SEARCH` (with a needle), `END_SEARCH`, `SEARCH_TOTAL` and `SEARCH_SELECTED` reach the app; Calm handles none of them yet. The search runs on its own thread over the active screen (the normal one with its scrollback, or the alternate one of a full-screen program, which has none), compares the letters A to Z without case, and `navigate_search` goes newest to oldest and stops at the ends. Its thread sends the matches in the viewport and the selected match's position to the **renderer only** (`Surface.zig`, `search_viewport_matches`, `search_selected_match`); the app hears the total and the selected index. Its matching, read in `sliding_window.zig` (2026-10-07): bytes compared with only A to Z folded (`indexOfIgnoreCase`), a match counted at every place one starts, overlapping ones too (after a match it looks again one byte past its start, so "aa" is 3 in "aaaa", confirmed against the engine's total), soft-wrapped rows joined and each line ended with a newline, so no match crosses a line's end; `navigate_search` scrolls the viewport to the selected match when it's off screen. Its macOS defaults: ⌘F `start_search`, ⌘G / ⌘⇧G `navigate_search`, ⌘E `search_selection`, ⌘⇧F and esc `end_search`, esc as a performable binding, which takes the key whenever a search is active.
- **Keys (built, M8.1):** Ghostty's own bindings stay: while a pane has the keyboard ⌘F (`start_search`), ⌘G / ⌘⇧G (`navigate_search`) and ⌘E (`search_selection`) reach it as terminal bindings, and while find's field has it the Edit menu's Find items run the same binding actions on the focused pane, so the user's own Ghostty keybindings for search keep working. `start_search` only tells the app to show its field; the words go to the engine as `search:<words>` (everything after the colon, colons included; empty stops it). `FindModel` (one per window) turns the four actions into the field's state: a second `start_search` on the searched pane closes it, one with words (⌘E) replaces them, the first total of a new search sends `navigate_search:next` so the count reads "1 of N" at the newest match (the engine's index 0, checked against the screen), and each pane's last words come back when ⌘F opens there again. The four actions reach the window a turn of the run loop later (`TerminalEngine`), so its answers aren't binding actions run inside libghostty's own call. Calm's defaults unbind `escape=end_search`, so esc in the terminal always reaches the program, and the field takes esc itself (`onExitCommand`). `TerminalSurfaceView.keyDown` reports every key without ⌘ (`surfaceDidType`), which closes find before the key goes on; the keyboard moving to another pane, going to another session, or the searched session closing closes it too. In the strip the readout steps away while find is open, and `SessionTitleView.findFieldWidth` sizes the field from the row's width and the title's whole width (measured hidden), so it narrows to 240 pt before the title gives way, and only the title changes between `ViewThatFits` children: the field is never rebuilt and never loses the keyboard. The viewer and Settings cover the strip, so find doesn't open over them yet (M8.7).
- **Where the current match is (decided 2026-10-07, M8.2): Calm's own matching, no engine patch.** A patch forwarding `search_selected_match`'s position would need the terminal's lock in a callback that runs without it, and the map needs Calm's own search of the scrollback anyway. So the pane finds the matches on screen itself (`FindMatcher`, pure and unit-tested: the engine's folding and overlaps, over `viewportRows()` grouped into lines through soft wraps as the link marks are, wide characters as two cells), and the engine's selected index, which counts from the newest match, picks one of them: the current match is the screen's matches counted backwards from the newest row. At the bottom of the scrollback that's the screen's own; scrolled up, the text from the screen's top to the newest row is read once (`GHOSTTY_POINT_SCREEN`'s bottom right) and counted, again only when the words or the position change. The position comes from `GHOSTTY_ACTION_SCROLLBAR` (total rows, offset, visible rows), now handled (`ScrollbackPosition`).
- **Marks (built, M8.3):** Ghostty paints a match only as a cell fill, which read as a selection, so Calm's defaults set its `search-background` and `search-foreground` to `cell-background` and `cell-foreground` (invisible; a search color in the user's config still wins), and `FindMarksView` draws the underlines, the band and the edge bar as Core Animation layers over the panes, beside `LinkMarksView`. The pill stays Ghostty's: every Calm theme's Ghostty lines (`CalmTheme.ghosttyLines`) set `search-selected-background` to the solid accent and `search-selected-foreground` to the background, so the text is recolored where it's drawn; for the user's own Ghostty colors Calm's defaults carry the same two lines from palette color 4 (`TerminalTheme.userFindPillLines`; a change of appearance reloads the config, since they're one appearance's). It is the engine's cell fill, so its ends are square and flush with the letters' cells, not the design's rounded pill 2 pt past them. A terminal color has no C value (`c_get.zig` reads only types with `cval`), so the overlay can't read the pill's color back: it works it out as the lines were written, from the theme matching the background or from palette color 4. The pane refreshes its marks 0.05 s after a frame (not on every frame of fast output), and only when the screen's rows, the current match, the grid's position or the background changed. The underline sits under the text's baseline, which libghostty gives with a selection's position (`tl_px_y`). That position is missing for viewport row 0 while the screen is scrolled up into the scrollback (libghostty reports -1: it counts that row as off screen), which put every mark, and the link marks and ⌥-click's cell, a row off there; `gridGeometry` now reads row 1 and steps back a row. Each set of marks steps aside for the other: the link dots lose the cells find marks, and find's underline loses the cells of a link under ⌘.
- **The map needs every match's row**, which Ghostty doesn't expose, so Calm reads the scrollback itself: `ghostty_surface_read_text` with a `GHOSTTY_POINT_SCREEN` selection returns all of it in one call. Measured 2026-10-07 in a headless self-test (a made-up 109-column log, Debug app on GhosttyKit's release build, a busy machine): 10,007 lines (1.1 MB) read in about 6 ms; 44,184 lines (5 MB, all that Ghostty's default `scrollback-limit-bytes` of 50 MB kept of 50,000) in about 24 ms. Finding the words and each one's line in one pass over the bytes took 2.0 and 8.6 ms compiled with `-O` (the Debug build's 61 and 270 ms are unoptimized Swift). So a full search is under a frame or two at the worst, but the read holds the terminal's lock for that long: search everything when find opens or the words change (after a short pause in typing), only the new lines while output arrives, and scan off the main thread. The read joins soft-wrapped lines (10,007 lines filled about 12,000 rows), so a tick's row counts each line's wraps; the box comes from `GHOSTTY_ACTION_SCROLLBAR` (total rows, offset, visible rows). Ghostty's total stays the count shown, so Calm's search must agree with it: the same case folding, and a match across a soft wrap found once.
- **The map as built (M8.4, 2026-10-07):** `FindMap.scan` (CalmModel, unit-tested) makes one pass over the scrollback's bytes: per line, its matches (the engine's folding and overlaps), its row (its width over the columns, the width being its byte count unless it has more than ASCII, then its characters' cells) and its number and text for the tag. The pane reads the whole scrollback on the main thread (`TerminalSurfaceView+FindMap`) and scans it in a detached task; a scan the words have moved past is dropped. It scans 0.15 s after the words change, and while output arrives at most once a second, whole: not "only the new lines" as planned, since rows can also leave the top of a full scrollback and a cleared screen starts over, and a whole scan is a read plus a pass (about 33 ms at the worst measured, 5 MB; most logs are far smaller). The engine's index picks the current line from the lines' match counts, newest first, wherever it is; a click steps there with `navigate_search` as many times as it takes, and the engine scrolls the match into view. `FindMapView` is one view per workspace, for the pane being searched, over everything on the panes (it takes the pointer); the ticks, track and box are drawn, the current tick is a layer of its own so it can slide (M8.6), and the tag is AppKit on the ⌘-link tag's surface. It shows only while `showsFindMap`: words, lines with matches, and a scrollback taller than the screen, which a full-screen program's never is.
- **Full-screen programs (built, M8.5):** the scroll bar reads the same for the alternate screen and for a normal one with little output, so engine patch 0018 adds `ghostty_surface_alternate_screen`. The pane asks it each time it looks at its matches and reports a change to find (`FindEvent.fullScreen`), which then counts "on screen" and shows its note when nothing there matches; the window fills in the running agent's name for it (`Session.agent`). The note (`FindNote`) is its own view over the terminal, under the field's right end, placed from the field's frame in the strip, since the strip's host clips what's drawn past it; its button closes find and opens ⌘K with the words.
- **Colors** follow from the theme's background, text and accent (the five themes were checked with a script, 2026-10-07; `FindColors`, with `FindColorsTests` running the same checks on the built-in themes: the band is the script's exact color, the solid within 3/255 of it, a lone tick 3:1 on its track in light themes): the pill and underline use the accent, moved in OKLab lightness in light themes until background-colored text reads at 4.5:1 on it; the band is the background with lightness +0.03 and chroma 0.016 toward the accent's hue in dark themes (−0.03 and 0.008 in light); a lone tick is the accent over the track at 60% in dark themes, or as strong as 3:1 needs in light (80–85%). A theme without an accent (the user's Ghostty colors) uses palette color 4. The band lies over the text (the terminal paints its own background), so it's a layer of a stronger tint at the least opacity that still makes the band over the background (`FindColors.bandLayer`, under 12% on every theme), and the text on the line keeps nearly all its contrast.
- **The viewer** (Files and viewer, below): Calm's own page (`viewer.html`, Markdown, code and text) gets a find function that marks and counts in the page; PDFs use PDFKit's `findString`, its highlight for the current match and, a guess not yet tried, temporary underline annotations for the rest; HTML and SVG files use `WKWebView.find(_:configuration:)`, with no count. The viewer's esc monitor lets find's esc go first.
- **At rest** find costs nothing: no timer runs while the field sits open; the map refreshes only when output arrives, and the slides are Core Animation, as in Motion in the window. As built (M8.6): each frame the pane draws reads the grid's position (`followFindGrid`, one cell's `read_text`) so the marks ride a smooth scroll, and moves the marks only if it moved; the rows are read 0.05 s after a frame, or at once when the screen scrolled. A step slides only when the screen held still (`PaneFind.slides`). Closing fades each pane's marks as one layer (`Marks.group`) and the map by its layer's opacity; new ticks fade in on a shape layer of their own until the drawing takes them over. A scrollback full enough to drop its top lines numbers its lines again, so a map whose lines mostly changed appears at once instead of fading.

## Command palette

- **Rows are closures (2026-09-30).** `PaletteCommand` (`Calm/Window/PaletteCommand.swift`) is an id, a title, an optional line, an optional key and a `run`. `MainWindowController+Palette.paletteCommands()` builds the list each time ⌘P opens, in category order (agent conversation, session and layout, view and navigation, folder, look, Calm, terminal), so a row that doesn't apply isn't there. Every row is one-shot (the user's rule: a palette runs a command, it isn't a menu to walk), so there is no second stage; what needs a target stays in the right-click menu.
- **One list with the card's menu.** The focused session's rows come from `SessionActionSet`, which the card's right-click menu reads too, so the two offer the same where they overlap; Copy Last Reply, Open Transcript and the global rows are the palette's alone.
- **Every row has a description (2026-10-01).** Calm's rows are cases of `PaletteRow`, whose `help` switches over all of them, so a new row without a description doesn't compile; `PaletteCommandsTests` also holds each to one short line. `PaletteCommand(_ row:, title:)` takes the id and the description from the case. The view shows the selected row's under its name, so that row grows by a line and the rows below it move with each arrow key; the selection change is animated (`Motion.animate`, 0.12 s) so they glide. The author picked this over a fixed line under the list, which would not have moved anything (both were built and compared, 2026-10-01). Ghostty's two rows bring Ghostty's own wording.
- **Ghostty's entries are an allowlist.** libghostty's `command-palette-entry` list, even without the entries that have a key, is dozens of rows of Ghostty's windows, tabs and screen dumps (found by reading the real list, 2026-09-30). `TerminalConfig.paletteActions` names the two that belong (`reset`, `toggle_mouse_reporting`); `PaletteCommandsTests` fails if a Ghostty release renames either.
- **Matching** (`CommandMatcher`): letters in order in the title, earlier and denser first; a description only matches as typed, after every title match. Scattered letters in a long sentence matched "split" to "Toggle Mouse Reporting". Rows are keyed by the command's id in the list, not its position: position-keyed rows showed the previous row's content after a filter (seen in a headless snapshot).
- **Copy Last Reply** reads the transcript when asked: `TranscriptReading.lastReply(of:)` returns the agent's newest message with text, in full, for Claude Code, Codex and pi (their transcripts are JSONL files; `readsLastReply` says which). `TranscriptTail.lastMessage` is a recap cut to a line with its Markdown stripped, and the full text is never kept, since the tail is saved in `state.json`. OpenCode keeps sessions in a database, so it has no such row.
- **Unsplit** (`Workspace.unsplit`) replaces a layout by one layout per pane, in the panes' order; the focused session keeps the layout's id, so what showed it keeps showing it. The controller gives each new layout its workspace view at once, which moves its pane over (a pane in no view would sit loose until chosen), then drops the emptied old view. Go to Welcome Page is `Workspace.deselect`: no layout chosen, the state closing the session in front already leaves.
- **Dump Logs** (`Diagnostics.swift`): `DiagnosticsReport` builds the text from facts and session lines that hold ids, states and agent names only; the trace comes from `/usr/bin/log show` for this process (`processID ==`, since a second Calm or a test would fill it with lines about another instance), 30 minutes. It is written to `~/Library/Logs/Calm` and Finder opens on it; headless it writes to the temporary folder and logs instead of opening Finder. `calm trace` prints the same trace from the CLI, for every launch of the app it came with (Control protocol below).

## Persistence

- **Decided (M2.7): zmx** ([zmx.sh](https://zmx.sh), MIT, actively maintained), pinned in `scripts/zmx.sh` (version and SHA-256) and bundled at `Contents/Resources/bin/zmx`.
- Each session's terminal command is `/usr/bin/env -u ZMX_SESSION <zmx> attach calm-<12 hex>`: attaching creates the zmx session on first use and reattaches, with scrollback, after a relaunch. zmx starts the account's login shell.
  - `env -u ZMX_SESSION`: inside a zmx session that variable makes `attach` switch the *calling* terminal instead of starting a client, which would hijack the terminal Calm was launched from.
  - `ZMX_DIR=$TMPDIR/calm-zmx` (mode 700) keeps Calm's sessions apart from any other zmx use; names stay short because each session is a Unix socket there. `ZMX_NO_DETACH_KEY=1` leaves Ctrl-\\ to programs.
- **A pane starts at its size.** Reattaching after a relaunch hands the running program a terminal of whatever size the new client reports, so that size has to be the final one. libghostty started every surface at an 800×600 placeholder and the config's text size, and the real size came later as a resize it holds for 25 ms. At launch the panes were built before the window had its saved frame or any layout, so zmx's client read 41×13: Claude Code redrew for 41×13, then for the real size, and its screen came back with the footer blank but for the cells it changed later (found in real use, 2026-09-30). Now `MainWindowController` restores the frame before building panes, `makeWorkspace` lays out the new workspace first, and each pane passes its size and the saved text size in the surface config (engine patch 0013), so the command starts with its final grid. The trace line `pane <id>: attaching at 145x44` gives the grid a pane started with. Splits still start at the placeholder: their shell is new. Check: two `scripts/selftest.sh` runs with `--persist --state <one file>`, the first typing a program that logs its size on start and on SIGWINCH; in the second, the trace grid matches `focused pane … grid`, zmx's `init resize` matches it, and the program sees only zmx's same-size SIGWINCH on reattach. Restoring full screen still resizes once, a turn after launch.
- Quitting detaches; closing a session runs `zmx kill <name> --force`. Inside zmx, libghostty's "process running?" check can't see the agent, so a close asks whenever the session has an agent run.
- **Restart** (`Restart`) is an ordinary quit plus a relaunch. Once the quit can't be cancelled (`applicationWillTerminate`, after state is saved), Calm starts a `/bin/sh` helper that waits for Calm's PID to be gone (an unreaped zombie counts as gone; it gives up after 30 s rather than start a second Calm), then runs `open <bundle path>`, retrying for 5 s in case `install.sh` is mid-swap. Two Calms never attach to the same zmx sessions or write the same state. `open` hands its own environment to the app it launches, so the helper gets Calm's environment minus the self-test drivers (`CALM_SELFTEST_*`, `CALM_SNAPSHOT*`): shells keep the same `PATH`, and a Debug or test instance keeps its `CALM_*` isolation instead of coming back on the real Calm's state. Opening by path (checked: Launch Services starts the copy at that path even while another copy with the same bundle ID runs) means a Debug build never wakes the installed Calm. Without `-n`, so a Calm the user opened in between is brought forward, not joined.
- Quit asks only when shells won't survive: zmx unavailable, or persistence turned off mid-run after zmx failed, and libghostty sees a running process.
- **Closing the session on screen selects none.** `Workspace.selectedLayout` is nil when `selectedLayoutID` is (it no longer falls back to the first layout), and `removeSession` clears it when the shown layout goes, so Calm never picks a session for the user (it used to take the newest, wherever that sat in the sidebar). The state is saved and restored like any other: a relaunch after it shows the same empty main area. `MainWindowController.showNoSession` hides every workspace view and follows no folder, and with no pane focused ⌘W and the other pane shortcuts do nothing (⌘W never falls through to closing the window). ⌃Tab from here goes to the first session (⌃⇧Tab: the last). Closing one pane of a split keeps its layout on screen, focus on the sibling; ⌘⇧T reopens the session and selects it.
- **Closing never reaches the next pane.** libghostty queues surface messages by address, and a new surface can be allocated where a freed one was. Killing zmx makes the closed pane's client exit, so its "child exited" could close the pane that replaced it, and then persistence was turned off as "failing" (found in real use: one ⌘W closed two sessions). So: close requests from libghostty run after its call returns; `teardown` drains the mailbox right after `ghostty_surface_free`; a child exit whose runtime is longer than the pane's age is ignored; and only a live pane's exit can turn persistence off. At launch, `calm-*` sessions in Calm's directory that no saved session refers to are killed.
- **Shell integration inside zmx.** libghostty injects Ghostty's shell integration only when the command it runs is a shell, and here it runs zmx. `ShellIntegration` sets the same variables Ghostty would (zsh: `ZDOTDIR` pointing at the bundled integration, keeping the user's in `GHOSTTY_ZSH_ZDOTDIR`; fish and elvish: the integration prepended to `XDG_DATA_DIRS`), and zmx hands them to the shell it starts. `shell-integration = none` in the Ghostty config turns this off. Bash and nushell need their command lines rewritten, so they rely on the process-based folder lookup. zsh starts one step earlier, in Calm's own `.zshenv` (written at each launch before any shell starts, to `~/Library/Application Support/Calm/zsh`): `ZDOTDIR` points there and `CALM_GHOSTTY_ZSH_DIR` at Ghostty's, which it sources next, so Ghostty's puts the user's `ZDOTDIR` back and runs their files as before. Calm's adds one thing, the ⌘ Return binding (Agents → Send with ⌘ Return), registered as a `precmd` function that removes itself, so it binds after the user's `.zshrc`. Checked in a pty with a bare home and with the author's own `.zshrc`, and headless through zmx.
- If zmx is missing or fails, sessions fall back to plain shells for the rest of the run (`CALM_NO_PERSISTENCE=1` forces this).
- App state (projects, sessions, layouts) lives in `~/Library/Application Support/Calm/state.json`: a versioned envelope, written atomically and debounced, and not at all when the file already holds the same bytes (`WorkspaceStore.save` reads it back first): with agents working a save came about every 2 s, and two in five changed nothing (2026-09-30). A file Calm can't read, or one from a newer Calm, is moved aside as `state.unreadable-<time>.json` instead of being overwritten. The window's windowed frame is kept by AppKit's autosave, which doesn't record a window left filling the screen; `Workspace.windowFilled` does (see Window).
- The shared text size (`Workspace.fontSize`, nil at the config's `font-size`) is saved there too. libghostty sizes each surface on its own, so Calm watches `CELL_SIZE` (it fires on every font change, whatever caused it), reads the pane's size back through `ghostty_surface_inherited_config`, and moves the other panes with `set_font_size`/`reset_font_size`; they report the saved size back, which ends the loop. New panes get `set_font_size` rather than the surface config's `font_size`, because only the binding action marks the size as the user's, so a config reload keeps it. With `window-inherit-font-size = false` libghostty won't report the size, and Calm quietly stops syncing.

## Smart links and Copy Cell

- **Links:** libghostty detects URLs and paths. Calm resolves relative paths against the session's working directory, parses `:line[:column]`, and routes to the viewer or the editor (`code -g`, `cursor -g`, `zed`, `xed -l` and so on).
  - As built (M5.1): libghostty's own link regex already matches URLs, absolute, `./`, `../` and `~/` paths with their `:line:column`; its `OPEN_URL` action goes to the pane's host, which knows the session. `Link.parse` (CalmModel) keeps only known schemes as URLs (so `Package.swift:12` is a path), peels up to two trailing numbers, expands `~` and resolves relative paths against the session's folder; a missing file is tried against the project's folder too. `EditorLocator` takes `files.editor` from config.toml (a name or a path) or finds the first installed of VS Code, Cursor, Trae, Windsurf, Zed, Sublime Text, IntelliJ IDEA, then Xcode (last: `xed` exists wherever Xcode does), checking known install paths since a GUI app's PATH is minimal. An `.app` path (Settings → General → Choose Application…) is matched by bundle name to a known editor's tool inside it (so a copy in ~/Applications gets the line too); any other app is opened with the file through NSWorkspace, without the line. Headless self-tests log what they would open instead of opening it.
  - As built (link marks and tag): libghostty highlights links only while ⌘ is held, and its `link` setting can't be set yet (`Config.zig`: "TODO: This can't currently be set!"), so Calm finds links itself. `LinkMatcher` (CalmModel) is libghostty's own pattern (`src/config/url.zig`, adapted for ICU: bounded lookbehind, escaped `[\:`) and is tested against Ghostty's own cases. Each pane (`TerminalSurfaceView+Links`) rescans when its layer gets a new frame, at most every 0.1 s: changed rows drop their marks, and once the rows read the same 0.3 s later it matches every line and keeps the links that resolve (`LinkOpener.resolveExactly` for each of `Link.candidates`, longest first: the pattern lets a path run on across single spaces, and counts a sentence's closing `.` as part of a path, so each try is also tried without trailing `.,;:!?`; the whole text goes first, since a name may end in a dot). Rows the terminal soft-wrapped are joined first (a two-row read without a line break), since libghostty's ⌘-click matches across them. `LinkMarksView`, one per workspace above its panes, draws a small view per mark so each can fade on its own. No resting marks while `ghostty_surface_mouse_captured` (such a screen is redrawn too often); ⌘ hover and click still work there through patch 0011, and the pane drops the hovered link when its rows change (libghostty looks again only on the next pointer move or key). The tag follows `MOUSE_OVER_LINK`, which arrives while libghostty holds its renderer lock, so the pane handles it on the next turn of the main loop (reading the screen takes the same lock). The action says where the link is, not what cells it covers, so the pane matches the row under the pointer again. `LinkTag` (Window) places it from the link's cells and fetches image thumbnails with `QLThumbnailGenerator`. Resting marks can't show OSC 8 links whose label isn't a path or URL. A link a program cut across rows itself (its own line breaks, as an agent's full-screen view draws a long URL or path) is joined by `HardWrap` (CalmModel, unit-tested): a soft line whose last text reaches within `edgeSlack` (3) columns of the last column, followed by a line whose first text is at most `maxIndent` (16) columns in, carries on into it; `LinkMatcher.matches(in:rows:continuations:)` then reads the rows as one, leaving the continuation rows' indent out, and `HardWrap.Joined.crosses` keeps the matches that run over a cut. The pane takes such a match only when a candidate of it resolves (`openable`), so a word that only ends at the edge doesn't glue onto the next row's word for a path; a joined match displaces the per-row pieces that overlap it, and per-row matching is otherwise unchanged. libghostty knows nothing of these links, so the pane does the pointer work itself, before libghostty's: `mouseDown` with ⌘ opens the joined link under the pointer (`openJoinedLink`) and swallows the press and release; `refreshJoinedLinkHover` (pointer or ⌘ changed, once per cell) and `updateLinkHover` (libghostty's link changed) set a `LinkHover` with `isJoined`, which makes the pane show the pointing hand (`currentCursor`) and `LinkMarksView` draw the solid underline. This works with the mouse captured, since none of it waits on libghostty. The cut is a guess (a URL ending exactly at the edge can't be told from a cut one); a border or gutter in front of the continuation, or a cut before the edge, isn't joined.
- **Copy Cell:** read the grid text around the click with libghostty's text API, scan left and right for the nearest vertical border characters and up and down for horizontal border rows, then join the cell's lines and trim padding. Pure function over a text grid, so it is unit-tested with fixtures of real agent tables.
  - As built (M5.2): `CopyCell` and `TextGrid` in CalmModel. The grid is built with display widths (`CellWidth`: CJK, fullwidth and emoji take two cells), so columns match the terminal's. Borders include box-drawing lines and junctions, `|` and `+`; a rule is a row of rule characters with at least one dash. Tables with a rule after every row are delimited by the rules; tables with only a header rule treat each line as a row, except that a line whose first column is empty continues the row above. Wrapped lines join with a space, or without one between two wide characters.
  - The view reads the grid one row at a time (a whole-viewport read joins soft-wrapped lines and shifts the rows) and maps the click to a cell from cell (0,0)'s origin and the cell size. `ghostty_text_s.tl_px_x` is the left padding, but `tl_px_y` is row 0's text baseline, not its top (`Surface.zig`: padding + cell height − the font's baseline, which the API doesn't expose). `ghostty_surface_ime_point` gives the bottom of the cursor's cell (padding + whole cells), so the top padding is the one value a whole number of cells from it and less than a cell above the baseline (`gridOrigin`). Before this, reading `tl_px_y` as the top put a click above a row's baseline (most of the row) on the row above. A small "Cell copied" note fades by the pointer. The right-click menu (when the program isn't capturing the mouse) offers Copy and Paste; its Copy Cell item was removed (2026-09-30, the author's call: ⌥-click and ⌥-drag do it everywhere, in programs that take the mouse too).
  - **⌥-click (2026-09-30):** it replaced ⌥-double-click, which the author disliked, and which in Claude Code's full-screen view handed the first click to the program (it counts clicks itself and selects on a double or triple click). `TerminalSurfaceView+CopyCell` holds an ⌥-press over a cell back from libghostty (`cellGesture`): released within 3 pt, it copies the cell and neither half reaches the program. Moved further, it becomes Calm's own selection inside that cell (`CellDrag`, over the screen as the drag began): `CopyCell.selection` takes the text from the press to the pointer in reading order, held to the cell (past the bottom means its end, past the top its start, beside a line that line's edge) and joined as Copy Cell joins wrapped lines; the release copies it. It was first sent on to libghostty as a drag, but a terminal's selection runs across whole rows, so in a wrapped cell it took the neighbouring cells' text too (the author's report, 2026-09-30), which is what Copy Cell is for. `PaneLinks.cellSelection` holds a band per line, which `LinkMarksView` draws in the theme's `selection-background` at 40% over the text, and which stays 0.6 s after the release to show what was copied. An ⌥-drag that starts outside a table still goes to libghostty (the rectangle selection, or the program's own). After a copy with no capture, a plain press and release is sent too, since libghostty has no action to drop an older selection that would otherwise stay highlighted. The outline comes from `CopyCell.cell` (its lines and columns, not just its text); the pane keeps it in `PaneLinks.cellOutline`, looking the grid up again only when the pointer enters another cell, and `LinkMarksView` draws it (`CellOutlineView`). Checked against Claude Code's own full-screen bytes (2.1.284, a made-up conversation resumed in a pty with a scratch home, so no model call), replayed with its mouse capture on, and the program's mouse reports logged: an ⌥-click or an ⌥-drag inside a cell reaches it as hover only.

## Paste

- A terminal can't carry image data, but agents attach an image from its path. So `TerminalClipboard.plainText` pastes files as their shell-escaped paths, text as text, and an image with neither (a screenshot) as the path of a PNG it saves in `$TMPDIR/calm-pasted-images`, a temporary folder so macOS clears old pastes. A drop onto a pane goes through the same function.

## Text input

- `TerminalSurfaceView+Keyboard` is the pane's `NSTextInputClient`, the one door for input methods, System Dictation, voice input methods and the emoji picker. Committed text is sent to the program as typed keys, never as a paste. Two answers matter to voice input, and both went wrong at first (dictation and 豆包's voice input did nothing, 2026-09-30): `selectedRange()` never says `{NSNotFound, 0}` (it reads as "no insertion point", and dictation won't start), so with no selection it is the empty range at 0; and `insertText` doesn't need a key event in flight, because a voice engine commits from its own callback, after the key that started it. `DictationInputTests` checks both. Headless runs can't drive real dictation or a voice input method, so what they do with these answers is checked by hand.

## Window

- **Square corners when filled (2026-10-07).** macOS rounds every titled window (16 pt on macOS 26), so a filled Calm let the desktop show through a sliver at each corner, against the menu bar and the screen's edges. AppKit has no public API for a window's corners. `SquareCorners` overrides four private methods of `NSThemeFrame` (`_cornerRadius`, `_getCachedWindowCornerRadius`, `_topCornerSize`, `_bottomCornerSize`) once at launch, for every window: they answer 0 for a `CalmWindow` whose `hasSquareCorners` is on and ask AppKit's own for every other window, and `windowCornerMaskChanged` has the frame rebuild its shape when that changes. `CalmWindow` turns it on while `isFilled` and not in full screen, following its own resize, move, screen and full-screen notifications and the app's screen-parameter change (the Dock showing or hiding moves `visibleFrame`). The override checks each method's type encoding first and installs all four or none, so a macOS that drops or changes them keeps round corners; it answers only on the main thread. Checked by reading `_cornerMask`, the shape the window server is handed (`CalmWindowTests`: square for the asking window, round for another at the same time, round again after); not yet seen on a real screen. The idea came from m4rkw/macos-corner-fix (MIT), which swaps the same methods for every window of an app; no code was taken.
- **Hidden sessions don't render:** every session keeps its panes alive, but only the layout on screen draws frames. `PaneVisibility` (unit-tested) keeps the two reasons apart: the pane's layout being the one shown (`restorePaneVisibility`, the session switcher) and the window being visible (`didChangeOcclusionState`); the pane draws only when both hold, and libghostty hears only when that answer changes. With one flag for both, the window coming back into view (another Space, uncovered, unminimized) woke every hidden session's pane until the next session switch: about 2 GB of frame buffers at once with eight sessions open (measured 2026-09-30).
- **Size across launches:** `setFrameAutosaveName` saves the windowed frame, but only for frames the user sets: a window left zoomed, filled or maximized keeps the older windowed frame in the defaults (found by zooming a window headless: the saved frame stayed put), so it used to come back small. `MainWindowController.noteFill` (from `windowDidResize` and `windowDidMove`) records whether `CalmWindow.isFilled` (the frame covers `screen.visibleFrame`, within a point) in `Workspace.windowFilled`, saved with the rest of the state; it ignores full screen and miniaturized windows, whose frames say nothing about the user's choice, and it stays off until `restoreFrame` has run, so restoring isn't taken for leaving the filled state. `restoreFrame` (called from `openMainWindow`) applies AppKit's frame, then `CalmWindow.fillAsLeft`: `zoom` from that frame, which makes AppKit remember it for Zoom, and `frameBeforeFill` for Fill. Without that, a window that opened already filled had no size to go back to, and a double-click on the title strip did nothing. Full screen is kept the same way, apart from the filled state: `windowDidEnterFullScreen` and `windowDidExitFullScreen` set `Workspace.windowFullScreen` (they cover the menu, the green button and Ghostty's `toggle_fullscreen` alike), and `windowFilled` stays as it was under it, so leaving full screen goes back to the filled window. `noteFill` has to skip full screen: on a notched display its frame is a point taller than `visibleFrame`, which passes `isFilled`. After `showAndFocus`, `restoreFullScreen` calls `toggleFullScreen` on the next turn of the run loop; it worked with the app inactive too (a launch with `open -g`), so it doesn't wait for activation. Headless runs never enter full screen, so a test can't take a Space over on the user's screen; the self-test action `calm.window_state` logs the frame and whether the window is in full screen, and full screen itself was checked on screen with a copy of the app (below). Known gap: in one of six test launches that should have restored full screen, the window came back filled but not in full screen, and the next five didn't repeat it; the cause isn't known. The fallback is the filled or windowed window. The defaults key follows the bundle id. The Debug build and its self-test runs are `com.jinhuang.calm.dev`, so their frame is their own and never the installed Calm's (before that they shared it, and in headless runs neither a programmatic resize (`--resize`) nor a zoom wrote it), and `windowFilled` lives in the state file, which self-tests keep apart (`CALM_STATE_FILE`).

## Files and viewer

- **As built (M5.3):** `FilesListing` reads the focused session's project folder off the main thread: `git ls-files -co --exclude-standard -z` (tracked plus untracked, ignored left out), `git status --porcelain=v1 -z -uall` for changes (repository-relative paths re-based with `git rev-parse --show-prefix`, so a project that is a repository's subfolder works), and `git branch --show-current`. Outside a repository it walks the folder breadth first (so a big first folder can't use up the 5,000-file limit before its siblings show), building paths relative to the folder as it goes, which survives symlinked folders (`/tmp` → `/private/tmp`). `GitChange.parse` and `FileNode.tree` (CalmModel, unit-tested) turn the output into the tree. `FilesColumn` owns the SwiftUI view, a width constraint between the sidebar and the terminal area (272 pt at the interface size, updated with the sidebar's in `applyAppearance`), and a 5 s refresh timer that runs only while the column is shown. Rows are tapped, not selected: a list's selection is the system accent, louder than the sidebar's highlight.
- **Changes first (2026-09-29):** line counts come from `git diff --numstat -z --relative HEAD` (staged and unstaged together, as `status` shows them; paths relative to the folder; `LineCounts.parse` keys a rename by its new path and leaves binaries out). `git diff` skips untracked files, so Calm counts their lines itself as git would (`LineCounts.lines`: a last line without a newline counts; a NUL byte in the first 8 KB means binary), bounded because it runs every 5 s: files up to 512 KB, 4 MB per read. A repository without commits has no HEAD, so git counts nothing and only untracked files are counted. `ChangedFile.list` orders the changes by path; `FileNode.rows` flattens the tree through the open folders (`FilesModel.expanded`, emptied for another folder). The tree is a `LazyVStack` of buttons, not an outline `List`, so its chevrons, gutter and row heights match the sidebar's. `ViewThatFits` drops the branch (a `GitLabel`) and a change's folder when they don't fit whole. Self-tests drive it with `files_open:<file>`, `files_expand:<folder>` and `files_state`.
- **Guarded folders are read when opened (2026-09-29).** Outside a repository the walk reads every folder it meets; in the home folder that would include Desktop, Documents and Downloads, which macOS guards, so the first look at the home folder asked for three permissions, and the read waited for the answers while the column stayed empty. `GuardedFolders` (CalmModel) names them; `FilesListing.walk` doesn't enter one below the root unless it's in `opened`, and lists it in `Result.unread` instead. `FileNode.tree(…, unread:)` shows an unread folder as an empty folder; opening it (`FilesModel.toggle`) adds it to `opened` and reads again, so the prompt comes when the user asks for that folder, and every later 5 s listing reads it. A root that is or lies inside a guarded folder is read whole: the user chose it. No probe for Full Disk Access is needed, since the folders stay visible either way. Not covered: a folder the user opened and macOS refused shows empty, with no word why (a quiet note with a link to System Settings → Privacy & Security is the place for it, if it proves confusing). iCloud Drive, removable and network volumes are guarded too but a walk doesn't reach them by itself (iCloud Drive sits in the hidden `Library`). A repository is listed through git, not walked, so none of this applies to it.
- **Finding the column (2026-10-01):** two things tell a new user it exists (FEATURES.md → F10). The sidebar footer's fourth row is `footerRow("Show Files" / "Hide Files", …, on: files.isShown)`; `SidebarView` takes the `FilesModel` itself (observed, unlike `manager.settings`), so its `isShown` redraws the row, and `SidebarActions.toggleFiles` is shared with the title strip. The open column keeps `summary` current from its own 5 s listing, and `refreshSummary` does nothing while it's up (`isShown`). The title row is four explicit `ViewThatFits` children (worktree and readout, worktree, readout, neither) so the readout gives way before the worktree, which gives way before the name or folder; the readout is `nil` while the column is up. The readout reports its frame to `SessionTitleHost` keyed by a per-view id (`setReadoutFrame`), so one variant going can't erase the frame of the one that replaced it; the host answers `hitTest` over the ⋯ button and the readout only. Self-test: `CFFIXED_USER_HOME=<a scratch git repo>` makes the test session's project a repository; add `.gitignore` for `Library/` and `.zsh*`, which the app and the shell write into a redirected home.

## Themes

A theme is a small TOML file with a light and a dark variant (either may be left out; the other then serves both):

```toml
name = "Forest"

[dark]
background = "#1f2e28"
foreground = "#c8c3af"
cursor = "#…"           # optional
selection = "#…"        # optional
palette = "#…, #…, …"   # optional: the 16 ANSI colors, comma-separated
sidebar = "#…"          # optional: the sidebar's background (else derived)
accent = "#…"           # optional: the chrome accent (else Calm's amber); never a state color

[light]
…
```

- **As built (M6.1):** `CalmTheme` and `ThemeLibrary` (CalmModel, unit-tested) read the files with the same flat TOML reader as config.toml. A bad color is dropped and a variant without a background or foreground is left out, each with a logged problem; the rest of the theme still works. Built-in themes are bundled from `Calm/Resources/Themes`; user themes live in `~/.config/calm/themes/`, and one with a built-in's name replaces it. `theme = "Name"` in config.toml picks one.
- **The built-in set:** five themes (Calm, Ink, Dusk, Forest, Plum) in light and dark, written by `scripts/themes.py` from OKLCH values per theme and role, which also checks their contrast. Each is a direction of its own (a hue, a depth or both), not a tint of another: an earlier six came from one generator that changed only the background's tint, and read as one theme six times in the picker. Calm is Ink's neutral gray, hues and accent with a lifted background and softer text. Original palettes, not copied from other themes. Text is 6.4–8.3:1 against the background; the six ANSI hues stay below the text's contrast in dark and at least 4.3:1 in light; bright white stays within 1.2× the text's contrast, since agents draw emphasis in it (and Claude Code's ANSI themes their body text). A unit test holds the shipped files to these.
- **Not the theme's to change:** colors an app sends as truecolor. Claude Code's `dark` theme draws its text in pure white, about 14:1 on Calm, whatever the theme; its ANSI themes, or a custom Claude Code theme with `"text": "ansi:whiteBright"` in `~/.claude/themes/`, follow the terminal's colors.
- **OpenCode wears the theme (2026-09-30).** Its own themes are truecolor too: the default paints near-white text on near-black with bright orange headings on every Calm theme, which the author found hard on the eyes. The shells Calm starts ask it for a theme through `OPENCODE_CLI_CONFIG_CONTENT` (the OpenCode adapter's `shellEnvironment`, next to Claude Code's plugin folder in `AgentIntegrations.environment`, read at each new session), which OpenCode 2 merges over `cli.json` without writing it; 1.x doesn't read it. It's left out when the user named a theme (`theme.name` in `cli.json`, found where OpenCode looks: `$OPENCODE_CONFIG_DIR`, `$XDG_CONFIG_HOME/opencode`, `~/.config/opencode`) or set the variable themselves.
  - **Calm's own theme, `calm`, while OpenCode is connected.** OpenCode's `system` theme takes the terminal's colors but arranges them its own way (2.0.19's code): its agent color and message bars in the palette's magenta (pink on Calm), its boxes in a lift of its own across the whole width, and its dim text in a fixed gray nearly as bright as the text; the author found it "weird", not Calm. So `OpenCodeTheme` writes `~/.config/opencode/themes/calm.json` in OpenCode 2's theme format (read from its built-in `opencode` theme: `base` gives every role as a reference into hue scales, a mode gives the scales): Calm's accent for the agent color, links and the bars, a dim text clearly dimmer than the text, boxes that lift only slightly (5.5% toward the text), headings and bold in the palette's strongest text rather than a color, and a transparent background so the padding and title strip match. OpenCode reads theme files only from a folder (its config's `themes/`, or a project's `.opencode/themes/`), so Calm writes one only for a connected OpenCode (Settings → Agents), with the marker in `$comment` (OpenCode ignores keys it doesn't know); `AgentSetupFiles.syncTheme` writes it while the plugin is there and a Calm theme is on screen (`TerminalTheme.onScreen`: a picked one, or the default unless the user's Ghostty config sets colors), removes it otherwise (Disconnect, the user's own Ghostty colors), and never touches a `calm.json` Calm didn't write. Unconnected, or with the user's own Ghostty colors, the variable asks for `system` instead.
  - **One appearance in the file.** For any theme but `system`, OpenCode picks light or dark from the palette it cached the last time `system` ran, not from the terminal (found when a light-mode test left a light theme on a dark terminal), and a theme with one mode is always shown in it. So the file holds the appearance on screen, and Calm rewrites it at launch, on every config reload (a theme picked, Increase Contrast), on an appearance change and after Connect or Disconnect (`AgentIntegrations.syncThemeFiles`); unchanged colors leave it alone.
  - **A running OpenCode follows.** OpenCode re-reads its theme files on SIGUSR2 (`subscribeRefresh`), and Calm's plugin watches `themes/` and sends its own process one when `calm.json` changes, only while OpenCode listens for it, since an unhandled SIGUSR2 ends a process. Self-tested end to end in a scratch home (`CFFIXED_USER_HOME` and `--agent-files`, OpenCode pointed at it with `OPENCODE_CONFIG_DIR`, a real conversation opened with `--session`, no model call): launch brought the plugin up to date and wrote `calm.json`, OpenCode opened in it, and picking Dusk seven seconds later restyled the running OpenCode. An appearance change in a running Calm wasn't checked headless (a run keeps one appearance).
  - **The costs,** from 2.0.19's code: while the variable is set it outranks `cli.json`, so a theme picked in OpenCode's settings is saved but shows from the next session on (which then leaves the variable out); a shell keeps the environment it started with (sessions run under zmx), so a session from before asks for nothing until a new one; and an OpenCode without the plugin keeps the theme it started with. Softening any app's truecolor in the terminal itself wasn't tried: the nearest thing, Ghostty's `minimum-contrast`, was dropped (see Accessibility), and it would change colors apps chose on purpose.
- **pi wears the theme too (2026-09-30).** pi's built-in `dark`, which the author's settings name, paints the user's message on a blue-green slab, section titles in orange and the prompt's frame in a pink that strengthens with the thinking level; its `system` theme takes the palette but places the colors its own way. `PiTheme` writes `~/.pi/agent/themes/calm.json` for a connected pi in 0.99.1's theme format (its `theme-schema.json`, a test fixture, allows no key it doesn't name, so the marker is an unused entry in `vars`): Calm's accent for the accent and the prompt's frame (a thinking level only strengthens it, from gray when off), a muted and a dim text each dimmer, message and tool boxes that barely lift, headings in the strongest text. Every color is written out and the file holds the appearance on screen, as for OpenCode; the same `AgentSetupFiles.syncTheme` keeps it.
  - **Applied by the extension, not the settings.** pi has no variable for its theme, and `ctx.ui.setTheme` with a name also saves it to `settings.json`, which would carry Calm's theme outside Calm and lose the user's choice. So Calm's extension, at `session_start` and inside Calm only, builds pi's theme object from the file with the class of the theme in use (`ctx.ui.theme.constructor`, the colors split into pi's background roles and the rest) and sets that: an object isn't saved, and pi's theme controller leaves it alone when the terminal's colors or appearance change (`reapplyForTerminal`). pi doesn't watch an object's file, so the extension watches `themes/` and sets the theme again when Calm rewrites it (and closes that watcher at `session_shutdown`, since a reload runs the file again). `/reload`, `/new`, `/resume` and `/fork` emit `session_start` and then call `themeController.applyFromSettings()`, which puts the setting's theme back ~10 ms later (seen on pi 0.99.1, on the real pi in a pty: `dark` at +12 ms), so for two seconds after each `session_start` the extension looks every 10 ms and sets Calm's again wherever pi's has taken its place; there is no event to wait for. It does this only while pi's own theme is a built-in (`system`, `dark` or `light`); a theme the user made stays.
  - **Checked** end to end in a scratch home with the author's setup (`"theme": "dark"`, the extension as installed before): launch brought the extension up to date and wrote `calm.json`, a copy of a real conversation (its folder moved into the scratch home, so pi didn't ask and the real file stayed untouched) opened in Calm's colors, `settings.json` still said `dark` afterwards, and picking Dusk while pi ran restyled it. pi's logo keeps its own colors.
- **How a theme reaches the terminal** (`TerminalTheme`). Ghostty ranks a theme file's colors below any color set directly in the config, wherever it's set, while `theme =` goes to the last file that sets it. So:
  - The **default** theme (Calm) is written as two Ghostty theme files and `theme = light:…,dark:…` in Calm's defaults. A theme or colors in the user's Ghostty config win, so an existing setup carries over, and Ghostty switches light and dark itself.
  - A theme **picked** in Calm is written as plain colors for the current appearance to `choices.ghostty` (with the other terminal-side choices from Calm's settings), loaded after the user's config, so it wins. When the system appearance changes, Calm rewrites it and reloads.
- **Chrome (M6.2):** the sidebar, cards, panels, files column and viewer derive their colors from the terminal's background (`SidebarStyle.derived`). When that background is a Calm theme's, the theme's sidebar color, foreground (for text), accent and red are used instead. The accent colors chrome only (`SidebarStyle.accent`); *needs you* stays Calm's amber (`SidebarStyle.attention`), since a blue or green accent read as *working* or *done*. When the user's own Ghostty colors are in effect, everything stays derived. Glass or solid and card or edge-to-edge are window options (M6.4), not part of a theme.
- **Picker (M6.3):** `ThemePickerModel` gives each theme's colors for the current appearance (background, text, sidebar, hues, cursor, accent); `AppearanceSection` draws them as chips and as `WindowPreview`, a miniature of the window with the picked layout and background. A pick saves `theme` with `CalmSettings.save` and reloads the Ghostty config. Picking Calm, the default, still writes `theme = "Calm"`, so it wins over colors in the user's Ghostty config; only the Ghostty choice removes the key. The **Ghostty** choice appears when `TerminalConfig.userColors` finds colors in the user's own config. A config only resolves `theme = light:…,dark:…` inside a surface, so the pair is read from the files (`CalmTheme.ghosttyThemePair`) and the probe loads one extra `theme =` line per appearance; colors set directly still win, as in the terminal.
- **Window options (M6.4):** `WindowStyle` owns the terminal area's insets and an `NSVisualEffectView` under everything. Glass makes the window non-opaque, shows the effect view, and sets Ghostty's `background-opacity` (0.84) in `choices.ghostty`, so it wins over the user's Ghostty config. The sidebar and files column keep 55% of their color; the viewer and panels stay solid so nothing reads through them. This avoids Ghostty's private-API window blur. Card insets the terminal area by 8 points (sliding through `Motion.animateLayout`) and rounds it (10 points, continuous corners, a faint border) on a window painted in the sidebar's color; the viewer takes the same corners. Settings → Appearance saves each option (a default removes its key) and reloads the Ghostty config only when the terminal side changes (glass, or motion, which turns the cursor shader on and off).
- **Adaptive background:** when an app paints the terminal's background (OSC 11, `COLOR_CHANGE`), the pane's override feeds `applyAppearance`. The chrome derives from the new color (the theme's tints drop, since its background is no longer on screen), and the sidebar eases into it over 0.35 s.
- **Settings screen (M6.5):** `SettingsPage` puts one `NSHostingView` over the whole window, as `WelcomePage` does, drawn in the chrome's `SidebarStyle` (restyled when the theme changes); its list is `SidebarView.width` wide and drawn like the sidebar's footer rows, a size up (`SettingsMetrics`), and a local key monitor takes esc while the page is on top. An extension of `MainWindowController` opens and closes it, hands focus back to the session, and pauses the sidebar peek meanwhile; `select` and the new-session paths close it, and a config reload refreshes its models. Each section has a small `@Observable` model (`ThemePickerModel`, `WindowOptionsModel`, `AgentsSettingsModel`, `GeneralSettingsModel`) that saves through `CalmSettings.save` (a default removes the key; comments and unknown keys stay). The controls in `SettingsComponents` (segmented, switch, buttons, menus) are drawn in SwiftUI because AppKit's only know the system accent. Ghostty's C API can't return `font-family` (a repeatable key has no C value), so `GhosttyConfigText.fontFamily` reads it from the config text; the size is the shared one (⌘+/⌘−) or the config's `font-size`. `SettingsMetrics` holds the page's sizes. Blocked notifications come from `UNUserNotificationCenter.getNotificationSettings` (never asked in self-tests; `CALM_NOTIFICATIONS_BLOCKED=1` shows the notice). The page's scroll view hides its indicators: with them, headless snapshots drew the page blank. Headless self-tests drive it with `settings`, `settings:<section>`, `set:<key>=<value>`, `pick_theme:<id>` and `report:<state>`, and log the files and System Settings pane it would open.
- **Accessibility (M6.6):** `AccessibilitySettings` reads Reduce Motion and Increase Contrast (self-tests force the latter with `--increase-contrast`) and reloads the config when either changes. With Increase Contrast, `SidebarStyle.contrasted()` strengthens the chrome, and `CalmTheme.Colors.contrasted()` (CalmModel, tested on every built-in theme) lifts each text color toward white or black until it reaches 4.5:1. Ghostty's `minimum-contrast` was tried first and dropped: it swaps short colors to white or black, which made dim text brighter than normal text.
- **Interface size:** `InterfaceScale.shared.factor` (an `@Observable`, set from `CalmSettings.interfaceSize` whenever the settings change) multiplies the chrome's sizes: `.calmFont(size:)` for type and `.scaled` for lengths (frames, paddings, spacing, corners; 0 and 1 stay, so hairlines stay hairlines). SwiftUI's Dynamic Type doesn't reach fixed-size fonts on macOS, so the chrome scales itself. The window miniatures in Settings keep their own proportions, and the session switcher's live previews keep their size.
- **Session card sizes:** `SessionCardLayout` (CalmModel, tested) says what goes under a card's title for a size and a state: the recap alone, Full's stacked lines, Compact's merged state and recap (two lines for a state that waits for a look), or nothing. `SessionCard` draws it and colors Minimal's time. `makeSidebar` passes `settings.sessionCardSize` to `SidebarView` as a value, and `applyAppearance` rebuilds the sidebar after `WindowOptionsModel` saves; the list's `.animation(value:)` eases the heights. It first read the setting from `manager.settings` in the body: the settings aren't observed and nothing else in the rebuilt view had changed, so SwiftUI kept the old cards until something it watches moved (the headless probe's workspace writes every 2 s hid it in self-tests; snapshot within a second of the change to see it). A setting the chrome draws from reaches its view as a stored value, like `style`. **Shrink to fit** (`sidebar.cards-fit`): `SidebarView` reports its scroll view's `contentSize` and `containerSize` (`onScrollGeometryChange`) to `SidebarCardFit`, an `@Observable` in the view's state, which asks `SessionCardFit` (CalmModel, tested) for the size to draw. Down is exact (the drawn list is taller than its room); up is a guess from `SessionCardLayout.nominalHeight` (the drawn heights, recaps counted as filling their lines) with a 16 pt margin. The guess can be short (a waiting card's merged line guessed at two lines draws one when its message is short, so Compact's cards come out smaller than guessed and Full's guess from there too small), and the first version flipped at every state change near the edge: the retry block was keyed on a hash of the visible cards, the open groups, the room and the interface size, and working agents change that every few seconds. So the first measurement after a step down, if the hash is unchanged, records how short the guess for the larger size was (`shortfall`, added to later guesses); after a step down growing waits `settle` (30 s), and `SidebarCardFit` schedules a look when it ends; and the retry block stays, now as `drawn`: each size's last drawn height with the contents hash it was drawn with (the rows in open groups, what the cards hold, the number of groups and open groups, the interface size; no longer the room, which the model keeps itself), so a size drawn taller than its room isn't tried with those contents until the room is as tall. When the room is larger than the one the cards last stepped down in (`steppedDownIn`), growing doesn't wait, and a size drawn with the same contents goes by its drawn height, without the margin; in the same room it still takes the guess and the margin, because a recap growing a line changes a card without changing the hash. Found after a real restart: `MainWindowController.init` laid the window out (`buildLayout`'s `layoutSubtreeIfNeeded`) at the saved windowed frame before `restoreFrame` filled the screen with it, so the sidebar's first look had 592 pt of room instead of 1001, stepped Full (998) down to Minimal, waited 30 s and then stopped at Compact (998 + 16 > 1001). `restoreFrame` now runs before `buildLayout`. `SidebarCardFit` keeps the whole `SessionCardFit` after every measurement (unobserved) and observes only the drawn size: keeping it only when the size changed lost what was learned in between. Changes in the first second after the sidebar's first layout apply without animation. Each change leaves a `cards fit: full → compact, list 551 in 506` trace line. `AccessibilitySettings.differentiateWithoutColor` (forced in self-tests with `CALM_DIFFERENTIATE=1`) brings Minimal's state mark back; the system's display-options notification already reapplies the appearance. Self-tests set the size with `--config '[sidebar]\ncards = "compact"\n'` or `set:cards=<size>`.
- Self-tests leave the user's Ghostty config out unless asked (`--ghostty-config`), write Calm's generated files to their own folder (`CALM_SUPPORT_DIR`), and can force the appearance (`--appearance light|dark`, `calm.appearance:<mode>`).

## Motion in the window

- The window's content view is layer-backed, so fades and slides run on Core Animation. Without layers AppKit falls back to timer-driven animation, which never ran when started outside event handling (for example from `calm open`), leaving a new session's workspace at alpha 0. The layout fade is a presentation-only `CABasicAnimation`: the view's own alpha stays 1, so a skipped animation can't leave a session invisible. Overlays (the switcher, the peeking sidebar) are removed on a timer rather than in an animation completion handler, so one can never linger invisibly over the terminal and take clicks.
- `Motion` is the one switch: no animation when the system's Reduce Motion is on or `motion` is `reduced`/`off` in `config.toml`.
- **Session switcher:** a local event monitor sees ⌃Tab before the terminal does and consumes it (and Esc, Return and the arrows while the switcher is open), so Ghostty's own ⌃Tab binding never fires. The switcher shows only after ~160 ms of holding ⌃, like ⌘Tab. Previews are `cacheDisplay` snapshots of each session's pane, refreshed every 250 ms; panes in hidden layouts are un-occluded while the switcher is open so their previews stay live, and occluded again when it closes. It cycles in sidebar order (`SessionManager.orderedSessions`, which ⌘1…9 use too).
- **Sidebar peek:** a 6 pt sensor at the left edge (tracking area only, it never takes clicks) slides a second sidebar view in over the terminal; it slides away 350 ms after the pointer leaves it.

## Motion in the terminal

- **Padding and title strip:** Calm's defaults set `window-padding-color = extend`, so the padding takes the nearest cell's color. libghostty doesn't expose that color, so each pane watches its layer's `contents` (the IOSurface libghostty renders into), samples the middle of the top row at most every 0.1 s (`SurfaceEdgeColor`) in the frame's color space (Display P3), and compares it with the pane's sides (the first and last pixel of 32 rows spread over the height: the padding there takes each row's edge color, see below). When at least half of them agree, the app painted its pane in that color (OpenCode, Neovim) and the strip takes it; half, not most, because one side can be a column in its own shade (Neovim's sign column, a file tree). When they don't, the top row is a band across the top (Claude Code's sticky prompt) and the strip keeps the theme's background. The middle of the pane is never read: it's content. An earlier version fell back to the body's most common shade (three middle rows), and a long diff in Claude Code, green on two of those rows, turned the strip green (found 2026-09-30); content almost never runs out to both sides, an app's background always does. The window paints the title strip with the focused pane's sample, edge to edge on a solid background. The sidebar still derives from the theme's background. Side-by-side splits share one strip, so it follows the focused pane. ## Configuration

- One file: `~/.config/calm/config.toml` (`CALM_CONFIG_FILE` overrides it), read and written by the settings screen. `CalmSettings` reads the flat subset of TOML Calm needs (`key = value`, comments, `[sections]` flattened to `section.key`) and reports malformed lines instead of failing. Each key sits under what it's about (renamed 2026-10-07 from flat names such as `session-cards` and `claude-code-hooks`): `theme`, `motion` and `ui-size` at the top, for the whole window's look; `background` and `layout` under `[window]`; `cards`, `cards-fit`, `footer` and `auto-grouping` under `[sidebar]`; `editor` and `open-in` under `[files]`; `notify`, `sound`, `send-with-cmd-return` and ⌘N's `new-session` under `[agents]`, for every agent; Claude Code's `hooks`, and ⌘N's `skip-permissions`, `worktree`, `flags` and `command`, under `[agents.<agent>]` (`claude-code`, `codex`, `opencode`, `pi`), a section per agent: a key's section is everything before its last dot; `footer` under `[sidebar]` (the sidebar's start rows: written by their hover handle, not by Settings). `SidebarView` gets it as a stored `showsFooter` from `makeSidebar`, like `style`, and keeps the handle's own choice in `footerChoice` until the saved value arrives (a sidebar peek isn't rebuilt when the setting is saved). Headless self-tests click the handle with `footer:hide` and `footer:show`.
- Settings are written one line at a time (`CalmSettings.save`), so comments and unknown keys stay; a section whose last key goes back to its default goes too, unless a comment is left in it. A string is written as a TOML basic string, `\"` and `\\` escaped, and read back unescaped (an agent's flags can hold quotes). Choosing a default removes the key, except the theme (see Themes → Picker).
- `CalmSettings.keys` lists every key with what it takes, its default and what it does, for `calm config` (CLI.md), which checks a value against it (`CalmSettings.change`) before `save`. A key Calm starts reading goes there too, or `calm config` won't know it; tests hold the choices and defaults to the typed accessors' enums, but can't see a key only the app reads (`files.editor`, `files.open-in`, `theme`, `agents.claude-code.hooks`). The agents' options aren't in `CalmSettings.keys`, since only the adapters know them: `Agents.settingsKeys` adds them, and `calm config` reads that.
- Ghostty options load in this order, each winning over the one before: Calm's `defaults.ghostty` (keybindings, padding color, motion, the default theme), the user's Ghostty config, Calm's `choices.ghostty` (a picked theme, glass), then `~/.config/calm/terminal.ghostty` for Calm-only overrides.

## Control protocol

- Unix socket at `~/Library/Application Support/Calm/calm.sock` (mode 600; `CALM_SOCKET` overrides it). One request per connection: a line of JSON with `v` and `cmd`, answered by `{"ok":true,…}` or `{"ok":false,"error":…}`. A request from a newer `calm` (a higher `v`) is refused with a note to update Calm. The types are in `CalmControl` (`ControlProtocol.swift`).
- **One Calm per socket, and a socket that heals (as built, 2026-09-30).** A Calm that starts while another answers on the same socket quits at once, in `main.swift` before the engine, the saved state or any shell is touched (`SingleInstance`, a plain connect without a request). A second copy used to unlink the running Calm's socket and bind its own, so every hook reached the newcomer; when it quit it left a dead socket file, every hook was refused, and the sessions of the Calm still running stopped following their agents: a session that started working stayed gray, one that finished stayed *Working*. This happened when a script ran the app's binary with `--version`. The Restart helper starts the new Calm only after the old one has exited, and self-tests and Debug runs set `CALM_SOCKET` to their own path, so neither is affected. A running Calm also checks every 5 s that the path still leads to its listener (`listenAgainIfLost`): when the file is gone or is what a dead Calm left, it listens again (trace: `control socket lost; listening again`); when a live Calm owns the path, it leaves it alone. Accepted connections set `SO_NOSIGPIPE`, so a caller that hangs up before the reply (a hook that timed out) can't end Calm.
- Commands: `open` (a folder becomes a project with a new session; a file, or `file:line`, opens in the viewer or the editor), `list` (sessions with id, title, project, folder, state, agent and the agent's id for the conversation running or last run there), `status` (a state report, with the agent, its session id, its transcript, the shells still running when the hook knows them, and a compaction starting or ending), `notify`, `search`, which is answered off the main thread since the index has its own queue, and `info` (the answering Calm's process id, bundle path and version, and the named session's state, agent and last report: what `calm doctor` asks; a Calm older than `info` answers "Couldn't read the request.", which doctor reports as too old), and `reload` (re-read config.toml and the Ghostty config, `TerminalEngine.reloadConfig(soft: false)`, as Reload Configuration does: what `calm config` sends after a change, since config.toml isn't watched), and `fork` (below). Search hits carry the conversation's id (`SearchHit.conversation`) for `calm show`.
- `calm hook <agent>` exists only in the CLI: the adapter (`HookReporting`) turns the payload into a `status` request.
- `open` and `list` start Calm when the socket is missing and wait up to 5 s; `status`, `notify` and `hook` never do. `CalmLaunch` picks the Calm: the app the CLI sits in (`Calm.app/Contents/Resources/bin/calm`, through the link on `PATH`), by bundle id only when the CLI isn't in an app, and none when `CALM_SOCKET` names a socket other than the standard one. Found 2026-09-30: `open -g -b com.jinhuang.calm` made a Debug build's CLI start the installed Calm, and a self-test shell whose Calm had quit would have started one on the standard socket that never answered on the test's.
- `calm hook` reads its payload with a deadline and a size limit (`HookInput`: 1 s, 16 MB) besides the socket's 1 s: a hook holds its agent up, and a runner that left stdin open would have held it for good (found in a black-box test, 2026-09-30; Claude Code must close it, since its hooks have returned at once in daily use). The limit was 4 MB, and a longer payload was cut and reported nothing.
- `calm search` reads the index itself when Calm isn't running, or when it hasn't answered after 15 s (a cold index takes it more than 10 s), saying so; an error from Calm is shown and exits 1 rather than searched around (`SearchRoute`), so "update Calm" reaches the user.
- **`calm doctor` (as built, 2026-10-06).** The CLI gathers facts and `Doctor` (CalmControl, unit-tested) turns them into checks, so every verdict is tested without a running Calm: `info` from the socket (2 s), the answering process's start time and the processes running its executable (`ProcessInspector.startDate`, `processes(running:)`: `proc_listallpids` + `proc_pidpath`), the app's Info.plist version and its executable's modification time (`install.sh` builds right before `ditto`, which keeps the time, so it is the install time; the `.app` folder's own date doesn't move), the first `calm` on `PATH` (paths through `realpath`, since Foundation's resolving drops `/private` and `proc_pidpath` keeps it), each agent's link as Settings → Agents sees it (`currentSetup`, `AgentSetupFiles.state`, Claude Code's plugin files in `ClaudeCodeAdapter.pluginDirectory`), and in a Calm shell whether `CLAUDE_CODE_PLUGIN_DIRS` holds that folder. Checked against the installed Calm (an older one answered "Couldn't read the request.") and end to end in a headless self-test, where `$CALM_CLI doctor` found its own session and flagged the `calm` on `PATH` as the installed app's, not the Debug build's.
- **`calm trace` (as built, 2026-10-06).** Runs `/usr/bin/log show --last <t>` (or `stream` for `--follow`) with `--style ndjson` and a predicate on the trace's subsystem and category, `processImagePath` of the app the CLI came with (every launch of it, so a restart and a second copy show, a Debug build or self-test doesn't), and `eventMessage CONTAINS` the session's 8 hex digits. `TraceLog.Printer` keeps each record's time and `eventMessage`, with a heading when the day or the process changes, and skips the closing `{"count":…}`. Tested on records from the real trace (fixture `trace.ndjson`); on the real log, 3 minutes took 0.9 s.
- **`calm fork` (as built, 2026-10-06).** The `fork` request names the session, the prompt (`message`), the folder (`path`) and `background`. `ControlServer.fork` takes the session's conversation (running or last run), the adapter's `forkCommand(agentSessionID:transcriptPath:prompt:)` (Claude Code and Codex append the quoted prompt; the others give nil, so a prompt is refused rather than dropped), and `MainWindowController.forkForCLI` opens it as F12's Fork does, in the source's project (`placementAndFolder`): selected, or with `background` made without selecting (`Workspace.newSession(selecting: false)`, which leaves the session in front unsettled) and its pane made at once at the main area's size, so the agent starts at its shown size rather than the placeholder that garbled a full-screen program after a restart. Sessions it made go into `forkedByCLI`, in memory, and a `fork` naming one is refused. End to end in a headless self-test (it logs the command instead of running an agent): the commands with and without a prompt and `--in`, the background fork never in the trace's `focus arrived` lines while the others are, and the refusals (a fork of a fork, no conversation, pi with a prompt, a missing folder). `--in`: Claude Code 2.1.291, run in a pty with a scratch home and no prompt, loaded a conversation from a git worktree of its repository and said "No conversation found" from an unrelated folder, since it keeps transcripts by folder and knows a repository's worktrees.
- **`calm show` (as built, 2026-10-06).** `SearchIndex.conversation(id:)` finds one conversation by its agent's id or a unique start of it (6 characters or more), a transcript's row before the prompt history's and the newest of several files with one id, with its messages in indexed order. The CLI adds the transcript's tail (`readTail`: Claude Code's recap and tasks; a database path `<db>#<id>` is read through the database), the branch (`AgentAdapter.branch(of:)`: Claude Code's newest `gitBranch`, Codex's `session_meta.git`), the start (the transcript file's creation; not for a database) and, from the running Calm's `list`, the session it is open in; `ConversationReport` (CalmControl) lays it out and leaves out what's empty. Checked on the author's real conversations of all four agents (on a copy of the index, printing which parts were filled, not their text) and end to end in a headless self-test with a scratch search home.
- The CLI is a small separate target (module `CalmCLI`) installed into the app bundle at `Contents/Resources/bin/calm` and linkable onto `PATH`. Beside it, `bin` holds a link to each CalmKit resource bundle (`CalmKit_CalmAgents.bundle → ../CalmKit_CalmAgents.bundle`): a command-line tool's `Bundle.module` looks beside the executable, not in `Resources`, and stops the process when the bundle isn't there, which killed `calm doctor` on 2026-10-07. Checked from a fresh Release build, through a symlink on `PATH` too; `AppBundleTests` holds the links in place.

## Testing

- **Unit:** CalmKit's packages (`swift test`), with fixtures from real transcripts; app-hosted tests in `CalmTests` for code that needs AppKit or the engine.
- **Integration:** control socket round trips, indexer on fixture folders.
- **Cost at rest** (`mise run perf`, `scripts/perf-check.py`, about 2 minutes, not part of `test`): headless runs of the Debug app, each read through the kernel's counters for the process (`proc_pid_rusage`) over 15 s after 10 s to settle, and held to a budget: an idle focused shell (at most 40 M instructions and 60 wakeups a second; 10 and 22 on 2026-09-30), and three working stand-in agents (`scripts/fixtures/agent-standin.sh`, a scratch `CFFIXED_USER_HOME`) with the window out of sight (`calm.window_unseen`; at most 40 M and 80; 9 and 20). The same three in view have the same budget (at most 40 M and 80; 10 and 20 since their marks and light are Core Animation layers, 312 M and 142 before; see Agent marks), and so do they with the one in front compacting (`compacting`: 9.9 M and 17 against `seen`'s 9.8 and 15 on 2026-10-07, the bar's breathing being a layer too). Instructions rather than CPU time: on a busy Mac identical runs took 3–13% of a core, as the work landed on different cores at different clocks, while their instruction counts stayed within a few percent. Checked against the regressions it guards: `custom-shader-animation = true` made the idle run 120 M and 789 wakeups, and marks ticking behind a hidden window made the unseen run 423 M; both failed.
- **Self-tests** (Debug builds): `scripts/selftest.sh` launches the app, drives it through variables read in `Calm/App/SelfTest.swift` (typing, key events, `calm.<action>` hooks in `MainWindowController.performForTesting`, motion probes), saves a snapshot, the screen text and a log, and quits. `CALM_HEADLESS=1` keeps the window invisible, click-through and never key, so a run never takes the user's focus (`Headless`). A headless run holds off App Nap but not the Mac's idle sleep, and quits by itself ten minutes past its snapshot delay: `selftest.sh`'s watchdog only stops the instance it started, and one that no script waited for (a relaunch, or a script killed mid-run) once ran for three hours at 5% of a core, keeping the Mac awake on battery (2026-09-30). Checks read the log and the snapshot; there are no reference images. A snapshot draws Core Animation layers at their model values, not mid-animation: the working mark shows the frame it started on, and `CALM_SELFTEST_SHIMMER_PHASE=0.5` holds the working line's light at one place so it can be compared; `calm.layer_motion` logs whether the animated layers keep to the wall clock.
- **Isolation:** each self-test gets its own `CALM_STATE_FILE`, `CALM_SUPPORT_DIR`, `CALM_CONFIG_FILE`, `CALM_SOCKET`, `CALM_ZMX_DIR`, `CALM_INDEX_FILE` and `CALM_SEARCH_HOME`, plus `CALM_GHOSTTY_CONFIG=none`, `CALM_NO_PERSISTENCE=1` (unless `--persist`) and `CALM_NO_NOTIFICATIONS=1`, so it never touches the installed Calm's state, shells or index. Everything Calm copies or pastes goes through `NSPasteboard.calm`, a pasteboard of its own in a headless run (`calm-selftest`), so a test never reads or replaces the user's clipboard; a hook that saved and put back only text once lost an image the user had copied (2026-09-30). A real program run inside a test can still write the clipboard itself (Claude Code copies a selection through its own `pbcopy` and a native add-on). `UserDefaults` follow the bundle id (see Window): the Debug build's is `com.jinhuang.calm.dev`, so a test never changes the installed Calm's defaults (Debug runs share them with each other).
- Swift Testing throughout; `mise run test` runs everything: the package's tests (`scripts/xcode.sh test-packages`), then the app's (`test-app`), and the second runs even when the first fails. On CI they are separate steps, and Lint, Build and both test steps each run whatever the others did, with a `Runner` step first that prints the cores, memory, OS, Xcode and display scale. Before that change a run stopped at its first red step, so CI showed one failure per run: a package test that failed only on a runner hid two red app tests for three runs (2026-10-06).
- **Tests that depend on the machine (found on CI, 2026-10-06).** A CI runner's display is 1×, an author's Mac is 2×, and a runner has system events a Mac at rest doesn't. `MotionLayersTests` compares the layer mark with SwiftUI's pixel by pixel, and that check was tuned at 2×: at 1× the 26-pixel tile is shrunk about 32× and the two resamplers disagree about as much as a wrong frame or a one-pixel shift (mean 2.6 to 4.1 and 13 to 18% of the pixels off, for a correct mark), so below 2× it only guards what is grossly wrong (mean under 6). `DictationInputTests` asks for "no key press in flight" through `keyTextAccumulator` and the type of `NSApp.currentEvent`, not for `currentEvent == nil`: the app's last event stays current outside any handler, and on a runner it is a system event. A new test that draws pixels or reads the current event should say what it assumes about the machine, and the failure message should print it.
- **Trace (as built, 2026-09-29):** `Trace` writes a timeline of what decides a session's row to the unified log (category `trace`, notice level, so it is kept): `/usr/bin/log show --last 5m --predicate 'subsystem == "com.jinhuang.calm" AND category == "trace"'` (plain `log` is a zsh builtin). Each line is `+seconds since launch`, the event, and the session's first eight hex digits (the ids in `state.json` and the zmx names). It was added to find out why a Restart is slow to show *working*: launch milestones (engine, state restored, control socket listening, probe scheduled, window open), `restore` per session (the saved state and agent), `launch pass` (how many saved runs, how long, and whether it finished before the window or the rows showed as loading) and `settle` per session (what the pass found, and what the row showed before and after), `pane` attach, `probe` (an agent started or ended in the foreground), `agent named` (a hook, or the probe finding a transcript, told which agent and transcript), `report` (source, state, and what the row showed before and after), `ignored` (a report naming an agent other than the one in the foreground, left out; always written), `transcript` (which fields the tail held, and any state change it made), and `control … waited` when a request waited 100 ms or more for the main thread (a hook waits that long too; `calm hook` gives up after a second). Every report and hook is written for the first minute after launch; later only those that changed something. Only states, sources, counts and agent names, never text a user or agent wrote. `SessionProbe`'s own polls aren't traced, so a slow transcript read shows as the gap before its `transcript` line.

## Distribution

- Now: built from source. `install.sh` builds a Release Calm into `/Applications` and links `calm` into `~/.local/bin`. It puts the app together afresh each time (about 4 s; compiling stays incremental) and refuses to install one whose package resource bundles differ from the ones just built: once (2026-10-07), an incremental build kept a stale copy of CalmAgents' bundle inside the app and installed a Calm without the files the commit added; the cause wasn't found, and a new resource folder or an edited file reached the app in every later try, Debug and Release. It swaps the app in with two renames, so a failed copy never leaves no Calm, and doesn't quit a running Calm: macOS keeps the running binary's pages, and the new one starts at the next launch or Restart Calm. The old app is moved aside (`.Calm.app.previous-<time>`), not deleted, while a Calm runs from it (`lsof` names each running Calm's program file where it now is), and goes at a later install. The running one is out of date meanwhile, and that has a cost (the bullet after next). CI (`.github/workflows/ci.yml`, a macOS 26 runner) builds GhosttyKit, then lints, builds and tests every push to `main` and every pull request (each of those reports even when another failed; see Testing). The engine cache (keyed by the pin, the patches and the fetch scripts, and holding the 39 downloaded packages too) is restored first and saved straight after the engine builds, so a later red step doesn't cost the next run the 9-minute build. Of those 39 packages, 32 come from Ghostty's own CDN and 5 from GitHub; `translate_c` comes from Codeberg and `fontconfig` from freedesktop's GitLab, and Codeberg answered 503 for at least 20 minutes on 2026-09-30 (it was fine by 2026-10-06), which failed two CI runs and would have failed a new user's first build the same way. So `scripts/ghostty-deps.py` first uses a copy kept in `scripts/ghostty-mirror/` (`translate_c`, 155 KB, MIT; Zig checks every package against its content hash, so a copy can't change what is built, and a corrupt one fails the build), and a package it can't download is reported and skipped, not fatal: `zig build` fetches again only what it really needs (fontconfig is Linux's; not mirrored, because its release archive exists only on that host).
- **Releases** are tags (`vX.Y.Z`) on `main`, with their notes in CHANGELOG.md. The version is written in two places, `project.yml` (`CFBundleShortVersionString`, which Diagnostics and `install.sh` read, and the generated `Calm/Info.plist`) and `CLI/main.swift` (`calm --version`); a release bumps both, runs `xcodegen generate`, and `VersionTests` fails if the two, or the checked-in Info.plist, disagree. `CFBundleVersion` stays 1 until something (Sparkle) needs it to climb. 0.1.0 is source only: nothing is built for download, because an unsigned download makes every user override macOS's block and answer the folder prompts again after each update (see the next bullet).
- **Local builds are signed ad-hoc; a stable local certificate was tried and dropped (2026-09-29).** macOS keeps a privacy grant (Desktop, Documents, Downloads, Full Disk Access, …) against the app's *designated requirement*, and an ad-hoc signature's is `cdhash H"…"`, a hash of that one build, so each rebuild or `./install.sh` is a new app and gets asked again. (Seen in the unified log on 2026-09-30 and 10-01: after each install tccd logged `Failed to match existing code requirement for subject com.jinhuang.calm` and asked again, for Documents, Media Library and App Management. The TCC database itself can't be read without Full Disk Access, and this machine has no signing identity to try instead: `security find-identity -v -p codesigning` lists none.) A self-signed certificate gives a requirement that survives rebuilds (`identifier "com.jinhuang.calm" and certificate leaf = H"…"`), but the setup cost too much trust: `codesign` refuses an untrusted identity, so trusting it takes a system password dialog; then every `codesign` run asks for the login keychain password (a build signs many binaries, and a run nobody answers fails with `errSecInternalComponent`) unless the key's partition list is set, which means typing the login password into a script. An app or its tooling that asks for a password over and over looks like malware, so Calm asks for none: the certificate, its script, and the `Config/Signing.xcconfig` hook were removed. (An xcconfig include also can't name a path under `$(HOME)`, so a per-checkout file would have needed copying into every worktree.) What keeps prompts few instead: guarded folders are read only when opened (Files and viewer, above), so macOS asks in context, about a folder the user chose.
- **Installing under a running Calm cuts its shells off from guarded folders until it restarts (seen 2026-10-01; cause not proven).** A Calm started at 22:51 was still running when the app on disk was replaced at 23:09, and again at 01:45. At about 01:41 its shells got `Operation not permitted` on `~/Documents/TRAVEL`: `brew` said the working directory must be readable, `mise` warned that it didn't exist or wasn't accessible, a Rust `use` command (`src/commands/use.rs`) panicked on `PermissionDenied`, and `bun` reported "possibly due to low max file descriptors (limit 256)", which I take to be misleading (256 is macOS's ordinary default for an app's children, and the same folder was what failed). sandboxd logged `tcc_server_message_request_authorization(kTCCServiceSystemPolicyDocumentsFolder) failed: … Failed to create Attribution Chain from message`; a banner said "Calm was prevented from modifying apps" (the App Management check; what triggered it wasn't traced). Restarting Calm at 01:49 cleared all of it, even for a shell the old Calm had started. Why isn't known: at 01:19, with the same out-of-date Calm running, tccd had answered `authValue=2` (allowed) for the same folder, so being out of date is not the whole story. `Failed to match existing code requirement` for `kTCCServiceSystemPolicyAllFiles` and `missing 'auth_value' in reply message` for the same service also fill the log at other times; they look like the routine answer when there is no Full Disk Access entry, not the failure. What we do: `install.sh` says so when it finishes, and whoever installs tells the user to restart Calm soon. A real fix waits for a stable signature (next bullet).
  - **2026-10-07: the folder picker too, and what deleting the old app does.** A Calm started at 17:43 had its app replaced at 17:45 and 17:49; New Project then did nothing. The picker's process refused it: `SecCodeCopyGuestWithAttributes failed for process … due to error 100002` (100000 + ENOENT), and `codesign -vv <pid>` on that Calm answered `No such file or directory`: `install.sh` had deleted the moved-aside app, so macOS could no longer find the running Calm's code. A program whose file is only moved stays `dynamically valid`, `valid on disk` (tried on a running ad-hoc bundle moved to `.Tool.app.previous-…`), so `install.sh` now keeps the old app aside while a Calm runs from it. That keeps the picker working; whether it also keeps the shells' guarded folders (the `Attribution Chain` failure above) isn't proven, so the advice to restart soon stays.
- Later: Developer ID signing, notarization, Sparkle updates, a Homebrew cask. A Developer ID identity has a requirement that stays the same across updates, so a user's grants survive them, and it asks the user for nothing beyond macOS's own folder prompts. It is the real answer to repeated prompts for users.
